# eska

Текущий этап разработки и очередь задач: [development tracker](docs/roadmap/README.md).

## Создание проекта

```bash
eska new demo --type configuration --workflow trunk
eska new demo-extension --type extension --workflow github-flow --no-vcs
eska --lang en new demo-report --type report --workflow custom
```

`new` создаёт **новый** каталог с `eska.toml`, `.gitattributes`, `.gitignore`,
`src/` и пустым `src/.gitkeep`. Это каркас для Designer XML, а не готовая
XML-выгрузка 1С. Родительский каталог должен существовать. Существующие файлы,
каталоги (даже пустые) и символические ссылки не изменяются; пути с `..`
отклоняются. Относительный путь вычисляется от текущего каталога или явно
заданного `--project-dir`.

Встроенные `.gitattributes` и `.gitignore` одинаковы для всех типов проекта.
Текстовые файлы нормализуются Git, известные бинарные форматы 1С и медиа
передаются в Git LFS. Служебные файлы инкрементальной Designer XML-выгрузки
`ConfigDumpInfo.xml` и `DumpFilesIndex.txt`, каталог сборки `build/` и локальные
настройки `.vscode/` исключаются. Инициализация Git LFS и блокировки форм будут
добавлены отдельно; `new` пока только создаёт общие правила атрибутов. Шаблоны
обоих файлов хранятся в `assets/project/` и встраиваются в бинарник при сборке.

В интерактивном терминале `eska new demo` запрашивает недостающие `--type` и
`--workflow` в TUI-меню:

- `↑`/`↓` или `k`/`j` — переместить выделение, Enter — подтвердить;
- `1`–`4` — сразу выбрать соответствующую строку, без Enter;
- Home/End или `g`/`G` — первая/последняя строка;
- Esc, Ctrl+C или Ctrl+D — отменить создание без записи файлов.

Для стандартной русской раскладки в меню работают соответствия `j → о`,
`k → л`, `g → п`, `G → П` независимо от `--lang`. Это ограниченный запасной
вариант, а не определение физических клавиш: прочие раскладки автоматически
не распознаются. Соответствия действуют только для навигации, без Ctrl/Alt/Super,
и не меняют аргументы CLI или текстовые данные. Стрелки и Home/End остаются
альтернативой без буквенных привязок. Поддержка новых языков интерфейса не
требует добавлять раскладки.

Выбранная строка выделена маркером, полужирным текстом и одним цветовым акцентом.
Меню работает во временном экране терминала; после выбора или отмены возвращаются
предыдущий экран, курсор и обычный режим ввода. Непустая переменная `NO_COLOR`
отключает оформление, сохраняя маркер выбора. Минимальный размер окна — 50×14;
при уменьшении меню просит увеличить окно и не принимает подтверждение невидимых
строк. Вставка текста не выбирает пункты. Текстовый ввод идентификаторов заменён
на клавиатурное меню; идентификаторы по-прежнему принимаются через CLI-флаги.

TUI выводится только в stderr. При перенаправленном stdin или stderr оба
параметра обязательны; команда не зависает в ожидании ответа. Если оба флага
переданы, терминальный режим не включается даже в TTY.

Типы: `configuration`, `extension`, `processing`, `report`. Workflow:
`trunk`, `git-flow`, `github-flow`, `custom`. Выбор сохраняется в config:

```toml
[project]
type = "configuration"

[vcs.workflow]
preset = "trunk"
```

Секция `[vcs.workflow]` необязательна для ранее созданных проектов. `new` и `init`
сохраняют только выбранный preset. Расширенная policy настраивается в config,
как описано ниже; создание workflow-веток и исполнение policy пока не добавлены.

По умолчанию встроенная библиотека `gix` инициализирует Git с пустой веткой
`main`, без первого commit и remote. Системный Git не требуется; пользовательские
Git-настройки и перенаправляющие переменные окружения не применяются.
`--no-vcs` отключает инициализацию Git, но сохраняет выбранный workflow в config.

При обычной ошибке записи, Git init или проверки удаляется только вновь
созданный каталог. Если сам откат не удался, ошибка сообщает путь оставшихся
файлов. Аварийное завершение процесса и одновременное изменение каталога другой
программой не покрываются транзакционными гарантиями.

Коды `new`: `0` — каркас создан (сообщение и путь в stdout), `1` — ошибка
создания или отмена ввода, `2` — неверные/недостающие параметры. Ошибки идут в
stderr; сообщения и интерактивный выбор доступны на русском и английском.

## Подключение существующей выгрузки

```bash
eska init
eska init existing-project --workflow trunk
eska init existing-project --source sources/designer --workflow github-flow --no-vcs
```

`init [path]` подключает **существующую** Designer XML-выгрузку: создаёт
`eska.toml`, отсутствующие `.gitattributes` и `.gitignore`, а по умолчанию ещё и
отсутствующий Git-репозиторий. Git-файлы берутся из тех же встроенных assets, что
и у `new`, независимо от `--no-vcs`; уже существующие пути сохраняются
байт-в-байт и не объединяются с шаблонами. Путь по умолчанию — текущий каталог;
`--project-dir` задаёт базовый каталог так же, как для `new`. Исходники не
перемещаются и не изменяются; `.gitkeep` не добавляется. Уже существующий
`eska.toml` (включая каталог или висячую ссылку с таким именем) — ошибка, без
перезаписи.

Команда ищет корневой XML-дескриптор непосредственно в корне проекта и в `src`,
без рекурсивного обхода. Распознаются `Configuration` (конфигурация или расширение
по наличию свойства `ConfigurationExtensionPurpose`), `ExternalDataProcessor` и
`ExternalReport` внутри `MetaDataObject` с пространством имён Designer XML.
Свойство `ConfigurationExtensionCompatibilityMode` само по себе не означает
расширение: оно встречается и в обычных конфигурациях. Тип определяется по
содержимому, не по имени каталога; `--type` и отдельного меню типов у `init` нет.

Для другого расположения укажите `--source` — непустой относительный путь от
корня проекта, без `..`; `--source .` выбирает сам корень. Ссылки разрешаются,
но исходники и проверяемые XML-файлы должны оставаться внутри проекта.
Если выгрузки есть и в корне, и в `src`, команда просит выбрать каталог через
`--source`. Несколько корневых дескрипторов в одном каталоге отклоняются:
каждую выгрузку следует подключать отдельно.

Неизвестным остаётся workflow: в TTY выбирается в том же клавиатурном меню, что
и у `new`. Если stdin или stderr перенаправлен, обязателен `--workflow`.
При переданном флаге TUI не включается. `--no-vcs` отключает операции с Git,
но выбранный preset всё равно сохраняется; его policy пока не исполняется.

Существующий Git (в том числе через `.git`-файл или у родительского каталога)
не переинициализируется: config, HEAD, index, refs, remotes и пользовательские
файлы не переписываются. Повреждённые Git-метаданные и bare-репозиторий
отклоняются; `--no-vcs` позволяет подключить исходники без проверки Git.
Если репозитория нет, создаётся новый с пустой веткой `main`, без commit и remote.

До подтверждения меню запись не выполняется. После выбора исходники проверяются
повторно; config и отсутствующие Git-файлы создаются эксклюзивно. При обычной
ошибке откатываются только созданные этим запуском `eska.toml`, `.gitattributes`,
`.gitignore` и `.git`, **не каталог проекта**. Неудачный откат сообщает оставшиеся
пути. Принудительное завершение процесса и внешние конкурентные изменения не
покрываются транзакционными гарантиями.

Ограничения T06: проверяются XML-файлы верхнего уровня выбранных каталогов,
кроме `ConfigDumpInfo.xml`; повреждённый XML не пропускается. Поддерживается UTF-8
(включая BOM), без DTD и внешних entities; лимиты — 64 МиБ и 1 000 000 узлов на
файл. Это распознавание корневого дескриптора, а не полная проверка пригодности
выгрузки к загрузке в 1С. Пустой каркас `eska new` без XML не является выгрузкой
для `init`, а готовый проект уже имеет config и не нуждается в повторном `init`.

Коды `init`: `0` — подключено (сообщение и путь в stdout), `1` — ошибка или
отмена, `2` — неверный/недостающий workflow либо ошибка синтаксиса CLI. Help,
сообщения и TUI доступны на RU/EN; ошибки идут в stderr.

## Клонирование проекта

```bash
eska clone https://example.org/team/project.git
eska clone ../project.git working-copy --remote upstream
```

`clone` создаёт только новый каталог, получает repository и разворачивает рабочее
дерево через `gix`, затем проверяет `eska.toml` обычным project discovery. Имя
каталога по умолчанию берётся из адреса repository без `.git`, имя remote —
`origin`. Существующий путь не изменяется. При ошибке удаляется только каталог,
созданный текущим запуском.

Для HTTP(S) используется встроенный Curl/Rustls transport. Параллельная обработка
pack и checkout включена через `gix/max-performance`. Локальные пути и SSH
используют protocol helpers `git-upload-pack`/`ssh`, как upstream `gix clone`;
для этих transport соответствующая внешняя программа должна быть доступна в
`PATH`. Shallow clone, выбор ветки и submodules пока не поддерживаются.

## Сборка нативного артефакта

```bash
eska build
eska build --output dist/application.cf
eska build --platform-version 8.5.4.1234
eska build --select-platform
eska build --distrobox 1c-ubuntu-env --format json
eska platform list
```

`build` собирает тип проекта в соответствующий нативный файл: `configuration` —
`.cf`, `extension` — `.cfe`, `processing` — `.epf`, `report` — `.erf`. Для
конфигурации и расширения в `ibcmd` передаётся каталог Designer XML, для внешней
обработки и отчёта — единственный подходящий корневой XML-дескриптор.

Версия `ibcmd` должна точно совпадать с `build.platform_version`.
`--platform-version` переопределяет её только для одного запуска, а
`--select-platform` предлагает выбрать одну из найденных платформ и также ничего
не записывает в проект или глобальный конфиг. `eska platform list` показывает
все проверенные через `ibcmd --version` установки текущего раннера; `--format
json` выдаёт схему версии 1.

Параметры машины хранятся вне репозитория в системном пользовательском каталоге
конфигурации. `eska config init` создаёт минимальный конфиг без перезаписи,
`eska config edit` создаёт его при отсутствии, открывает временную копию через
`ESKA_EDITOR`, `VISUAL`, `EDITOR` или редактор ОС, проверяет TOML и только после
изменения сохраняет прежнюю версию рядом как `config.toml.backup-*`:

```toml
[build]
runner = "auto" # auto | host | distrobox
# container = "1c-ubuntu-env"
# platform_arch = "x86_64"
```

Приоритет настроек: CLI, переменные `ESKA_IBCMD` / `ESKA_PLATFORM_ARCH` /
`ESKA_DISTROBOX`, глобальный конфиг, автоматические значения. `auto` сразу ищет
`ibcmd` в `PATH` и стандартном каталоге ОС: `/opt/1cv8/<arch>/<version>/ibcmd`
в Linux или `%ProgramFiles%\\1cv8\\<version>\\bin\\ibcmd.exe` в Windows. Для
`runner = "distrobox"` обязателен `container`; такой раннер применяется только
на Linux-хосте с доступной командой Distrobox.

Для `8.3.27.2325` команда создаёт управляемую временную файловую базу и выполняет
`config import --out`. Временные данные удаляются после успеха, ошибки и
прерывания; существующий артефакт сохраняется при неудачной сборке. Возможный
прямой режим новых платформ 8.5 пока не включён: их фактическая справка в текущем
окружении не проверена.

Human-результат локализован. `--format json` выдаёт стабильную схему версии 1 с
типом и обратимо закодированным путём артефакта, версией платформы и длительностью;
диагностика `ibcmd`, включая `INFO` и `WARN`, построчно выводится в stderr по мере
появления и не загрязняет JSON stdout. Абсолютные пути внутри каталога исходников
заменяются на обозначения объектов Конфигуратора с сохранением конкретного файла
справки, например `Обработка.РаботаСФайлами.Форма.ПрисоединенныйФайл ·
Ext/Help/ru.html`, а префиксы уровней выделяются цветом. Human-режим перед
запуском показывает версию платформы; в интерактивном терминале последней строкой
анимируется состояние сборки, которое удаляется перед итогом. Итог выделяет
результат и показывает путь артефакта как ссылку на содержащий его каталог. При
перенаправлении вывода ANSI-коды, ссылка и анимация не добавляются; непустой
`NO_COLOR` отключает оформление. Коды `build`: `0` — артефакт собран, `1` —
ошибка проекта, инструмента или сборки, `2` — ошибка аргументов CLI.

## Проверка проекта

`eska` ищет ближайший `eska.toml` вверх от текущего каталога и проверяет настройки
и каталог исходников. Другую начальную директорию можно передать явно:

```bash
eska --project-dir /path/to/project
eska --lang ru --project-dir /path/to/project/src/CommonModules
```

Минимальный `eska.toml`:

```toml
[project]
type = "configuration"
```

Настройки сборки необязательны. Для существующих проектов используются
совместимые defaults `8.3.27.2325` и `build/`; явные переносимые overrides:

```toml
[build]
platform_version = "8.3.27.2325"
artifacts_directory = "build"
```

Версия содержит ровно четыре числовых компонента. Каталог artifacts задаётся
относительно корня проекта, не может быть пустым, абсолютным или содержать `..`.
Путь к `ibcmd`, архитектура платформы и Distrobox относятся к конкретной машине
и в `eska.toml` не сохраняются.

`type` обязателен: `configuration`, `extension`, `processing` или `report`.
По умолчанию `source = "src"`, `source_format = "designer-xml"`; другие форматы
пока не поддерживаются. Source — непустой относительный путь без `..`, допустимо
`.`. Неизвестные поля и секции, включая пользовательскую locale, отклоняются.

Корень проекта — каталог найденного config. Source должен существовать и быть
директорией внутри этого корня, в том числе после разрешения символических
ссылок. Начальный каталог и source приводятся к физическим абсолютным путям;
поиск через ссылку идёт по родителям её целевого каталога. Повреждённый или
недоступный ближайший config не пропускается ради родительского проекта.

Коды завершения: `0` — проект корректен (stdout/stderr пусты), `1` — ошибка
поиска, конфигурации или исходников (локализованный текст в stderr), `2` — ошибка
аргументов CLI. `--help` и `--version` не требуют проекта. Diagnostics ошибок
аргументов пока формирует `clap` на английском.

Запуск без подкоманды ничего не меняет и не проверяет XML-содержимое исходников.
Для проекта с настроенным workflow команда `eska status` показывает task/branch/base,
сводку изменений, ahead/behind относительно удалённой базовой ветки и readiness:

```bash
eska status
eska status --format json
```

Human output локализован: подписи выровнены по колонке, а в TTY секции и состояния
получают цветовые акценты. При перенаправлении ANSI-коды не выводятся; непустой
`NO_COLOR` отключает оформление. JSON не зависит от локали, содержит
`schema_version = 1` и считается стабильным API. До реализации locking в T39 поле
`locks` явно содержит `available: false` и `count: null`. Команды `sync`,
`publish` пока не реализован.

## Просмотр изменений

`eska diff` показывает текущие изменения либо разницу между committed Git-состояниями:

```bash
eska diff
eska diff --raw
eska diff --format json
eska diff --semantic
eska diff --semantic --raw
eska diff --semantic --format json
eska diff main
eska diff v1.2.0
eska diff main feature/task
eska diff main --since-branch-point
```

Без revisions команда сохраняет текущую семантику HEAD → index → рабочая копия.
Одна revision сравнивается с локальным `HEAD`, две — друг с другом в указанном
порядке. Поддерживаются локально доступные ветки, теги, полные и сокращённые
commit ID и однозначные Git revision expressions. `--since-branch-point`
использует merge base как начало сравнения и показывает только изменения целевой
ветки. Revision-режим не выполняет fetch и не включает index, рабочую копию или
untracked-файлы.

Изменения ограничиваются корнем проекта, даже если Git-репозиторий находится
выше. Пути выводятся относительно проекта и сортируются по байтовому Git-пути.
Для каждого файла отдельно сохраняются состояния `index` (HEAD → index) и
`worktree` (index → рабочая копия), поэтому файл, изменённый на обоих этапах,
не теряет ни одно состояние. Учитываются added, modified, deleted, type changed,
untracked, intent-to-add и conflicts; ignored-файлы не показываются. Workflow
для чтения diff не требуется.

Human-режим показывает распознанные Designer XML пути как объекты Конфигуратора
и группирует их сначала по верхнему типу метаданных, затем по состоянию. Состояние
показывается один раз для всей подгруппы вместе с количеством объектов; строки
имеют одноколоночные маркеры: `✎` — изменение, `+` — добавление, `−` — удаление,
`↔` — изменение типа, `!` — конфликт, `?` — untracked, `◌` — intent-to-add.
Например, изменения файлов
`CommonModules/ОбщийМодуль1.xml` и `CommonModules/ОбщийМодуль1/Ext/Module.bsl`
объединяются в `ОбщийМодуль.ОбщийМодуль1`, а изменение свойств дочернего объекта
в XML владельца показывается как
`Справочник.Контрагенты.Реквизит.Реквизит1`. Формы, макеты и стандартные модули
также получают логические имена: например,
`Documents/Приход/Forms/ФормаДокумента/Ext/Form/Module.bsl` отображается как
`Документ.Приход.Форма.ФормаДокумента`. Если путь или XML нельзя надёжно распознать,
выводится исходный project-relative путь в группе «Прочие файлы» либо имя
владельца метаданных без недостоверного уточнения.

Файлы справки, модули команд, содержимое форм и макетов, общие картинки,
XDTO-пакеты, схемы WS-ссылок и бинарные варианты модулей сворачиваются в своего
владельца метаданных. Для вложенных подсистем сохраняется полная цепочка дерева,
например `Подсистема.Учет.Подсистема.Продажи`. Служебные файлы корневого `Ext`
относятся к `Конфигурация`; Git-файлы и `eska.toml` остаются обычными файлами.

В TTY заголовки типов выделяются голубым, подгруппы и маркеры получают цвет
состояния, а сами имена объектов сохраняют обычный цвет терминала. При
перенаправлении вывода ANSI-коды не добавляются; непустой `NO_COLOR` отключает
подсветку без удаления символов и группировки.

Object-aware представление рассчитывается только для human-режима. Для текущих
изменений `--raw` выдаёт по одной строке
`<index><worktree>\t<path>` без локализации; пустое состояние обозначается `.`,
остальные — `A`, `M`, `D`, `T`, `?`, `I`, `U`. Небезопасные для строки пути
заключаются в кавычки с escape-последовательностями. JSON имеет
`schema_version = 1`; каждый элемент `files` содержит `path`, `path_encoding`,
`index` и `worktree`. Обычные пути имеют `path_encoding = "utf-8"`, а редкие
не-UTF-8 Git-пути передаются обратимо как percent-encoded байты. `--raw` и
`--format` взаимоисключающие.

Для revisions raw содержит одну колонку `<change>\t<path>` с кодами `A`, `M`,
`D`, `T`. JSON использует schema version 2: `comparison` явно содержит strategy
`direct` или `merge-base`, исходные revisions, полные commit ID и optional
`merge_base_commit`; каждый файл содержит `path`, `path_encoding` и `change`.
Workspace JSON schema version 1 остаётся без изменений.

`--semantic` включает отдельное представление логических событий: добавление,
удаление и изменение объектов, изменение модулей, процедур, функций, форм и
свойств метаданных. Анализ читает только изменённые файлы и точные пары
HEAD/index/worktree либо blob-пары выбранных revisions. Для XML сравниваются
структурные свойства объектов, поэтому изменение только форматирования не создаёт
semantic event. Процедуры и функции распознаются консервативно по завершённым
русским и английским BSL-декларациям; при неоднозначном модуле остаётся только
надёжное событие `module_changed`.

Semantic human-output группирует события сначала по верхнему типу метаданных,
затем по виду события и этапу index/worktree/revision. Заголовок подгруппы
содержит количество событий, а объект выводится полным локализованным путём
Конфигуратора. В TTY применяются те же цвета заголовков и маркеров, что в обычном
diff; перенаправленный вывод остаётся без ANSI, а непустой `NO_COLOR` отключает
подсветку.

Semantic raw содержит строки
`<stage>\t<event>\t<object_id>\t<member-or->\t<path>` без локализации. Semantic
JSON использует отдельную schema version 3 с `kind = "semantic"`, явным
`comparison`, стабильными event names и структурированным объектом. Обычные
file-level human/raw/JSON-контракты и их schema versions 1/2 не меняются.
Three-way semantic merge и сравнение отдельных элементов формы не выполняются.

Команда только читает Git через встроенный `gix`: index, файлы, refs и commits
не изменяются. Коды завершения: `0` — diff получен, включая чистый проект;
`1` — ошибка проекта или репозитория; `2` — ошибка аргументов CLI.

## Просмотр истории

`eska history` показывает локальные commits, достижимые из текущего `HEAD`, от
новых к старым по времени commit:

```bash
eska history
eska history --limit 50
eska history --format json
```

По умолчанию выводится до 20 записей; `--limit` принимает значения от 1 до 1000.
Human-режим содержит сокращённый commit ID, subject, автора, локализованную дату
с часовым поясом и задачу. В интерактивном терминале email автора — гиперссылка
`mailto:`, открывающая почтовое приложение; при перенаправлении это обычный текст.
Workflow для чтения истории не обязателен. Задача показывается только для commit
вне локальной base-ветки, если он достижим ровно из одной task-ветки, имя которой
соответствует workflow policy. Для base, уже влитых, неоднозначных и не
соответствующих policy commits выводится `—`.

JSON не зависит от локали и имеет `schema_version = 1`. Каждый элемент `commits`
содержит полный `id`, массив `parents`, структурированного `author`,
`authored_at`, `subject` и optional `task`. Кодировки имени, email и subject
указаны явно; не-UTF-8 Git-данные передаются обратимо в percent encoding.

Команда читает refs и commits через встроенный `gix`, не выполняет fetch и не
изменяет HEAD, refs, index или рабочие файлы. Коды завершения: `0` — история
получена, включая пустую; `1` — ошибка проекта, policy или репозитория; `2` —
ошибка аргументов CLI. Graph renderer, собственный индекс истории и provider API
не входят в первую версию.

## Сохранение изменений

`eska save` сохраняет все текущие изменения внутри корня проекта в один commit:

```bash
eska save -m "feat: Добавлен новый справочник"
eska save
```

С `-m` используется указанное сообщение без запуска генератора и редактора. Без
`-m` команда строит deterministic draft: Conventional Commit title получает
semantic scope при одном типе метаданных, body перечисляет semantic events и
оставшиеся file-level пути. Draft локализуется выбранным языком CLI, не содержит
служебных bidi-символов и открывается в настроенном Git editor перед commit. Если
Designer XML нельзя надёжно разобрать, генератор сохраняет точные file-level пути
вместо недостоверных semantic events. Пустое итоговое сообщение, отсутствие
изменений, detached HEAD и конфликты в файлах проекта отклоняются до создания
commit; репозиторий без первого commit поддерживается.

Для вложенного проекта commit включает staged, unstaged, deleted и untracked
файлы только ниже его корня. Изменения и staging соседних проектов сохраняются и
не попадают в commit. Перед внутренней подготовкой файлов команда запоминает Git
index; при ошибке staging, editor, hook или commit исходный index восстанавливается
байт-в-байт. Рабочие файлы команда не откатывает. Аварийное завершение процесса и
одновременное внешнее изменение index не входят в гарантию восстановления.

Команда использует системный Git через единый infrastructure layer, чтобы
соблюдать repository config, editor и hooks. Техническая staging area остаётся
внутренней деталью. Коды `save`: `0` — commit создан; `1` — ошибка preflight,
Git или проекта; `2` — ошибка аргументов CLI. `--interactive`, `--auto` и
AI refinement пока не реализованы.

## Запуск задачи

`eska start <task>` начинает работу по настроенной workflow policy:

```bash
eska start FI-1234
```

Если remote из workflow policy настроен, команда получает его refs, проверяет
связь локальной и удалённой base-веток и обновляет локальную base только
fast-forward. Если remote не настроен, fetch пропускается и рабочая ветка
создаётся от локальной base; успешное сообщение явно отмечает этот режим.
Trunk использует `task/FI-1234` от `main`, Git Flow —
`feature/FI-1234` от `develop`, GitHub Flow — `feature/FI-1234` от `main`.
Активная ветка регистрирует текущую задачу: отдельный state-файл не создаётся.

Preflight проверяет весь Git worktree, даже если проект лежит в его подкаталоге.
При staged, unstaged, untracked или конфликтующих файлах команда завершается до
fetch и ничего не переключает. Также отклоняются detached/unborn HEAD,
отсутствующая или разошедшаяся base и уже существующая task-ветка. Ошибка доступа
к настроенному remote содержит его имя, безопасно отображённый fetch URL и
исходную причину сетевого backend. Пароль в стандартной password-части URL
заменяется на `redacted`, в том числе в диагностике. Fetch, проверка ancestry и
fast-forward неактивной base выполняются через `gix`. Обновление неактивной ref
использует compare-and-swap и отклоняется, если base занята другим linked
worktree. Настройки credentials и транспорта сохраняются. System Git заранее
выбирается только для remote-helper transport, который не поддерживает
закреплённая версия `gix`; произвольная ошибка `gix` не запускает fallback.
Обновление активной base и переключение на новую ветку остаются в изолированном
system Git слое, чтобы согласованно изменить HEAD, index и worktree.

Коды `start`: `0` — ветка создана и активирована, `1` — ошибка preflight, Git или
проекта, `2` — ошибка аргументов CLI. Human output и ошибки доступны на RU/EN.
`--kind hotfix`, автоматический shelve и запуск из существующей task-ветки пока
не поддерживаются.

## Переключение задач

```bash
eska switch FI-1234
eska switch --base
```

`switch <task>` активирует уже существующую локальную task-ветку по workflow
policy; отсутствующую ветку создаёт только `eska start`. `switch --base`
временно возвращает на локальную policy base без завершения и удаления задачи.
Команда не выполняет fetch, не создаёт ветки и не хранит отдельное task state.

Перед переключением проверяется весь Git worktree, включая файлы вне вложенного
проекта. Любые staged, unstaged, untracked или конфликтующие изменения
отклоняются с предложением выполнить `eska save` либо отменить их. Локальные refs
и dirty state проверяются через `gix`; согласованное изменение HEAD, index и
worktree выполняется системным Git через единый infrastructure layer без
автоматического выбора remote-ветки.

Коды `switch`: `0` — выбранная ветка активирована; `1` — ошибка preflight, Git
или проекта; `2` — отсутствующий либо конфликтующий target. Human output и
ошибки доступны на RU/EN. Автоматический shelve пока не поддерживается.

## Завершение задачи

```bash
eska finish
```

`finish` работает только из активной task-ветки, определённой текущей workflow
policy. Команда отклоняет unsaved changes во всём worktree, detached/unborn HEAD
и незавершённые merge, rebase, cherry-pick, revert, apply-mailbox или bisect.

При настроенном policy remote сначала выполняется fetch и локальная base
обновляется только fast-forward по тем же правилам, что у `start`. Для
`require-integrated` текущий task commit должен быть достижим из свежей remote
integration target; без настроенного remote проверяется локальная integration
target. Для `require-published` task commit должен быть достижим из remote
task-ветки. После успешной проверки команда переключается на локальную base и
удаляет task-ветку только при `delete_local_branch = true`.

Команда не публикует и не интегрирует изменения, не удаляет remote-ветку и не
создаёт отдельное task state. Ссылки проверяются через `gix`; task-ветка
удаляется compare-and-swap только после переключения и только если не изменилась.
System Git используется лишь для согласованного переключения HEAD, index и
worktree на base.

Коды `finish`: `0` — policy выполнена и локальное завершение закончено; `1` —
ошибка preflight, refs, fetch или переключения; `2` — ошибка синтаксиса CLI.
Human output и ошибки доступны на RU/EN.

## Слой чтения Git-репозитория

В библиотеке доступен `vcs::repository::Repository`: `discover`, `head`,
`references`, `history(limit)`, `status`, `divergence(reference)`, проверка
ancestry и защищённое обновление неактивной ref. Команда
`eska status` собирает эти данные через locale-independent `project::status`,
`project::history` консервативно связывает commits с task-ветками, а
`project::start` исполняет проверенный task plan, `project::save` формирует
project-scoped commit с восстановлением index при ошибке, `project::switch`
проверяет и активирует существующую workflow-ветку, а `project::finish` проверяет
publication/integration refs и завершает локальный lifecycle задачи. Остальные
изменяющие VCS-команды ещё не добавлены.

Discovery ищет ближайший репозиторий вверх от существующего каталога, разрешает
символические ссылки, поддерживает `.git`-файлы и linked worktrees. Bare и
повреждённый ближайший репозиторий возвращают ошибку. Общая граница открытия
используется также в `init`; переинициализации существующего Git не происходит.
Читается локальная конфигурация репозитория, без пользовательских/system config
и перенаправляющих Git-переменных окружения.

HEAD различает ветку без коммитов, обычную ветку и detached HEAD. Refs возвращают
полные имена и исходные targets, включая symbolic refs и объекты аннотированных
тегов. История ограничена количеством коммитов и возвращается от новых к старым
по времени commit; shallow boundaries соблюдаются.

`vcs::status::Status` разделяет изменения в индексе и рабочем каталоге, отмечает
конфликты и intent-to-add. Untracked-файлы перечисляются по отдельности,
ignored-файлы исключаются. Пути отсортированы и хранят исходные байты, включая
не-UTF-8 имена. Перемещения представлены удалением и добавлением, без поиска
сходства; `changed_paths()` возвращает оба пути из готового результата.
Операция не записывает index и не разбирает XML. Репозиторий не блокируется на
время чтения: одновременные внешние изменения не образуют атомарного снимка.

Чтение обычных репозиториев выполняется через встроенный `gix`, без системного
Git. Локальные атрибуты и фильтры обрабатывает `gix`;
настроенный внешний фильтр может требовать отдельный executable. Ahead/behind
считается по локальному commit graph относительно полного имени ref. Сетевой
слой `vcs::network` объединяет clone и fetch через `gix`. Системный Git из
`vcs::command` остаётся для remote-helper fetch fallback, fast-forward активной
base, переключения ветки, staging и commit. Эти вызовы не разбирают human output.

## Workflow policy

Модель workflow проверяет настройки и строит декларативный план задачи. Встроены
presets `trunk`, `git-flow` и `github-flow`.
Загрузка config не запускает Git-операции и не требует наличия репозитория.

`trunk` создаёт short-lived ветку `task/{task}` от `main`, синхронизирует её
через rebase на `origin/main`, публикует task-ветку и требует её интеграции в
`main` через MR перед завершением. После подтверждённой интеграции план разрешает
удалить локальную task-ветку; удаление remote-ветки не подразумевается.

`git-flow` создаёт `feature/{task}` от `develop`, синхронизирует её через rebase
на `origin/develop`, публикует feature-ветку и требует интеграции обратно в
`develop`. В policy зарезервированы ветки `release/{task}` от `develop` и
`hotfix/{task}` от `main`, но их планирование и исполнение остаются отложенными.

`github-flow` создаёт short-lived ветку `feature/{task}` от `main`, выполняет
rebase на `origin/main`, публикует ветку и требует подтверждённой интеграции через
PR/MR в `main` перед локальным удалением. Создание PR/MR провайдером не входит в
декларативный plan и остаётся отдельной задачей.

Имена веток и другие отдельные правила можно переопределить прямо у выбранного
preset. Например, Trunk с принятой в организации базовой веткой `master`:

```toml
[vcs.workflow]
preset = "trunk"

[vcs.workflow.policy]
base_branch = "master"
task_branch_template = "task/{task}"
integration_target = "master"
```

`base_branch` определяет ветку для `start` и `switch --base`,
`task_branch_template` — имена task-веток, `integration_target` — ветку, в
которую задача должна быть интегрирована перед `finish`. Для Trunk и GitHub Flow
`base_branch` и `integration_target` обычно совпадают, поэтому при переходе с
`main` на `master` нужно изменить оба поля.

Пропущенные поля наследуются от `trunk`, `git-flow` или `github-flow`, явное
`false` сохраняется. Config загружается и записывается обратно без
материализации остальных defaults. `custom` остаётся для самостоятельной policy
или наследования через `extends`; у именованного preset поле `extends`
запрещено.

Самостоятельная custom policy без `extends` должна явно задать все поля:

```toml
[vcs.workflow]
preset = "custom"

[vcs.workflow.policy]
base_branch = "main"
working_branch = "task-branch"
task_branch_template = "feature/{task}"
remote = "origin"
sync_strategy = "rebase"
integration_target = "main"
publish = "push-task-branch"
finish = "require-integrated"
delete_local_branch = true
```

| Поле | Значение |
|---|---|
| `base_branch` | Локальное имя базовой ветки, например `main` или `develop` |
| `working_branch` | `task-branch`; работа напрямую в базовой ветке отложена |
| `task_branch_template` | Корректное имя ветки с одним маркером `{task}` |
| `remote` | Имя remote одним компонентом, например `origin`; не URL |
| `sync_strategy` | `rebase`, `merge`, `fast-forward-only` |
| `integration_target` | Локальное имя ветки для интеграции |
| `publish` | `push-task-branch` или `disabled` |
| `finish` | `require-published` или `require-integrated` |
| `delete_local_branch` | `true` или `false`; удаление допустимо только при `require-integrated` |

`require-published` несовместим с `publish = "disabled"`. Условия проверяются
снова после применения overrides к базовой policy. Существующий config только
с `preset = "custom"` остаётся допустимым выбором без настроек; попытка получить
из него полную policy возвращает ошибку недостающего поля.

В библиотеке настройки доступны через `ProjectConfiguration::workflow_settings()`.
Вызов `settings.resolve(None)?.plan("FI-1234")` для `trunk` получает план с
веткой `task/FI-1234`, sync ref `refs/remotes/origin/main`, integration target,
намерением публикации и условиями завершения. Тот же вызов работает для
самостоятельной полной custom policy.
План не зависит от локали, времени или состояния файлов.

Task ID подставляется буквально одним компонентом пути, без преобразования
пробелов или изменения регистра. Пустые и некорректные Git-имена, ведущий `-`,
полные `refs/...`, дополнительные маркеры шаблона и совпадение рабочей ветки
с базовой или integration target отклоняются. Проверки существующих веток,
dirty state, публикации и интеграции относятся к будущему исполнителю команд.
Удаление remote-ветки не подразумевается. CLI пока только проверяет config;
ошибки policy выводятся на RU/EN в stderr с кодом `1`.

## Навигация по исходному коду

Обработчики команд находятся в `src/cli/commands/`: для изменения `init`
откройте `init.rs`, для `new` — `new.rs`. Операции без CLI находятся в
`src/project/`, конфигурация — в `src/config/`, Git и workflow presets —
в `src/vcs/`. TUI и локализация принадлежат `src/cli/`.

Подробная структура, границы модулей и карта «что изменить → какой файл открыть»:
[навигация по исходному коду](docs/architecture.md).

## Тестирование при разработке

```bash
cargo fmt --check
cargo check
cargo clippy --all-targets --all-features -- -D warnings
ESKA_TEST_ROOT="$(realpath ../eska-playground)" cargo test
```

Все ручные запуски CLI выполняются только внутри соседнего каталога
`eska-playground`, в отдельных demo-проектах. Автоматические
CLI-тесты с `ESKA_TEST_ROOT` создают там уникальные временные подкаталоги и
удаляют только их; существующие demo не изменяются. На других машинах и в CI
без этой переменной тесты используют системный временный каталог.
Git-сценарии в `tests/vcs/` используют системный Git только для подготовки
реальных репозиториев; отдельный дочерний тест проверяет чтение без Git в `PATH`
и с перенаправляющими переменными окружения.
