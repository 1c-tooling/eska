# T70: производительность реального stdio-процесса

Замеры от 2026-09-18: Linux, Rust 1.98.1, профиль `dist` (оптимизация и thin LTO),
тот же большой стенд и оборудование, что в [T68](metadata-performance.md).
Платформа 1С, сборка конфигурации и расширение VS Code не запускались.

## Методика

Отдельный Python-клиент запускает новый `eska ide --stdio` для каждого измерения.
Время включает framing, передачу через pipes, JSON и ожидание ответа. Stdout
постоянно читается отдельным потоком. Пять запусков без дискового кеша и пять
повторных с ним; у small/synthetic отдельно записан первый запуск заполнения.
Большой стенд использует ранее заполненный кеш T68: повторное первое заполнение
не измерялось, существующий кеш не удалялся. Файловый кеш ОС не очищался.

Во время серии не запускались Cargo и другие нагрузочные проверки. Индексация
явно запускается клиентом; во время работы клиент запрашивает status с паузой
10 мс, что позволяет измерить задержку интерактивного запроса между descriptors.
Поиск: четыре запроса по десять повторов, как в T68; p95 — 38-е значение из 40.
Root/index p95 при пяти запусках — максимум выборки. Память — Linux VmHWM
серверного процесса, без Python-клиента. Замеры не являются гарантией задержек
на другой машине или в Extension Host.

Большой стенд: 131381 индексируемый объект, ошибок descriptors — 0.
Root SHA-256: `874f9727197a8d159acef09a9b4e30c0cc6c540c6f04fb4cd5bfb8bff864f0dc`.
Проверка хеша до/после прошла. `diskCache:false` не пишет файлов; при true backend
записывает только производный кеш. Отдельные process-тесты сравнивают все байты
XML/BSL и manifest, включая случаи с включённым кешем.

Худшая задержка status во время индексации — 133,28 мс: один XML нельзя прервать
посередине разбора. Это укладывается в ориентир 200 мс T68; обычный выбор узла
после индексации не ждёт полного обхода. Максимумы по большому стенду:

- Первое раскрытие: 5.74 мс.
- Первое чтение свойств: 9.38 мс.
- Повторные свойства, p95: 5.51 мс.
- Фильтр корня: 2.64 мс.
- Refresh одного объекта: 21.52 мс.

Бюджеты T68 для открытия, раскрытия, повторного выбора, поиска, индексации,
refresh и памяти соблюдены. В этой серии дисковый кеш не дал устойчивого ускорения всех
сценариев: он исключает повторный XML parse, но добавляет чтение/проверку файлов;
ускорение конкретного сценария не обещается. UI-проверка остаётся в T81.

Отдельный контрольный запуск финального backend после проверки завершения:
open 124,50 мс, индекс 8,607 с, поиск p95 27,40 мс, peak RSS 190,4 MiB.
Он также укладывается в бюджеты; исходная серия выше не пересчитывалась по
этому одиночному запуску. Его raw результат сохранён отдельно в том же JSON.

## Воспроизведение

```sh
cargo build --profile dist
python3 tools/ide-protocol-bench.py small
python3 tools/ide-protocol-bench.py synthetic
python3 tools/ide-protocol-bench.py big
python3 tools/ide-protocol-bench.py big --cached
```

`--runs` задаёт число свежих процессов; `--binary` — путь к executable.
Small/synthetic создаются только во временном собственном каталоге соседнего
`eska-playground` и удаляются после измерений. Big читает
`../eska-playground/big_configuration_temp`; команда не собирает проект 1С.
