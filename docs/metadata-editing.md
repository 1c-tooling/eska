# Редактирование существующих свойств

Редактор VS Code и `eska metadata` используют один core API `ProjectSession`:
схема → проверенный план → запись. Источник — Designer XML. EDT нужен только
для воспроизводимого извлечения справочника при разработке, не при работе ESKA.

Архитектурное правило для дальнейших операций изменения проекта: человек и ИИ
используют общий backend. Операция публикует машиночитаемые допустимые значения,
ограничения, preconditions и preview; эти ограничения проверяет core, независимо
от клиента. Новый UI не должен становиться единственным способом изменения.
Нынешняя поставка реализует это правило для существующих свойств.

## CLI для ИИ и скриптов

```bash
eska metadata inspect --format json
eska metadata inspect --object 'catalog:Товары/attribute:Артикул'
eska metadata types types.json
eska metadata choices reference.json
eska metadata check change.json
eska metadata apply change.json
```

В workspace укажите один member через `-p NAME`; `--project-dir` выбирает
контекст. Вместо файла запроса можно передать `-` для stdin. Лимит запроса —
1 MiB. `inspect`, `types`, `choices` и `check` не изменяют исходники и не создают disk cache.

`inspect` возвращает объект, свойства, непосредственных потомков через группы
дерева и `editing`: точный SHA-256 файла `snapshot`, источник, `writable`,
профиль справочника, `fields`, `readOnlyProperties`, возможности undo/redo.
В новом процессе CLI история пуста; последовательная история принадлежит IDE session.
`fields` — закрытый список разрешённых операций. Отсутствующее поле нельзя
изменить, даже если его значение выглядит как строка или число.

Запрос `types`:

```json
{"schemaVersion":1,"objectId":"catalog:Товары/attribute:Артикул","path":[{"key":{"namespace":"http://v8.1c.ru/8.3/MDClasses","name":"Type"},"occurrence":0},{"key":{"namespace":"http://v8.1c.ru/8.1/data/core","name":"Type"},"occurrence":0}]}
```

Для `check` и `apply` возьмите `objectId`, `snapshot` и **точный `path` из inspect**:

```json
{
  "schemaVersion": 1,
  "objectId": "catalog:Товары",
  "snapshot": "SHA-256 из editing.snapshot",
  "path": [{"key":{"namespace":"http://v8.1c.ru/8.3/MDClasses","name":"Comment"},"occurrence":0}],
  "change": {"kind":"text","value":"Новый комментарий"}
}
```

`text` передаёт также boolean (`"true"`/`"false"`), число и технический токен
перечисления. Схема содержит допустимые `values` и RU/EN `options`, ограничения
числовых параметров. Смена типа использует
`change:{kind:"dataType",key:{namespace,name}}` из ответа `types`.
Для `schema.kind:"reference"` команда `choices` принимает такие же ключи запроса,
как `types`, и возвращает `value`, `objectId`, `metadataKind` и RU/EN `caption`.
Выбранный `value` передаётся через `change:{kind:"text",value}`. Core повторно
проверяет существование объекта, класс ссылки и допустимого владельца формы.
`nullable:true` разрешает пустую строку для очистки одиночной ссылки.
Существующие строки списков ролей имеют `nullable:false`; дубли ролей отклоняются.
Клиент не передаёт XML, byte offsets, файловые пути для записи или произвольный
patch. `check` возвращает рассчитанные core-ом замены UTF-8 байтов и признак
`changed`; эта проверка не резервирует файл. `apply` повторяет все проверки.

Один stdout JSON: `{schema_version:1,result:...}` либо
`{schema_version:1,error:{kind,details}}`. Успех — exit 0, доменная ошибка — 1,
ошибка аргументов CLI — 2. Ответы не зависят от `--lang`; help локализован.
Основные ошибки: `property_conflict`, `property_invalid`, `property_unsupported`,
`property_read_only`, `property_write_failed`. `property_committed_refresh_required`
означает, что запись уже состоялась, но обновить представление не удалось:
нужно повторно прочитать объект, **не повторять apply**. После обрыва процесса
результат также следует выяснять чтением, а не автоматическим повтором запроса.

## Поддерживаемая область

Редактируются известные строковые, булевы и перечислимые свойства, содержимое
существующих языковых строк, проверенные вложенные поля и параметры типов.
Можно заменить существующий тип и его qualifiers, сохранив количество типов:
строка, число, дата, булево, хранилище значения, UUID и перечисленные backend-ом
ссылочные типы существующих объектов текущего проекта. Повтор одного типа
отклоняется. Разрядность числа — 1–38, дробная часть не превышает разрядность;
схема учитывает текущий соседний параметр.

Поддержаны одиночные ссылки на общие формы, язык, стиль, хранилище настроек,
нумератор, справочник, планы счетов/расчёта/видов характеристик, задачу и регистр
сведений; основные формы с доменом конкретного владельца выбираются среди его
форм. В списках основных ролей и ролей ограничения автономной конфигурации можно
заменить существующую строку. Пустой список остаётся для чтения.
Основная и дополнительная формы обработок/отчётов, включая внешние, выбираются
среди собственных форм. «Форма выбора» реквизита выбирается среди форм его
единственного ссылочного типа; для составного/нессылочного типа список пуст.
Правило подтверждено провайдерами EDT и загрузкой XML в платформу 8.3.27.2325.
Минимальное и максимальное значения обычных и стандартных реквизитов доступны
как `schema:{kind:"decimal",nullable:true}`. Пустая строка очищает границу;
число записывается в принятом Designer формате `xs:string`. XML-аннотация
переключается между `xsi:nil` и `xsi:type` только внутри выбранного элемента.

«Значение заполнения» реквизита использует `schema.kind:"value"`: `key` хранит
текущий тип (null — не задано), `types` содержит допустимые expanded QName,
RU/EN подписи и ограничения длины строки, точности/знака числа, частей даты.
Изменение имеет вид `change:{kind:"value",key:{namespace,name},value:"..."}`.
Для очистки передайте `key:null,value:""`; пустая строка с ключом `xs:string`
остаётся отдельным значением. Даты — календарные значения без часового пояса
`YYYY-MM-DDTHH:mm:ss`; проверяются календарь и заданные части даты.
Для ссылочного типа запрос `choices` дополнительно принимает его `key` и
возвращает пустую ссылку, существующие значения перечисления или однозначные
предопределённые элементы. Core повторно проверяет принадлежность выбранного
значения этому типу. Произвольные типы, имена и runtime-данные записать нельзя.

Не поддерживаются добавление/удаление элементов, Name/UUID и другие внутренние
идентификаторы, языковые коды, переключение формата формы/макета, multi-file
операции. Неизвестные writer mappings, остальные домены ссылок, TypeSet,
редактирование самих предопределённых данных и числовые свойства без проверенного диапазона остаются
для чтения. Наличие свойства в модели EDT само по себе не разрешает запись.

`fields.tsv` и `enums.tsv` в `src/project/metadata_edit` содержат технические
идентичности модели EDT, не переводы. Основание — те же активные bundles и
SHA-256, что в [каталоге платформы](platform-catalog.md). Профили: 8.3.27 и 8.5.1;
последний выбирается при `build.platform_version = "8.5.1.*"`, иначе используется
базовый каталог 8.3.27. Это не заявляет поддержку всех будущих версий платформы.
Для повторного извлечения `Inspect.java` сообщает changeable/derived/cardinality;
`tools/platform-catalog/editing_schema.py MODEL VALUES OUTPUT` создаёт
детерминированные TSV в выбранном каталоге playground. Специализированные XML
writers адаптируются и проверяются отдельно в `schema.rs` и `types.rs`.

Смена типа или его qualifiers отклоняется, если существующее значение
заполнения либо форма выбора перестанут соответствовать типу. Возвращается
`property_dependency` с `details.property:{namespace,name}` и
`details.reason:"incompatible_type"`. Сначала нужно явно очистить/исправить
зависимое поле. Preview и apply применяют одно правило; автоматического сброса
значений нет.

## Запись и конфликты

Адрес поля: expanded XML name + номер одноимённого ребёнка на каждом уровне.
Mapping проверяется заново в свежем исходнике. Поддерживается только однозначный
скалярный текст; комментарий, разбивающий текст на несколько частей, не имеет
однозначного места изменения. Полный XML не сериализуется. Сохраняются BOM,
CRLF/LF, атрибуты, префиксы, комментарии и все байты вне рассчитанных замен.
No-op не пишет файл и не меняет generation. Смена типа может удалить старую и
добавить новую группу qualifiers; их порядок соответствует Designer XML.

Кандидат повторно разбирается, идентичности объектов сверяются с исходными.
Правила поддержки проверяются на уровне изменяемого объекта, включая mixed XML:
запрещённый соседний объект не редактируется. Symlink-компоненты, неподдержанные
пути, readonly-файл и конфликт SHA-256 отклоняются. Во временный sibling-файл
пишется готовый результат, сохраняются permissions, выполняется sync, затем
повторно проверяются исходные байты/путь/permissions и вызывается `fs::rename`.
Нет delete-then-rename или full-serialize fallback. Очищается только свой temp.

На Linux проверена запись и сохранность байтов; нативная проверка Windows/macOS
ещё не выполнена. `fs::rename` зависит от ОС/файловой системы и возвращает ошибку,
если replacement невозможен. Проверка перед rename не является OS compare-and-swap:
остаётся короткое окно гонки с независимым внешним писателем. Нет гарантии
сохранности после потери питания (каталог отдельно не fsync-ится), сохранения
ACL/xattrs или распределённой транзакции. Эти ограничения не следует скрывать
за словом «атомарно».

История хранит прямые и обратные замены с SHA-256, поэтому undo восстанавливает
даже исходное написание entities. Изменение любого байта файла другим редактором
останавливает replay. Лимиты: 100 шагов/8 MiB на объект, 256 объектов/32 MiB на
session; старые записи вытесняются. Новый backend-процесс начинает пустую историю.

## Проверки

Регрессии покрывают четыре типа проектов, inline-реквизит, preview/no-op,
точный diff и undo, неизвестные/защищённые поля, enum/type validation, stale
snapshot, права и ошибочный путь. Нативный VSCodium 1.109.5 проверяет реальные DOM
события замочка, Enter, Esc, Ctrl+Z/Ctrl+Shift+Z и сохранение черновика при конфликте.
На изолированной копии в playground платформа **8.3.27.2325** через `eska build`
приняла шесть замен типа: string, dateTime, boolean, ValueStorage, UUID,
CatalogRef. Корень реальной бухгалтерии прочитан через CLI без изменения базы.
Для ссылок проверены замена существующей роли, назначение и замена общей формы,
очистка одиночной ссылки: все четыре XML приняты платформой 8.3.27.2325.
Установка и очистка обеих числовых границ также проверены загрузкой платформой.
Это проверка выбранных примеров; domain checks редактора не заменяют полную
проверку конфигурации платформой или выполнение её BSL.

Для значений заполнения платформа 8.3.27.2325 приняла шесть примитивных значений
и четыре ссылочных (пустые ссылки, перечисление, предопределённый элемент).

## Предварительный просмотр переименования

`eska metadata rename-preview rename.json` читает отдельный запрос:

```json
{"schemaVersion":1,"objectId":"catalog:Товары","newName":"Номенклатура"}
```

Ответ содержит `applyAvailable:false` и `plan`: исходный/новый ID, UUID, имена,
SHA-256 снимка источников, `files` с заменами и сомнительными вхождениями,
`moves` для descriptor/payload и `issues`. Координаты замен — UTF-8 байты
исходного файла; `before`/`after` содержат исходный и предлагаемый XML-текст.
Снимок учитывает содержимое всех исходных файлов и состав каталогов, включая
добавленные файлы и бинарные payload. Git internals, `.eska` и каталог
результатов сборки исключены; вывод сборки внутри дерева метаданных не скрывается.
Пути относительны source проекта.
Команда не пишет исходники, не создаёт disk cache и не меняет историю отмены.

Подтверждённые XML-ссылки определяются по namespace, типу значения и проверенной
схеме свойства; имена generated types берутся из `InternalInfo` объекта.
Обычный текст и все текущие BSL-вхождения попадают в `uncertain` без замены.
Бинарный модуль/форма отмечается `opaque_code_or_form`; недоступная поддержка
и запрет записи видны в `issues`. XML вне ограничений текущего parser отмечен
`xml_unavailable`, текст больше 64 MiB — `text_too_large`; эти файлы пока
учитываются в снимке без анализа ссылок. Коллизии имён и физических путей проверяются
без учёта регистра. Symlink и неизвестная физическая запись прерывают просмотр.
Правила идентификатора основаны на проверенном EDT `NameValidator`: до 80
UTF-16 единиц, буква/подчёркивание в начале, далее буквы/десятичные цифры/подчёркивание.

Запись переименования, семантическая обработка BSL/запросов, структурная история
и подключение поля «Имя» к этому плану пока не реализованы. Предопределённые
элементы и заимствованные объекты расширения пока отклоняются. Этот preview
служит проверке следующего этапа; он не заявляет полноту обновления ссылок.
