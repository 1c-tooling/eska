# Анализ запросов: предложение для мейнтейнера bsl-analyzer

Черновик для согласования от 2026-10-26. Сопровождает
[T115–T119](roadmap/21-query-analysis.md) и
[компактный конструктор](roadmap/24-compact-query-constructor.md).
Предложение не отправлено мейнтейнеру; способы интеграции и имена новых методов
не утверждены. Здесь перечислены желаемые контракты, а не доступное сейчас API.

## Проверенная исходная точка

Последний опубликованный релиз при проверке —
[v0.4.0](https://github.com/itrous/bsl-analyzer/releases/tag/v0.4.0).
Дополнительно прочитан актуальный upstream commit
`423df75597d54e2f1cbc6dad226e66ec374ee813`. Проверка статическая:
воспроизведение ошибок и приёмка сервера входят в задачи реализации.

| Типы выражений и результатов | Scope разрешает поля/цепочки; `query_to_projection` переносит `field.ty` в результат | Публичное структурированное представление вместо разбора hover/строк типов |

## Предлагаемые изменения

### A1 / T115 — Типы значений характеристик и составных полей

Отдельно представить ссылку на ПВХ и набор типов его значения. Раскрывать
CharacteristicTypes/определяемые типы с доступным контекстом базы и расширений.
Сохранить примитивные типы, квалификаторы строки/числа/даты, ссылочные варианты
и неопределённость. Значение записи ИБ и неизвестного параметра не угадываются.

Для составного поля объединять допустимые типы с происхождением: какие варианты
содержат реквизит, где его нет, откуда пришёл каждый тип. Дерево не выбирает
произвольную первую ссылку. Ограничения глубины и циклы имеют явную причину.
Семантика NULL, отсутствующего реквизита и ошибки уточняется по платформе.

Приёмка: минимальные owned fixtures для `ОбъектСсылка` регистра
`dzp_ИдентификаторыВнешнихСистем`, обычной ссылки на тот же ПВХ, составных
реквизитов с одинаковыми именами и разными типами, нескольких звеньев ссылки,
расширений, отсутствующего описания и циклов. Тип проходит до результата запроса
и существующих проекций BSL, без регрессии текущей навигации.

### A2 / T116 — Публичная семантическая модель

Экспортировать результат существующего parser/HIR/resolver через один
read-only контракт. Предпочтительно согласовать расширение действующего LSP;
выбор LSP или другого уже поддержанного транспорта остаётся за мейнтейнером.
Имена методов ниже не задаются. Rust-ядро в ESKA не встраивается.

Вход: текст/открытый документ с версией, контекст приложения и metadata revision,
точка пакета/область, необязательная позиция или диапазон выражения.
Ответ: версия схемы, точная ревизия документа/контекста, области и родители,
источники/псевдонимы, поля, выражения, колонки результата и их типы/происхождение.
Идентификаторы должны быть стабильны в пределах снимка; HIR ID не считаются
долговременной публичной identity. Результат принадлежит конкретному запросу.

Для дерева нужны порционное получение полей и ленивое раскрытие ссылки,
признаки наличия потомков, варианты составного типа, доступные определения.
Для редактора — диапазоны, тип выражения, агрегатность в текущей области,
ожидаемый тип там, где он доказуем. Происхождение вычисления может содержать
несколько исходных полей; отсутствие происхождения должно быть явным.

Поддержать JOIN/NULL, ВЫБОР, ЕСТЬNULL, ВЫРАЗИТЬ, виртуальные таблицы,
вложенные запросы, UNION/UNION ALL, создание и удаление временных таблиц.
Неподдержанный синтаксис возвращает частичный результат с границами покрытия.
Неизвестный тип не подменяется строкой или успешно проверенным полем.

### A3 / T117 — Контекст отдельного запроса и выражения

Согласовать отдельный SDBL-документ с привязкой к существующему workspace.
Для запроса из XML не создавать фиктивный BSL-модуль с вымышленным контекстом.
Для BSL сохранять полезный контекст владельца и уже работающую проекцию;
для XML явно отсутствуют факты о BSL-вызовах установки параметров.

Привязка к приложению должна однозначно выбирать набор базы/расширений.
Текущий `root_id` MCP query — утверждение о зарегистрированном корне, а не
фильтр resolver; этого недостаточно как доказательства изоляции двух приложений.
Нужен согласованный способ передачи/выбора контекста и его ревизии.

Повторно использовать общие diagnostics, completion, hover, definition и
semantic tokens; добавить недостающие SDBL signature help и каталог функций
с аргументами/описанием на основе имеющихся источников анализатора.
Отдельный фрагмент анализировать в полном запросе с его scope, а не как
самостоятельный SELECT. Временный ввод не меняет исходный файл.

Вход и ответ связываются с версией документа. Согласовать единицы координат
и position encoding, диапазоны исправлений и additional edits. ESKA отображает
координаты выражения/запроса/BSL или XML-владельца и проверяет допустимость правки.
Нельзя применять исправление, если оно выходит за разрешённый контекст.

Полнота включает как минимум отсутствие metadata, индексацию, частичный
контекст и успешную проверку доступной семантики; пустой список диагностик
не скрывает недоступную проверку. Не задавать второй противоречащий enum рядом
с существующим контрактом полноты: согласовать расширение текущей модели.
Нужны отмена, ограничение размера/глубины, подавление устаревших ответов и
переиспользование текущего процесса/индекса без запуска анализатора на каждый ввод.

### A4 / T119 — Ожидаемые типы параметров

Выдать имена и все использования параметров, ограничения типов от выражений,
несовместимые требования и причины неизвестности. Для `ИД В (&МассивИД)`
различать коллекцию и тип её элементов; ограничение не доказывает фактический
тип переданного значения. Для BSL сопоставить доказуемые вызовы установки
параметров, сохранив неопределённость условного и динамического кода.

Приёмка: повторные параметры, противоречивые ограничения, виртуальные таблицы,
пакет/вложенные области, условная установка, вычисляемое имя и отсутствие BSL
контекста. Отбор по неизвестному параметру не выбирает один вариант типа ПВХ.

## Что остаётся в ESKA и Explorer

Компоновка, таблицы, drag-and-drop, выбор, панели и диалоги — Explorer.
Создание источников/связей, псевдонимы, групповые операции, модификаторы SELECT,
перестановка пакета, точечные правки, diff, поддержка, recovery и Undo-планы — ESKA.
Анализатору не передаются обязанности хранения сессии конструктора или доступа
на запись к владельцу. Форматтер согласуется отдельно по T120–T123; он не нужен
для внедрения компактной оболочки. Выполнение запроса в ИБ в этот план не входит.

## Решения для согласования и порядок поставки

1. Подтвердить A1 как исправление модели и согласовать семантику составных полей.
2. Выбрать транспорт A2/A3, схему capability negotiation, контекст приложения,
   единицы координат, полноту, лимиты и cancellation; зафиксировать примеры JSON.
3. Согласовать минимальную поставку: A1, модель источников/результата, отдельный
   запрос и имеющиеся языковые сервисы. Следующей частью — ожидаемые типы
   параметров и недостающие сервисы выражений; явно объявлять неполное покрытие.
4. Принять контрактные тесты на RU/EN SDBL, Unicode/CRLF, два приложения,
   изменения расширений, незавершённый ввод и смену ревизии во время запроса.
5. Выпустить совместимую версию с объявленными возможностями; ESKA проверяет
   установленный бинарник и контракт. Принятый PR или локальная сборка сами
   по себе не закрывают интеграционные задачи.

До согласования UI-задачи используют действующий API ESKA. Отсутствие нового
сервиса отключает только зависимые подсказки; существующие операции конструктора
и текст пользователя сохраняются. Это граница возможностей, а не сообщение
об отсутствии ошибок в запросе.
