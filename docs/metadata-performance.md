# T68: производительность metadata workspace

## Пакетное удаление из поискового индекса: ревью 2026-09-24

Удаление нескольких ссылок из корневого XML раньше обходило весь индекс отдельно
для каждой удалённой ветви. Теперь один проход сверяет типизированные ancestry
с множеством удалённых владельцев. Дополнительный постоянный индекс не нужен.

На той же синтетике из 42 001 записи удаление 1 000 справочников с 20 реквизитами
заняло **480,6 мс вместо 7 112,5 мс** по медиане трёх запусков (в 14,8 раза быстрее).
Это Linux, Rust 1.98.1, debug/test profile; время только `index_search_step(1)`
после `changed_paths`. Создание fixture, начальная индексация и само уведомление
в интервал не входят. Это отдельное измерение, не пересчёт release-бюджетов T68.
[Все исходные значения и команда повтора](measurements/review-search-removal.json).
Обычный regression test проверяет пакетное удаление, очистку ошибок отсутствующих
descriptors и сохранение ветви с похожим именем; временных порогов в CI нет.

## Исходные замеры T68

Замеры от 2026-09-18. Rust 1.98.1, release (`opt-level=3`, thin LTO),
Linux 7.2.5, Intel Core i5-13420H (12 логических CPU), 15,3 GiB RAM, btrfs. Замеры backend,
без платформы 1С, сборки конфигурации и VS Code. Исходники стендов не менялись.

## Протокол и бюджеты

Пять свежих сессий без дискового кеша, затем первое заполнение и пять открытий
с кешем. Файловый кеш ОС не очищался: cold означает отсутствие сессии/разобранных
данных, а не холодный накопитель после перезагрузки. Серии запускались
последовательно одним release test binary. Во время финальной серии Cargo
и другие нагрузочные проверки не запускались.

Сохранены исходные бюджеты T63: root p95 ≤ 200 мс; первое раскрытие descriptor
до ~1 MiB ≤ 50 мс; повторный выбор/properties ≤ 20 мс; поиск ≤ 50 мс;
peak RSS ≤ 256 MiB. После первичного baseline добавлены локальные бюджеты:
индексация большого стенда без кеша и с прогретым кешем ≤ 15 с, первое
заполнение кеша ≤ 30 с, обновление одного объекта ≤ 50 мс, шаг индексации
из восьми descriptors ≤ 200 мс. Это ориентиры данного стенда/оборудования,
не SLA произвольной конфигурации. Отдельный XML нельзя отменить посередине
разбора; интерфейс должен выполнять индексирование вне UI-потока.

Поиск: четыре запроса (`Контрагент`, `код`, `а`, отсутствующее имя), по десять
повторов, лимит 50. p95 по 40 значениям; root/index p95 по пяти открытиям —
максимум этой небольшой выборки. RSS — high-water mark всего test process
через `/usr/bin/time -v`, включая подготовку синтетики и все повторы.
Цифры времени не проверяются нестабильными assert в CI.

## Причины изменений

Первый пробный запуск выявил полный `records.retain` при каждом впервые
прочитанном descriptor. Он обходил весь накопленный индекс; начальную серию
остановили, не выдавая её за завершённый benchmark. Теперь полный проход
нужен только при замене уже индексированного descriptor. Счётчик готовых
записей без инвалидированных ветвей также не перебирает весь индекс.

После этого первый одиночный замер большого стенда показал около 65 мс
для частого поискового запроса и 328 MiB RSS. Идентификаторы переведены на
общие `Arc<str>` без изменения строкового представления, сравнения и порядка.
Поиск сначала выбирает лучшие N совпадений, затем сортирует только выдачу.
Порядок ранжирования и признак усечения сохранены.

Кеш хранит JSON payload без дополнительного экранированного String-слоя
(`serde_json/raw_value`), проверяет хеш исходника и контрольную сумму payload.
Каждая запись публикуется переименованием; отдельный fsync для disposable
кеша не выполняется. При потере записи после сбоя она восстанавливается.

## Воспроизведение

```sh
cargo test --release --test integration --no-run
ESKA_TEST_ROOT="$(realpath ../eska-playground)" \
ESKA_METADATA_BENCH=big ESKA_METADATA_RUNS=5 \
/usr/bin/time -v target/release/deps/integration-<hash> \
  project::metadata_workspace::benchmarks::measures_metadata_workspace \
  --ignored --nocapture
```

Вместо `big` доступны `small` и `synthetic`; `ESKA_METADATA_CACHE=1` включает
дисковый кеш. Для холодного заполнения нужен пустой каталог кеша выбранного
стенда; повторные вызовы используют накопленный кеш. Удаление кеша не является
частью benchmark. `small`/`synthetic` автоматически удаляют собственный проект.
`big` сохраняет только производный кеш; XML/BSL остаются без изменений.

Raw результаты и счётчики — [t68-metadata.json](measurements/t68-metadata.json).

## Счётчики и границы измерений

Каждая серия большого стенда: 137 134 открытия XML, 708 234 154 прочитанных
байта, 228 599 проверок путей, 228 583 обращения к metadata файлов, **ноль
read_dir**. Сюда входят root, свойства, полная индексация и refresh; XML читается
повторно для проверки гонок записи T67. 4,9 GB всех XML проекта не обходятся:
payload форм/макетов и BSL для поиска не читаются. Число чтений не зависит от
добавления постороннего XML или объёма BSL — это проверяет обычный тест.

При повторном открытии с диском: **0 XML parse** (включая discovery корня),
45 712 попаданий в кеш, 0 записей; без диска — 45 710 descriptor parse к концу
индексации и два разбора корня с учётом discovery. Refresh неизменённого
справочника даёт один parse без диска и ноль при валидном дисковом кеше.
Изменённый XML требует разбора; это отдельно проверено тестом с сохранёнными
mtime и размером. Сам поиск/выбор по готовым данным не читает XML.

В последнем тёплом запуске чтения исходников заняли 544 мс, их хеширование —
221 мс; это части проверки свежести, без времени проверок путей и декодирования
кеша. Тёплый запуск прочитал ещё 116 254 875 байт кеша. Счётчики операций
resolver/metadata не равны всем внутренним системным вызовам canonicalize.

Итоговый кеш большого стенда: 45 710 записей, 116 117 455 байт полезных файлов
(~110,7 MiB), занято на btrfs ~244,3 MiB. Удержанный LRU в конце серии весит
238 862 байта исходных XML; это вес по политике cache, не объём Rust allocations.
RSS в таблице включает весь индекс, дерево, буферы и allocator.

Проверки `fmt`, `check`, строгий Clippy и полный набор: 160 unit + 322 integration
прошли, 4 ignored. Новый ignored benchmark отдельно прошёл 33 измерения.

## Повторное полное обновление

Полный refresh корня и пакет с неизвестным путём собирают затронутые дескрипторы
один раз. Очистка таблицы путей выполняется после всей группы изменений.
Уже запущенный поисковый индекс при полном refresh перестраивается с корня;
устаревшие записи освобождаются сразу. Приостановленный индекс остаётся
приостановленным, а незапущенный не запускается. Точечные изменения сохраняют
незатронутые записи и ветви.
