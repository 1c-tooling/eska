# Выпуск ESKA

Версия Rust и компоненты Clippy/rustfmt закреплены в `rust-toolchain.toml`.
Локальная разработка, CI и все задания выпуска используют этот файл через
rustup. При обновлении версии нужно повторить полный набор проверок CI.

Версии всех Cargo packages наследуются из `workspace.package.version`.
Release-plz обновляет их вместе с точными версиями внутренних зависимостей;
номер вручную не повышается. В crates.io публикуются инструменты и библиотеки,
необходимые для сборки этих инструментов. Общие тег `v<version>` и CHANGELOG
принадлежат `eska`; изменения остальных packages включаются в этот CHANGELOG.

После слияния release PR в `main` Release-plz публикует crates и создаёт тег.
Выпуск бинарников запускается через `workflow_dispatch` на этом теге. Перед
публикацией Cargo обязательны fmt, check, strict clippy, тесты workspace,
Python-тесты компонентов и сборка распакованных `.crate` через `cargo package`.
Дополнительно `tools/release_bundle.py verify-crates` проверяет манифесты внутри
архивов: внутренние тестовые зависимости не должны попадать в crates.io.
Для них используется только `path`, без `version` и наследования workspace.
Обычные зависимости сохраняют точную версию из workspace. Одна проверка
`cargo package --workspace` недостаточна: она подставляет ещё не опубликованные
packages из временного локального registry и скрывает ошибки порядка публикации.
Для релизного PR бот явно запускает CI через `workflow_dispatch`: события PR,
созданные `GITHUB_TOKEN`, не запускают другой workflow автоматически.

Если `Publish crate` остановился после публикации части packages, сначала
исправьте причину и слейте исправление в `main`. Затем запустите `Release-plz`
вручную на `main`, указав текущую `workspace.package.version` в поле `version`:

```sh
gh workflow run release-plz.yml --ref main -f version=0.15.0
```

Ручной запуск повторяет CI, проверяет совпадение версии и разрешает выпуск
без нового release PR только для этого запуска. Уже опубликованные версии
пропускаются; после успеха запускается сборка бинарников по общему тегу,
даже если `eska` был опубликован до сбоя. Версию вручную менять не нужно.
Повтор старого задания не подхватывает исправления из нового коммита.

После сбоя публикации **бинарных файлов** повторите упавшее задание: оно использует
уже собранный `release-assets`. Полный повтор сборки допускается только при совпадении байтов
с файлами, которые уже загружены в GitHub.

## Файлы поставки

Матрица содержит Linux GNU/musl и macOS на x86-64/ARM64, Windows x86-64.
Каждый runner исполняет собственные бинарники: проверяет контракты, устанавливает
и повторно устанавливает все пять компонентных ZIP в пустой каталог, проверяет
help на двух языках и initialize/shutdown Metadata API. Это проверка поставки,
не запуск платформы 1С или полной конфигурации `buhmfo`.

`tools/release_bundle.py prepare` создаёт игнорируемый
`target/release-bundle/dist.toml` из текущей версии Cargo. Cargo-dist 0.32.0
собирает полный архив с пятью исполняемыми файлами и лицензиями из тех же
бинарников, что вошли в выборочные ZIP. Прежние имена установщиков и receipt
cargo-dist сохраняются. Отдельные архивы имеют имя
`<tool>-<version>-<target>.zip`, индексы — `release-<target>.json`.
Общий `SHA256SUMS` вычисляется после сборки всех установщиков.
Манифесты всех runner объединяются до генерации установщиков, чтобы в них вошли
контрольные суммы полных архивов. После сборки выполняются отдельные задания
Linux, Windows и macOS (x86-64/ARM64): чистая и повторная установка пяти команд
через shell/PowerShell, отдельная квитанция, запуск Metadata API и отказ
перезаписывать компоненты Explorer. Каталоги установки и XDG-конфигурации изолированы.

Сборка общего выпуска отклоняет неполную матрицу, несовпадающие версии, SHA-256
или одинаковые имена bootstrap-файлов с разным содержимым. Релиз сначала
создаётся как draft; публичным он становится после загрузки и проверки всех
assets. Повторный запуск сохраняет совпадающие assets, а конфликтующие байты
или неполный уже опубликованный релиз приводят к ошибке без перезаписи.

Полная и выборочная установка остаются разными способами владения файлами.
Установщик компонента не заменяет стороннюю или изменённую установку молча.
Полный shell/PowerShell установщик также отказывается заменять команды,
для которых есть квитанции `components/*.json` от Explorer или `components.py`.
Обновляйте такую установку прежним способом либо задайте полный путь к другому
каталогу исполняемых файлов через `ESKA_INSTALL_DIR`. Шаблоны cargo-dist закреплены
версией; изменение места вставки этой проверки останавливает сборку выпуска.
Для перехода с монолитной установки через Cargo один раз выполните команду
установки пяти packages из README. Старый Cargo-updater обновлял только `eska`;
новый обновляет все пять инструментов с сохранением root/target/profile.

## Русские описания

`release-plz.toml` задаёт русские заголовки и вводный текст CHANGELOG.
Scope и текст коммита сохраняются: например,
`*(ide)* Добавлено читаемое представление ссылок и типов свойств`.
Описание GitHub Release берёт записи конкретной версии из CHANGELOG и добавляет
русские инструкции установки. Английское автоматически созданное cargo-dist
описание не используется для GitHub Release.

## Проверка перед публикацией

Ручной `Release` с `tag=dry-run` выполняет всю матрицу и оставляет артефакт
`release-assets`, не создавая тег, release или публикацию в crates.io.
В GitHub его можно запустить после push выбранной ветки. Затем следует проверить
файлы, подготовить release PR и слить его. Push и публикация требуют отдельного
действия владельца проекта.

Explorer выпускается после ESKA. Его CI скачивает именно опубликованный
`eska-project` и поддерживаемый upstream bsl-analyzer, проверяет установку
через собственный установщик Explorer и установленный VSIX с настоящим LSP.
Отсутствие совместимого архива ESKA останавливает выпуск расширения.

Локальные проверки используют соседний `eska-playground`; успешная Linux-проверка
не подтверждает Windows/macOS или фактическую публикацию GitHub/Open VSX.
