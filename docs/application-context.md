# Контекст приложения Designer XML

`eska.toml` определяет состав приложения через имена проверенных workspace
members. Каталоги и `source` берутся из их манифестов; добавлять `/src` или
угадывать зависимости по соседству каталогов не требуется.

Схема T83 и read-only resolver находятся в `eska-project-core::application`;
существующий `eska` без подкоманды проверяет новые объявления вместе с
манифестами. Генерация `bsl-analyzer.toml`, самостоятельный project CLI,
пакетный анализ и LSP подключаются следующими этапами. Эти команды пока
не являются частью доступного CLI.

## Явное приложение

Добавления в корневой workspace `eska.toml`:

```toml
[analysis]
default_application = "accounting"

[applications.accounting]
configuration = "main"
extensions = ["integration", "reports"]
external_objects = ["data-import", "external-report"]
extension_dependencies = { reports = ["integration"] }
# Необязательно: намеренно другая платформа анализа.
# target_platform_version = "8.5.1"
```

Все значения `configuration`, `extensions`, `external_objects` и обе стороны
`extension_dependencies` ссылаются на `project.name`, а не на XML-имя или путь.
Имена приложений и members имеют формат `[a-z0-9][a-z0-9_-]*`.

| Поле приложения | Проверка |
|---|---|
| `configuration` | Обязательный member с `project.type = "configuration"` |
| `extensions` | Только members типа `extension`; список может быть пустым |
| `external_objects` | Только members типа `processing` или `report`; список может быть пустым |
| `extension_dependencies` | Ключ и каждое значение входят в `extensions` этого приложения |
| `target_platform_version` | Необязательная версия из трёх или четырёх числовых компонентов |

Повторения members в одном приложении, повторные рёбра, зависимости за его
пределами и циклы отклоняются. Проверяются все объявления, включая невыбранные.
Разные приложения могут использовать общие members; resolver возвращает
только состав выбранного приложения и не объединяет независимые конфигурации.

Порядок источников: основная конфигурация, расширения после их зависимостей,
внешние объекты. Среди готовых к добавлению расширений приоритет имеет
раньше объявленное в `extensions`; порядок внешних объектов сохраняется.

## Выбор контекста

Явно запрошенное имя имеет приоритет над `analysis.default_application`.
Если default не задан, единственное объявление выбирается автоматически.
При нескольких объявлениях требуется явный выбор или корректный default.
Отсутствующее default-приложение — ошибка манифеста, без fallback.
Текущий каталог member не выбирает приложение автоматически.

Workspace без `applications` остаётся допустимым для прежних операций.
Для анализа единственный member образует собственный контекст; несколько
members требуют явного объявления приложения. Пустой workspace не даёт
успешный результат анализа с пустым составом.

Standalone-конфигурация, расширение, EPF и ERF работают без `applications`.
Расширение или внешний объект без основной конфигурации имеют признак
`limited_context`; это допустимый контекст, а не запрет редактирования.
Имена внешних XML-файлов определяются по реальным дескрипторам. Файл
`Обработка.ДругоеИмя.xml` не переименовывается под имя каталога или member.

## Платформа и совместимость

Для приложения target по умолчанию равен эффективному
`build.platform_version` основной конфигурации, включая её override корневой
версии workspace. Build-настройки расширений target не меняют.
Явный `applications.<имя>.target_platform_version` заменяет только target
анализа. Версия сборки остаётся прежней.

Для standalone или единственного member workspace без `applications` override
задаётся в корневом манифесте:

```toml
[analysis]
target_platform_version = "8.3.27"
```

При объявленных приложениях этот общий override отклоняется: значение должно
находиться в конкретном `applications.<имя>`. Настройки `analysis` в member
workspace отклоняются; они принадлежат корню. Отсутствующая версия остаётся
неизвестной, без выбора установленной платформы или скрытого default.

Режим совместимости берётся из `CompatibilityMode` основной конфигурации
и `ConfigurationExtensionCompatibilityMode` расширения в namespace
`http://v8.1c.ru/8.3/MDClasses`. Он не вычисляется из target/build-версии.
Отсутствующий режим остаётся неизвестным; чужой namespace его не подменяет,
повторённое или структурное значение отклоняется.

Политика анализатора задаётся в корневом `tools.bsl-analyzer`;
[генерация, владение и миграция](analyzer-configuration.md) используют этот же resolver.

## Проверки и границы

Resolver использует общие discovery, canonical paths и Designer root reader.
Он проверяет declared type по фактическому XML и возвращает имя/UUID из XML.
Отдельного индекса BSL, вызова Git, runner, анализатора или записи кешей нет.
Читаются только выбранные корневые дескрипторы, с существующими ограничениями
размера/разбора; дочерние XML и BSL не обходятся.

Тесты покрывают BOM/CRLF и opaque bytes без изменений, нестандартные source,
кириллицу/пробелы, standalone и workspace, наследование/override платформы,
выбор и неоднозначность, типы/ссылки/граф, повреждённый TOML/XML и symlink escape.
CLI-ошибки проверяются на обоих языках с пустым PATH.
Это структурная проверка и подготовка контекста, не подтверждение успешного
статического анализа или выполнения на платформе 1С.

T83: fmt, workspace check, строгий workspace Clippy, 762 Rust-теста
(6 ignored), Rustdoc и 138 Node-тестов с настоящим backend прошли.
Ручные CLI-прогоны на двух языках проверили exit 0/1 и одинаковый JSON
metadata. На отдельной копии `buhmfo` resolver вернул одну конфигурацию и
пять расширений, target `8.3.27.2325` и разные XML-режимы совместимости;
платформа и анализатор не запускались. [Фактический результат](measurements/t83-context.json).
