## Исправления

- Python-установщик всегда пишет machine-readable JSON в UTF-8, включая пути
  с кириллицей и supplementary Unicode при системной кодировке cp1251.
- Нативные Git-пути преобразуются из `\\?\`/UNC в форму, понятную gix и Git,
  с сохранением `OsString`. Исправлены локальное клонирование и полки Windows.
- Относительные пути manifest запрещают корневые и drive-relative Windows-пути;
  TOML сериализует разделители `/`. CLI JSON продолжает выдавать нативные пути.
- Recovery store корректно обрабатывает Windows prefix/root components, поэтому
  Metadata API может инициализировать и восстанавливать черновики запросов.
- Windows HTTPS использует curl/Schannel и системное хранилище сертификатов.
  Прежняя комбинация curl/rustls завершала реальный clone ошибкой настройки
  verifier. Проверка сертификата не отключается; system Git fallback не добавлен.
- Платформенные ветви и тестовые fixtures приведены к строгому Windows Clippy;
  файловые проверки учитывают mandatory locking и `.exe`.
- На границе запуска `ibcmd`/Designer Win32 verbatim paths преобразуются
  в обычные drive/UNC paths без потери `OsString`. Иначе настоящая 1С отвергала
  `--data` при создании базы. Диагностика понимает оба представления пути.
- На Windows генератор analyzer config выбирает встроенную справку API, если
  проект не задал собственную политику. Автозагрузка установленных HBK в upstream
  0.4.1 зависала при `check-config`; явные `auto`/`installed`/`external` сохраняются.
- Абсолютные пути reference configuration передаются upstream как обычные
  drive/UNC paths. Win32 verbatim prefix больше не превращается в `//?/…`,
  который ломал LSP-переходы во внешнюю БСП. Проверены генератор и настоящий LSP.
- В Explorer исправлено сохранение выбора при скрытии пустой выбранной группы;
  обновлены Windows native runner, порядок освобождения backend и NTFS junction
  fixtures. Подробности интерфейсной проверки — в отчёте второго репозитория.

Экспериментальный Rust API изменён: `ContextDiscoveryError::Manifest.source`
теперь `Box<ManifestConfigError>`, что уменьшает размер распространяемой ошибки.
Публичные CLI JSON/schema и номера контрактов сохранены.

## Воспроизведение

Из корня checkout, PowerShell:

```powershell
$env:ESKA_TEST_ROOT = (Resolve-Path ../eska-playground).Path
$env:CARGO_BUILD_JOBS = '1'
$env:CARGO_PROFILE_DEV_DEBUG = '0'
$env:CARGO_PROFILE_TEST_DEBUG = '0'
$env:RUST_TEST_THREADS = '2'
cargo fmt --check
cargo check --offline --locked --workspace
cargo clippy --offline --locked --workspace --all-targets --all-features -- -D warnings
cargo test --offline --locked --workspace --no-fail-fast
$env:ESKA_TEST_HTTPS_REPOSITORY = 'https://github.com/odineska/eska.git'
cargo test --offline --locked --workspace --test integration public_https_clone_uses_the_native_transport -- --ignored --nocapture
```

`--offline` относится к разрешению Cargo dependencies. Последний тест реально
обращается к HTTPS Git и выделен в opt-in, чтобы обычный прогон не требовал сети.
Для первого получения dependencies нужен `cargo fetch --locked` с доступом к сети.

## Установка на проверяемой машине

Из окончательных локальных ZIP установлены все шесть компонентов в
`%USERPROFILE%/.eska/bin`. Проверены SHA-256, tool contracts, receipts и
справка ru/en. Анализатор установлен штатным Node installer Explorer в
`%USERPROFILE%/.eska/analyzer`, включая пять license/notice-файлов и receipt.

Переносимый VS Code находится в `%USERPROFILE%/Tools/eska-windows/VSCode`,
Node/Bun — в соседних каталогах. Пользовательский PATH дополнен без удаления
прежних записей. Профиль VS Code явно указывает project, formatter и analyzer;
языковые функции включены. Ярлык `ESKA VS Code` на рабочем столе открывает
собственный `../eska-playground/windows-ready-demo-zv78mna1/Windows-Демонстрация`.

Установленный комплект отдельно прошёл validate/context, делегирование
`eska fmt`, analyzer-config prepare, fmt apply/check, Git status с trunk workflow
и реальный `eska-check` (`status: passed`, exit 0). После установки платформы
автоматическое обнаружение нашло **8.3.27.2342**; сборка прошла без `--ibcmd`.
Окончательный demo импортирован из настоящего EPF, собран повторно, имеет чистый
Git status; `windows-ready-demo.json` фиксирует все этапы установленного комплекта.
