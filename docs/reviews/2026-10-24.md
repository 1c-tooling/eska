# Ревью архитектуры и производительности — 2026-10-24

Проверены текущий Rust workspace ESKA и соседний `eska-vscode-explorer` в ветках
`codex/design-xml-analyzer`. Обе рабочие копии перед началом были чистыми.
Исходные revisions: ESKA `bea77472fb73e007d171c814fb3d60038bee7436`,
Explorer `29dd397574fa23457b6a68ff5571a7fd58a72789`.

Основная доменная логика уже находилась в ESKA. Найдено и устранено дублирование
правил обратной навигации в расширении: теперь владелец исходника и путь дерева
разрешаются общим Rust-ядром. Подтверждённое ускорение касается этого пути,
включая определение BSL-владельца для редактора запросов.

операциям и тестам. Это проверка архитектурных границ всех компонентов,
а не заявление о построчной проверке каждой ветви программы.

## Найденные проблемы и изменения

**Поиск владельца в Explorer обходил дерево.** `revealFile` выделял имена из пути,
запрашивал группы и соседние узлы, затем сверял `metadata/source`. Объём передачи
и удерживаемого дерева зависел от числа соседей; другой адаптер должен был бы
повторить этот алгоритм.

Добавлен [общий resolver](../../crates/eska-project-core/src/project/metadata_workspace/source_navigation.rs)
и `metadata/revealSource` в [API 1.24](../ide-protocol.md#api-124-обратная-навигация-по-исходнику).
Resolver использует существующий словарь владельцев совместно с support,
проверяет объявления и точное соответствие forward mapping. Ответ содержит
только исходник и цепочку предков. Поисковый индекс не запускается, соседние
XML не читаются. Неизвестные, удалённые и необъявленные файлы не получают
фиктивного владельца; выход за source и внешние symlink targets отклоняются.

Explorer больше не выводит владельца из имён каталогов. Частичные цепочки
подключаются к обычному удалению устаревших узлов, поэтому исчезнувший объект
не остаётся в кеше адаптера. Регрессионный тест проверяет этот случай.

**Стенд stdio запускал только legacy CLI.** `tools/ide-protocol-bench.py` теперь
по умолчанию вызывает `eska-project serve --stdio`, поддерживает явный legacy
и `--root` для чтения существующего большого проекта. `--root` нельзя сочетать
с записью кеша. Проверены оба варианта запуска.

**Документация разработки Explorer отставала от кода.** Исправлены версия
handshake, статус BSL Apply и описание уже перенесённых сессий. Старые прототипы
session-readonly отделены от действующей модальной приёмки.

Новый адаптер требует API 1.24 для обратной навигации и открытия BSL-запроса.
С более ранним backend остальные согласованные возможности сохраняются;
прежний обход дерева не оставлен вторым источником правил. Новый backend
продолжает обслуживать прежние версии API, метод 1.24 для них не объявляется.

### Обратная навигация

Пять свежих подключений на размер, по 31 переходу: первый с пустым деревом
адаптера, следующие 30 — повторные. Запуск backend и `workspace/open` завершены
до измерения. Синтетический root содержит указанное число объявлений Catalog;
XML и модули созданы только для объектов fixture. Это измеряет поиск владельца
через реальные pipes, а не полный XML parse всех объектов или отрисовку IDE.

| Объявлений Catalog | Первый переход до / после, медиана, мс | RPC до / после | Узлов в адаптере до / после |
| ---: | ---: | ---: | ---: |
| 100 | 9,443 / 0,707 | 37 / 1 | 155 / 5 |
| 2 000 | 32,964 / 0,683 | 37 / 1 | 2 055 / 5 |
| 10 000 | 132,102 / 0,831 | 37 / 1 | 10 055 / 5 |

На 10 000 объявлений первый переход ускорился примерно в 159 раз. Медиана
повторных переходов — 1,647 → 0,311 мс. Пять удерживаемых узлов относятся
к пути выбранного модуля; при раскрытии UI обычные списки соседей подгружаются
отдельно. Поэтому «один RPC» относится к разрешению владельца, не ко всем
запросам, которые TreeView делает при показе выбранной ветки.

### Общие операции Metadata API

По три свежих процесса до/после, `diskCache:false`. В каждой выборке поиска
40 запросов; в таблице медиана трёх значений p95. RSS — пиковая память backend,
без Python/Node и редактора. Большой проект читается из соседнего playground;
hash корневого Configuration.xml проверен до/после каждой серии. Это не hash
всей конфигурации. Small намеренно содержит один отсутствующий descriptor.

| Стенд | Объектов | Open до / после, мс | Индекс до / после, мс | Поиск p95 до / после, мс | Peak RSS до / после, MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| small | 40 | 0,977 / 0,906 | 12,635 / 12,709 | 0,872 / 0,813 | 15,40 / 15,29 |
| synthetic | 42 001 | 8,126 / 8,691 | 260,120 / 282,392 | 4,508 / 4,663 | 41,21 / 41,36 |
| buhmfo | 138 373 | 207,062 / 200,984 | 6 207,881 / 6 186,582 | 29,920 / 32,403 | 202,09 / 202,13 |

На buhmfo ошибок индексации нет. Первое раскрытие после изменения — 4,400 мс,
первые свойства — 17,053 мс, повторные свойства p95 — 6,394 мс, refresh одного
объекта — 20,735 мс. Медиана максимальной задержки status во время индексации —
108,252 мс. Времена обычных операций близки к исходным; поиск и synthetic index
в этой серии немного медленнее. Три запуска не доказывают статистической
эквивалентности. Ускорение этих операций не заявляется, новый кеш не добавлялся.

## Воспроизведение

Из корня `eska`:

```sh
cargo build -p eska-project --profile dist
python3 tools/ide-protocol-bench.py small --runs 3
python3 tools/ide-protocol-bench.py synthetic --runs 3
python3 tools/ide-protocol-bench.py big --root ../eska-playground/big_configuration_temp/src/buhmfo --runs 3
```

Из корня `eska-vscode-explorer`, после `npm run compile`:

```sh
ESKA_TEST_BINARY="$(realpath ../eska/target/dist/eska-project)" \
ESKA_TEST_ROOT="$(realpath ../eska-playground)" node test/reveal-performance.mjs

ESKA_TEST_BINARY="$(realpath ../eska/target/dist/eska-project)" \
ESKA_TEST_ROOT="$(realpath ../eska-playground)" VSCODE_EXECUTABLE=codium \
node test/run-host.mjs test/source-navigation-host.cjs
```

Для baseline нужны исходные revisions обоих репозиториев; один новый клиент
со старым backend не воспроизводит прежний алгоритм. Standalone benchmark
`test/reveal-performance.mjs` можно запускать с каждой собранной парой.
Параметры установленного VSIX, локали и обычного окна описаны в
`eska-vscode-explorer/docs/development.md`.
