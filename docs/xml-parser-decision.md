# T63: стратегия чтения Designer XML

Решение от 2026-09-17: **оставить `roxmltree 0.21.1` для bounded parsing одного
metadata descriptor по запросу**. Уточнение T64: добавлен `quick-xml 0.42.0`
без optional features для предварительного ограничения глубины (см. ниже).
XML DOM не хранится в модели или cache: parser извлекает логические значения,
ссылки и диапазоны, затем освобождает DOM и входной буфер. Общая DOM проекта
и чтение payload форм/макетов или BSL для построения дерева запрещены.

Потоковый `quick-xml 0.42.0` быстрее и экономнее по памяти на крупных XML,
но текущий tree parser укладывается в исходные бюджеты с запасом. Экономия около
3 мс на корне сама по себе не оправдывала замену стратегии извлечения модели.
Вернуться к потоковому извлечению значений можно по измерениям T68, если модель
и cache нарушат бюджеты. Предварительный проход T64 выполняет только защиту
границы; namespace, значения и диапазоны по-прежнему извлекает roxmltree.

Версии сверены с актуальной документацией:
[roxmltree 0.21.1](https://docs.rs/roxmltree/0.21.1/roxmltree/),
[quick-xml 0.42.0](https://docs.rs/quick-xml/0.42.0/quick_xml/).
Кандидат исследован без optional features; его manifest указывает MIT и
MSRV 1.86. Для текущего UTF-8 Designer XML не использовались encoding,
Serde или async features. Свой XML tokenizer не разрабатывается.

## Условия сравнения

Linux 7.2.5-200.fc44.x86_64, Intel Core i5-13420H, 16 079 640 KiB RAM,
Rust 1.98.1. Отдельный исследовательский executable, стандартный Cargo release
profile (`opt-level=3`), зависимости закреплены точно. Это не release-профиль
eska с LTO и не интерфейс VS Code.

[Harness](../tools/xml-parser-bench.rs) создаёт `roxmltree::Document` либо
читает `quick_xml::NsReader` через `BufReader<File>`. Оба варианта каждый раз
открывают и читают тот же файл, проверяют namespace, считают элементы,
атрибуты, декодированный текст, глубину и первую metadata byte-position.
Для tree обход также вычисляет глубину через родителей; это стоимость
parse-and-inspect, не изолированный микротест XML-tokenizer.

Пять отдельных процессов на вариант/файл, порядок tree/stream чередуется.
В процессе 31 повтор; таблица показывает медиану пяти медиан и медиану пяти
p95. Peak RSS — максимум пяти процессов через `/usr/bin/time`.
Файловый cache ОС прогрет; cache не сбрасывался, поэтому эти числа не называются
cold disk latency. [Исходные результаты и SHA-256 входов](measurements/t63-xml-parser.json).

| Вход | Байты | Tree median / p95, мс | Stream median / p95, мс | Tree / stream peak RSS, KiB |
|---|---:|---:|---:|---:|
| Маленький справочник fixture | 1 403 | 0,017 / 0,027 | 0,015 / 0,027 | 2 596 / 2 420 |
| `Configuration.xml` большого стенда | 1 773 646 | 9,224 / 11,250 | 5,953 / 6,601 | 11 124 / 2 536 |
| `Document.ВводНачальныхОстатков` | 965 947 | 8,265 / 10,520 | 5,552 / 6,303 | 10 840 / 2 556 |
| `Report.РегламентированныйОтчетПрибыль` | 48 821 | 0,274 / 0,388 | 0,233 / 0,355 | 2 832 / 2 492 |

Все структурные счётчики и исправленные byte offsets совпали. Для трёх реальных
XML учтённые копии нормализованного текста составили соответственно 76 561,
209 466 и 2 741 байт в обоих вариантах. Это только текстовые буферы, которые
API пометил owned после нормализации, **не общее число/объём allocations**.
Tree удерживает полный входной UTF-8 буфер; stream — IO/event buffers
(максимальная ёмкость event buffer здесь 868 байт). RSS включает весь процесс.

## Корректность и пределы

Проверены namespace prefixes, BOM, CRLF, Unicode, CDATA, обычные и числовые
entities. С обоими адаптерами отклонены mismatched tags, повтор одного
атрибута, неизвестный prefix элемента, неизвестная entity, DTD, несколько
корней, 257 уровней, больше миллиона узлов и файл больше 64 MiB.

Для streaming это не всё встроенные гарантии: запрет DTD, единственный корень,
node/depth/event limits и разрешение entities явно выполняет исследовательский
адаптер. `quick-xml 0.42.0` исключает UTF-8 BOM из `buffer_position`; до поправки
первый metadata offset отличался на 3 байта. После учёта BOM позиции совпали.

Упрощённый stream-адаптер принимает три входа, отвергнутых roxmltree:
необъявленный prefix атрибута, два атрибута с одинаковым expanded name через
разные prefixes и `&#x1;`. Это ограничения исследованного адаптера, а не
утверждение, что такую валидацию невозможно добавить. Переход потребовал бы
дополнительной namespace/XML валидации и новых регрессионных проверок.

Чужой namespace синтаксически корректен для обоих XML parsers, но его metadata
count равен нулю; слой Designer XML обязан отвергать такой корень отдельно.
Проверка T62 подтверждает это на фактической точке открытия проекта.

Исходное предложение T63: 64 MiB UTF-8, миллион XML-узлов, 256 уровней.
В T64 depth probe вызвал stack overflow в debug-тесте до проверки DOM:
tokenizer roxmltree рекурсивен, у ParsingOptions нет предела глубины.
Поэтому фактический предел снижен до **64 уровней** и проверяется до DOM
через `quick-xml::Reader::read_event`, без собственного tokenizer. Граница 64
проходит на стандартном стеке тестового потока. Размер/число узлов сохранены.
Исходные release-замеры ниже/выше не включают этот предварительный проход;
новый backend baseline должен учитывать его в T68.
Из-за ограниченного размера выбранных файлов полный per-file DOM
допустим, но удерживать DOM всех открытых объектов нельзя. Неизвестный тип
метаданных даёт диагностическое сообщение, неизвестное свойство сохраняется
структурированно; payload остаётся отдельным source.

Source mapping использует исходные byte ranges roxmltree с учётом BOM/CRLF.
Нормализация текста для значения не меняет координаты исходного XML.
Конвертация в строку/UTF-16 столбец IDE выполняется на границе source API,
не путём переписывания XML. Полный вход не клонируется для каждого свойства.

## Исходные бюджеты T68/T81

Это проект бюджетов для этого стенда и класса оборудования, не обещание для
любой машины. Замеры здесь ещё не включают модель, search index или VS Code.
T68 должен зафиксировать повторяемый baseline окончательной реализации и
проверить бюджеты; T81 — повторить пользовательские сценарии через расширение.

| Сценарий | Исходная цель |
|---|---|
| Корень до готовности поискового индекса | p95 ≤ 200 мс после готовности процесса |
| Первое чтение одного descriptor до ~1 MiB | p95 ≤ 50 мс backend |
| Повторное раскрытие/выбор уже загруженного узла | p95 ≤ 20 мс backend, без повторного XML parse |
| Поиск по готовому индексу | p95 ≤ 50 мс backend, без чтения XML |
| Выбор/фильтр через VS Code | p95 ≤ 100 мс до реакции интерфейса |
| Память процесса metadata workspace со всем поисковым индексом | peak RSS ≤ 256 MiB; размеры index/cache учитываются отдельно |

Числа индексации и 3 808 общих модулей ещё не измерены: T68 обязан добавить
их вместе с отменой и приоритетом интерактивных запросов. Счётчики I/O/parse
проверяются детерминированно, wall-clock budgets не превращаются в flaky tests.

## Воспроизведение

Создать собственный временный Rust-проект **в соседнем `eska-playground`**,
скопировать harness в его `src/main.rs`. Manifest эксперимента:

```toml
[package]
name = "eska-xml-parser-bench"
version = "0.0.0"
edition = "2024"

[dependencies]
roxmltree = { version = "=0.21.1", default-features = false, features = ["std", "positions"] }
quick-xml = { version = "=0.42.0", default-features = false }
```

Собрать только этот Rust harness через `cargo build --release`, затем запустить
его с аргументами `tree <XML> 31` и `stream <XML> 31` под `/usr/bin/time`.
Входы большого стенда находятся относительно репозитория в
`../eska-playground/big_configuration_temp/src`.
**Сборка конфигурации 1С не запускается**, исходники читаются без записи.
Собственный временный каталог эксперимента после сохранения результатов удаляется.
