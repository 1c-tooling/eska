# Статическая проверка CI

`eska-check` — самостоятельный компонент для Designer XML и полного BSL-анализа
выбранного приложения. Он не запускает `eska`, `eska-project`, IDE, Git или платформу
и не связывает ядро bsl-analyzer. Нужен опубликованный `bsl-analyzer-app` 0.3.2
с машинным контрактом 3.4. Сам компонент собирается: `cargo build -p eska-check --locked`.

Пример для CI; `PROJECT_ROOT`, `BSL_ANALYZER` и `CHECK_REPORT` задаёт среда запуска:

```sh
target/debug/eska-check --project-dir "$PROJECT_ROOT" \
  --analyzer "$BSL_ANALYZER" --format json --report "$CHECK_REPORT"
```

`--project-dir` начинает обычный поиск `eska.toml`; по умолчанию используется cwd.
`--application` выбирает объявленное приложение. Если выбор неоднозначен,
проверка останавливается. Состав, source, зависимости и платформа берутся из
[общего контекста](application-context.md), правила — из `[tools.bsl-analyzer]`,
[пороги CI](analyzer-configuration.md#пороги-ci) — из `[tools.eska-check]`.
Пути членов приложения в аргументах pipeline повторно не перечисляются.

`--analyzer` принимает путь либо имя исполняемого файла. Без него используются
`ESKA_BSL_ANALYZER` и затем `bsl-analyzer-app` из PATH. Версия и CLI-контракт
проверяются у выбранного файла. `--timeout` — положительное число секунд на
каждый внешний процесс, по умолчанию 600. Сеть и установщик не запускаются.

## Проверка и запись

Проверка разрешает контекст, подготавливает только принадлежащий ESKA
`bsl-analyzer.toml`, обходит объявленные XML-дескрипторы общими resolver/parser
и вызывает `analyze --format jsonl` внешнего анализатора. Производный конфиг
проверяется настоящим `check-config`, повторный запуск идемпотентен. Чужой
конфиг, ручная правка managed-файла и чужой активный контекст дают ошибку.
Миграция и переключение контекста требуют отдельного явного действия через
[проектный инструмент](analyzer-configuration.md); CI не выполняет их молча.

Полный набор BSL-файлов сверяется с событиями `start/file/done`, включая чистые
файлы. Ошибка файла, ненулевой `failed_files`, потеря/дубликат события, неверная
версия, повреждение JSONL, обратные диапазоны, несогласованные счётчики
и ненулевой exit после `done` означают незавершённую проверку. Пустой набор
тоже не считается успехом. Процесс при timeout или отмене завершается и reaped.

`analysis.diff_base` и непустой `analysis.ignored_authors` отклоняются как
частичный анализ; флагов changed-only нет. Литеральные `source.exclude`
применяются в значении upstream, относительно корня конфига. Symlink,
непредставимые UTF-8 пути и выходящие за root исключения отклоняются.
Baseline допускается только с итоговым состоянием disabled либо full/complete.
Порог применяется к эффективным диагностикам после выбранной upstream-политики.

Общий lease запрещает конкурентную замену контекста. Перед выдачей отчёта
повторно проверяются манифесты, конфиг и байты XML/BSL, а также добавление
и удаление файлов. Изменение входов означает незавершённый результат.
ESKA не создаёт дополнительный BSL-индекс.

Структурная проверка не заменяет компиляцию платформой и не проверяет
непрозрачные данные форм. Отсутствующий, повреждённый или неподдерживаемый
объявленный дескриптор останавливает её. Размер одного JSONL-события ограничен
8 MiB, всего потока — 256 MiB; превышение не выдаётся за частичный успех.

## Результат

`--format human|json` выбирает stdout; по умолчанию human. `--lang ru|en`
меняет интерфейс и справку. Код возврата отделяет диагностики от сбоя инструмента:

| Exit | Результат | `complete` |
|---|---|---|
| 0 | `passed` | true |
| 1 | `threshold_exceeded` | true |
| 2 | Ошибка аргументов clap | JSON не обещается |
| 3 | `incomplete` | false |
| 130 | `cancelled` | false |

JSON schema 1 имеет `kind: "check"`. Завершённый отчёт содержит `scope: "full"`,
фактический `context` с root/application/limited_context, версию анализатора,
вид структурной проверки, число объектов, `counts`, `policy`,
`input_fingerprint` и `files`. Каждый файл содержит обратимый `{value,encoding}`
путь и `diagnostics` с code/message/severity и нумерацией строк/столбцов с нуля
из JSONL. Human-вывод показывает строки и столбцы с единицы. Ошибка содержит
`error: {code,data}` и не содержит неполного массива диагностик.

Времена не входят в отчёт. CLI locale не меняет JSON, выбор контекста или
правила. Язык upstream-сообщений остаётся настройкой `[tools.bsl-analyzer.output]`.
Локализованные объяснения и upstream-логи ошибок идут отдельно на stderr.

`--report` сохраняет тот же JSON независимо от формата stdout. Родительский
каталог должен существовать; файл должен быть новым и находиться вне source
выбранного контекста. Существующий файл сохраняется, отказ происходит до
подготовки конфига и анализа. Ошибка начального resolve ещё не создаёт файл
отчёта; JSON ошибки доступен на stdout. Ошибка записи даёт exit 3. При аварийном
прерывании записи файл может быть неполным; потребитель проверяет и JSON,
и exit code. XML/BSL и исходный пользовательский конфиг не перезаписываются.

Контракт проверен по [исходникам analyze 0.3.2](https://github.com/itrous/bsl-analyzer/blob/v0.3.2/crates/bsl-analyzer/src/bin/cli/analyze.rs)
и [JSONL-событиям](https://github.com/itrous/bsl-analyzer/blob/v0.3.2/crates/ide/src/jsonl.rs).

## Проверка T93

На Linux x86_64 прошли полный workspace fmt/check/strict Clippy/test/Rustdoc:
798 Rust-тестов passed, 12 ignored. Три явных теста с настоящим опубликованным
анализатором прошли отдельно: четыре standalone-типа, приложение с базой,
пятью расширениями и EPF, CLI с пустым PATH и побайтно одинаковым JSON ru/en.

Process-тесты покрывают нулевой exit при неполном потоке, `failed_files`,
ошибки файлов, неверную версию, ненулевой exit после `done`, timeout и SIGINT,
политику порогов, сохранность пользовательского конфига и отчёта, BOM/CRLF,
локализацию human и JSON. После timeout/отмены проверено отсутствие owned PID.
Нормальный граф зависимостей `eska-check` не содержит полной ESKA,
`eska-project`, `gix`, platform runtime, HTTP/updater или BSL-движка.

Промежуточные полные прогоны получили ошибки Git preflight при параллельных
sandbox-командах: внутри sandbox у playground виден пустой `.git`, на хосте
его нет. Финальный полный прогон одним запуском вне sandbox прошёл без
параллельных файловых команд; код VCS не менялся. Windows/macOS, Remote
и большое измерение `buhmfo` ожидают приёмки T89.
