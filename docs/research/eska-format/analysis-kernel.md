# Основа анализа EF-17

Выбран `ide-host-core` из bsl-analyzer с адаптером канонических метаданных ESKA.
Lexer, parser и вычисления BSL переиспользуются. Для постоянного сервера нужна
адресная передача метаданных с отслеживаемыми ревизиями; текущий эксперимент
проверяет независимые неизменяемые контексты, а не инкрементальный IDE-host.

Проверен commit `9021ba07471eee8a2614bed2105a2c8699f60780`, версия workspace
0.2.85, Rust 1.98.1, Linux x86_64. Установленный отдельный CLI 0.2.86 использован
только для проверки синтаксиса двух обезличенных BSL-модулей.

## Реальная граница API

[AnalysisHost](https://github.com/1c-tooling/bsl-analyzer/blob/9021ba07471eee8a2614bed2105a2c8699f60780/crates/ide-host-core/src/lib.rs)
отделён от LSP/MCP. Он принимает файловые тексты через `SourceDatabase` и выдаёт
снимки `Analysis`. Метаданные можно передать готовым `Configuration` через
`RootDatabaseImpl::set_graph_config_cache`: зарегистрированный корень получает
запись до первого запроса, XML-loader не требуется.
[Проверенная реализация](https://github.com/1c-tooling/bsl-analyzer/blob/9021ba07471eee8a2614bed2105a2c8699f60780/crates/ide-db/src/database.rs)
назначает этот cache для одного batch build. Его ключ — путь, а содержимое не
является Salsa input. Прототип создаёт новый host для каждой версии и никогда
не меняет cache опубликованного host.

Другой вход, `set_metadata_listing`, уже поддерживает адресную инвалидацию,
но `parse_mdo_query` получает XML-тексты файлов. Это не готовый интерфейс
канонических метаданных. Необходимое продолжение EF-18 — типизированный вход
по объекту/семейству с ревизией и проверкой полноты, общий для XML и ESKA.
Внешнее I/O остаётся в host; при неполной загрузке результат явно неполный.

| Вариант | Результат проверки | Решение |
|---|---|---|
| Адаптер к неизменяемому `Configuration` | Работает уже сейчас, включая несохранённые YAML/BSL | Использовать для воспроизводимого сравнения и batch-снимков |
| Небольшое расширение входного API bsl-analyzer | Позволяет переиспользовать вычисления и инвалидировать отдельные объекты | Целевой путь постоянного host; реализация и измерения — EF-18 |
| Отдельный fork всего языкового ядра | Потребует сопровождения тех же 30 библиотек и изменений движка | Не выбран; собственный parser не нужен |
| XML между ESKA и анализатором | Не даёт требуемой канонической границы | Не является выбранным способом интеграции |

Upstream ещё не изменён. Исследование не переключает и не редактирует checkout
bsl-analyzer, не объявляет его внутренний cache стабильным публичным протоколом.

## Воспроизводимый пример

[Runner](scripts/probe_analyzer.py) проверяет точный commit и чистоту reference,
создаёт уникальный каталог в соседнем playground и отдельные Rust consumers.
[Основной пример](scripts/analyzer_probe.rs) импортирует небольшой существующий
fixture и связывает `Справочники.Sample.СоздатьЭлемент()` с YAML-реквизитом.
Для каждой ревизии входа сохраняются hash manifest/владельца и revision BSL.
Оба query-контекста могут существовать одновременно.

Проверяются появление `DraftField` после несохранённой правки `Name`, сохранение
`SourceField` в предыдущем снимке, изменение вывода после BSL overlay,
отказ при неверном YAML и отсутствие записи исходников. XML-экспорт не вызывается;
у корня анализа нет `Configuration.xml`. Runtime запускается с пустым PATH.
Правка имени проверяет чтение draft: её допустимость для защищённого экспорта
не утверждается. Создание/rename остаются неподдержанными операциями EF-06/EF-07.

Пример намеренно проектирует только имена справочников и их прямых реквизитов.
Типы реквизитов явно `Unknown`, остальные владельцы посчитаны как unsupported.
Проверенные дополнения не означают готовность полного статического анализа.

```text
python docs/research/eska-format/scripts/probe_analyzer.py --analyzer ../bsl-analyzer
```

Для измерений к команде добавляются отдельные `--source <ESKA source directory>`.
Runner не импортирует и не изменяет эти входы. Lockfiles закреплены рядом
с примерами; `--locked` обязателен. Результаты и неизменённые приватные
конфигурации не включаются в репозиторий.

## Зависимости и сопровождение

Нормальный/build граф основного consumer на Linux содержит 199 packages,
из них 30 библиотек reference. В нём нет Git-движка, Tokio, reqwest, LSP/MCP,
launcher и клиента 1С. Один процесс использует IDE/batch API напрямую;
полный `bsl-analyzer-app` в ESKA не встраивается.

Reference также использует отдельный
[fork Salsa](https://github.com/itrous/salsa/commit/5d2686f1f94dc3d618569652d5576ce997491b3b)
на ревизии `5d2686f1f94dc3d618569652d5576ce997491b3b` (0.28.2).
Workspace patch не наследуется зависимым consumer. Обычная crates.io Salsa
0.28.5 дала ошибку `memory_usage(&mut self)` при сборке `ide-db`; закреплённый
patch прошёл сборку. Это отдельная стоимость обновления, а не готовая замена
движка произвольной совместимой patch-версией.

Для обновления сравниваются typed models, path/revision resolution, cancelled
queries и полнота; повторяются оба примера и C1/C2/C3. Изменение XML-bootstrap
не принимается автоматически как изменение адаптера ESKA. Узкую входную границу
следует держать у владельца языкового host, а не копировать весь database в ESKA.

Лицензии проверены по
[per-crate данным reference](https://github.com/1c-tooling/bsl-analyzer/blob/9021ba07471eee8a2614bed2105a2c8699f60780/LICENSING.md).
`lexer`, `parser`, `sdbl-hir`, `ide-diagnostics` имеют LGPL-3.0-or-later;
MIT/Apache у host не отменяет лицензии этих зависимостей. Provenance
`bsl-metadata` остаётся under review, а встроенные справочные данные 1С имеют
отдельные условия. Лицензия текущего ESKA не менялась. Поставка самостоятельного
анализатора должна включать notices и проверенный состав исходников в EF-21.

## Измерения

Release prototype: debug=0, LTO=false, codegen-units=16; размер binary около
44,8 MB. Это размер исследовательского consumer, не готового пакета поставки.
В каждом процессе один BSL-модуль; память — `/proc/self/status`, swap=0.
Кеш ОС не сбрасывался. Время чтения включает все YAML-владельцы, даже
непроецируемые; время запроса не включает эту подготовку.

| Вход | Открытие | Полная проекция | Дополнение BSL | Пик памяти | Справочники / реквизиты | Остальные владельцы |
|---|---:|---:|---:|---:|---:|---:|
| C1 | 0,055 s | 3,21 s | 24 ms | 56 MiB | 87 / 740 | 2 557 |
| C2 | 0,542 s | 53,34 s | 28 ms | 166 MiB | 743 / 9 829 | 15 542 |
| C3 | 0,649 s | 71,51 s | 27 ms | 189 MiB | 1 010 / 12 598 | 17 741 |

Это ограниченная проекция метаданных и один запрос, не полный индекс BSL.
Полное чтение C2/C3 при каждом вводе неприемлемо; показания не подтверждают
готовность IDE. EF-18 должен измерить ленивый ввод, адресную инвалидацию,
отмену и память настоящего набора модулей.

## Синтаксис для T26/T84

[Второй consumer](scripts/syntax_probe.rs) использует только `parser`/`syntax`:
52 normal/build packages на Linux, без Salsa, IDE host и метаданных проекта.
Он проверил lossless CST, ошибочный синтаксис, координаты строкового литерала
`Версия()`, сохранение BOM/CRLF/комментария и отсутствие `Экспорт`.
Обе строки `1.2.3`/`1.2.3.4` разбираются одинаковым parser.

Эти компоненты подходят для formatter и структурной правки внешней версии
без семантического индекса. Сам форматтер, правила `Версия()`, ручной bump
и трёхкомпонентный native version reader здесь не реализованы.
Workspace MCP в сессии недоступен; установленный CLI проверил ParseError
двух собственных файлов (0 диагностик). Отсутствующая XML-конфигурация в этом
синтаксическом примере не выдаётся за проверенный семантический контекст 1С.

Полный runner прошёл build/strict Clippy обоих consumers, все проверки draft
и три измерения. [Машинный результат](ef-17-results.json) содержит версии,
профиль, hashes воспроизводимых примеров и состав зависимостей без приватных путей.
Повтор использовал собственный build cache из playground; для этого есть
необязательный `--build-cache`. Исходники приложения, Cargo.toml/lockfile ESKA
и checkout reference не изменялись; повтор полного набора приложения не требовался.
