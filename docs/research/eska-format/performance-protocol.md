# Методика EF-09

Замеры ядра выполняются отдельным opt-in `real_playground_measure` в release,
без сборки платформой, повторного чтения всего YAML для приёмки и копирования
дерева ради assert. Отдельные операции: импорт, acceptance/open/restore базы,
обычный экспорт и защищённый экспорт. Для экспорта записываются первый вызов
с новым результатом и два повторных вызова с проверкой существующего результата.
Открытие базы учитывается отдельно; при повторах используется тот же объект базы.

Время измеряется вокруг core API через `Instant`, память — RSS и VmHWM процесса
из `/proc/self/status`. Наблюдения сохраняются после каждой операции, исходная
и конечная память — отдельно. VmHWM является показанием ОС, не лимитом процесса.
Сборка тестового binary не входит во время API. В debug результат не выдаётся
за release-стоимость. Исходники читаются, каждый прогон создаёт новый собственный
каталог в соседнем playground. Linux page cache не сбрасывается; это измерения
обычного локального исполнения, а не гарантированного холодного диска.

[`scripts/measure_storage_git.py`](scripts/measure_storage_git.py) сравнивает
исходный XML, XML из детерминированного writer и ESKA с полной принятой базой.
Во всех случаях меняются один Comment и один BSL-комментарий. ESKA получает
только эти две разрешённые правки из подготовленного стенда; запрещённая правка
из EF-08 не переносится. Для каждого варианта отдельно создаётся двухкоммитная
история с обычным Git и с LFS. Каждый репозиторий имеет собственные настройки,
три повторения clean/dirty status и diff, отдельно измеряются add/commit и pack.
Pack выполняется с одним потоком, общий Git config и hooks пользователя
не подключаются; сетевых операций нет. Это измерения **system Git**,
а не будущего `eska-vcs` или gix.

Логический объём файлов и фактические `st_blocks` с каталогами учитываются
раздельно. Отдельно записываются рабочий источник, полная база, Git index,
objects/pack и LFS objects. Временный экспорт, завершённые XML-поколения и
восстановленный источник учитываются отдельно от постоянного исходного дерева.
Git-дедупликация не означает уменьшение рабочей копии; LFS не считается
экономией без включения его локальных объектов.

Проверка реального блока базы C1 выявила изменение его байтов стандартным
`* text=auto`: 2 802 байта стали 2 731 после CRLF-нормализации Git.
С `-text -filter` байты сохраняются. Поэтому benchmark явно использует `-text`
для всех исходников и блоков; в LFS-сценарии extensionless блоки классифицируются
по исходным путям в `accepted.json`, чтобы копии одного payload использовали
тот же LFS object. Настройка VCS для публичного ESKA-проекта должна обеспечить
этот перенос до его использования. Core не читает Git-настройки и не обходит
проверку SHA-256. Сам benchmark не добавляет готовую VCS-интеграцию продукту.

Физические входы C1/C2/C3 инвентаризируются без сборки больших конфигураций.
Дополнительно C2/C3 импортируются отдельными release-процессами с
`RLIMIT_AS = 4 GiB`; лимит адресного пространства не называется лимитом RSS.
Для проверки временного XML одновременно сохраняется первое поколение и
готовится второе из отдельного источника с двумя разрешёнными правками.
Opt-in получает его через `ESKA_FORMAT_NEXT_INPUT`; рабочие источники не меняются.
Время измерений и состояние доступных ресурсов фиксируются в private отчётах;
сравнение разных стендов не выдаётся за контролируемый эффект нового формата.
Решение по интеграции принимается после результатов, с отдельным учётом размера,
латентности, памяти, Git и обязательной базы.
