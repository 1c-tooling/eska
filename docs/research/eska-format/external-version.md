## Источник и явная миграция

Номер хранится в единственном строковом возврате экспортной `Версия()` без
параметров. Native XML внешнего объекта идентифицирует объект и не служит
резервным источником номера. При наличии `СведенияОВнешнейОбработке()` её
подтверждённое поле версии должно получать значение вызовом `Версия()`.
[Синтаксический профиль](external-version-syntax.md) ограничен и не заменяет
семантический анализ произвольной регистрации БСП.

`version migrate` показывает план. `--write` применяет его к тому же снимку;
`--initial-version` явно задаёт номер отсутствующей функции. План добавляет
документированную функцию, экспортирует пригодную закрытую сигнатуру и
связывает подтверждённый литерал регистрации. Остальная логика сохраняется.
Импорт и чтение ничего не переписывают; пустой scaffold не получает выдуманных
нативных метаданных. Отсутствующий модуль существующего объекта создаётся
только через явную миграцию. Повтор готового плана не меняет файл.

`version`, ручной bump, doctor и build используют общий контракт. Сборка
проверяет его до запуска платформы и на immutable snapshot, в том числе без
явного `[version].scheme`. CI получает code, путь, исходный byte range и
remediation; doctor добавляет `project.version`. JSON не зависит от языка.

## Нативный цикл и выполнение

В собственных изолированных проектах выполнены preview RU/EN, применение,
повтор, чтение RU/EN, minor bump, сборка и новая выгрузка через `new --from`.
Проверены точная версия manifest и независимая контрольная сумма артефакта.
Всего прошли 40 положительных этапов этого цикла.

| Артефакт | Схема | До bump | После bump, выгрузки и вызова |
|---|---|---|---|
| EPF | `x.y.z` | `1.2.3` | `1.3.0` |
| EPF | `x.y.z.build` | `01.02.003.0004` | `01.03.001.0001` |
| ERF | `x.y.z` | `1.2.3` | `1.3.0` |
| ERF | `x.y.z.build` | `01.02.003.0004` | `01.03.001.0001` |

Три исходных модуля не имели функции; один ERF имел пригодную закрытую
`Версия()`. Миграция добавила/экспортировала функцию и связала регистрацию;
отдельный чужой литерал версии сохранился. Bump менял только байты номера.
Повторная выгрузка сохранила экспорт и точное число компонентов, включая нули.

В отдельную owned ИБ загружен и применён CF проверочного клиента через `ibcmd`:
команда apply ESKA ещё не реализована. Клиент 1С в Xvfb создал каждый из четырёх
скомпилированных внешних объектов и вызвал обе экспортные функции.
`Версия()` и поле `СведенияОВнешнейОбработке().Версия` совпали с ожидаемым
номером во всех случаях. Регистрация использует настоящую `Структура`, без
подмены БСП. Приёмка не подтверждает интеграцию с подсистемой регистрации
боевой конфигурации или поведение её остальных полей.

## Отказы и проверки

Копия настоящего нативного проекта с закрытой `Версия()` отказана сборкой на
RU/EN до платформы. Исходник и прежняя пара EPF/manifest сохранились побайтно;
code, range и remediation совпали. Автоматические проверки дополнительно
покрывают отсутствующие модуль/функцию, дубли, неверные тела/сигнатуры, директивы,
ошибочный синтаксис, неподтверждённую регистрацию, mismatch схемы, stale bytes,
`.bin`, symlinks и read-only. BOM/CRLF и права файла сохраняются.

Все 18 Rust/SDK/adapter gates прошли: fmt, check, strict Clippy, обычные и
all-feature tests, Rustdoc с запретом предупреждений и минимальная сборка core.
Результат: 729 unit, 584 integration, 44 project-tool, 12 build-tool,
359 SDK и 82 adapter теста. 24 прежних ignored сохраняют свой статус.

Workspace MCP был недоступен. Справочный MCP использован для API платформы;
установленный `bsl-analyzer-app` 0.3.2 завершил анализ четырёх модулей и двух
модулей проверочного CF с `failed_files = 0`, без diagnostics severity `Error`.
Внешние модули имеют замечания к оформлению исходных регистрационных функций.
Проверочный CF также имеет diagnostics о тестовых путях и использовании
внешнего кода. Эти замечания не выдаются за отсутствие всех diagnostics;
платформенное выполнение проверено независимо.
