# Расширения в формате ESKA — EF-14, часть 1

Project core принимает `type = "extension"` с `source_format = "eska"`.
Импорт определяет тип по корню native XML; читатель сверяет его с настройкой
проекта. CFE сохраняет корень `Configuration`, его native UUID и имя,
`ConfigurationExtensionPurpose`, `ObjectBelonging`, заимствованные объекты,
зависимости, модули и ресурсы. Эти сведения не заменяются directory-derived
identity и не назначают права сами себе. Права принадлежат отдельно принятой базе.

`eska-project import` создаёт family/readable проект расширения, `inspect`
читает его настройки и корень, `prepare` проверяет pin и готовит защищённое
поколение. Модель форм map 4 и запросов map 5 применяется через существующие
явные source API. Общий CLI new/init и выбор окончательной структуры остаются EF-20.

`eska-build` собирает CFE из защищённого поколения и проверяет фактический
snapshot. Тип root XML, выбранного проекта и артефакта должен совпасть.
Manifest сохраняет pin, карту исходников, SHA-256 и native version по обычным
правилам CF/CFE. `--base-configuration` позволяет загрузить явный CF в управляемую
ИБ для сборки; checksum базы участвует в правилах её повторного использования.

Анализаторный контекст основной конфигурации остаётся EF-18. SDK возвращает
`SessionError::UnsupportedProjectType`; checker — exit 3 с
`analysis_scope_unsupported`; LSP initialize — `-32000` с тем же machine kind.
Поддержанный source reader не означает завершённый семантический профиль.
Новая ветка экспериментального `SessionError` меняет недокументированный Rust API;
формы успешных CLI/JSON ответов не изменены.

## Платформенная проверка

На установленной 1С 8.3.27.2325 через Distrobox использовано настоящее расширение
из playground: 107 native файлов, 25 модулей, 10 управляемых форм. Map 5 вынес два
запроса СКД/динамического списка в самостоятельные `.sdbl`.

Пройдены три сравнения независимой нативной сборки и ESKA: readable map 3,
map 5 без правок, map 5 после правок комментария метаданных, BSL-модуля,
запроса СКД и порядка двух элементов формы. После сборки CFE повторно распакован
через `eska new --from`. В каждом сравнении совпали все 107 пути и все байты
метаданных, модулей и ресурсов. Отличался только служебный ConfigDumpInfo.
Дополнительно CFE собран с явно переданным CF основной конфигурации.

Настоящий freeze модуля проверен отдельно: строгая сборка RU/EN отказана до
поиска платформы; `--allow-exclusions` восстановил принятый модуль при упаковке,
сохранив рабочую правку. Повторная выгрузка CFE подтвердила принятые bytes.

Прямая `ibcmd config export --file` для этого CFE дала 106 файлов и ошибку
формата хранилища. Полная загрузка/выгрузка именованного расширения дала 107.
Пробная выгрузка служит только для проверки identity и выбора native режима;
её частичные файлы не публикуются. Повторный export обязан сохранить type/UUID/Name
и ConfigDumpInfo. Отдельные тесты проверяют неверные суффиксы, ошибки загрузки
и выгрузки, другую identity и отсутствующий dump state без изменения проекта.
На настоящей платформе подтверждены CFE с суффиксом `.cf` и CF с `.cfe`:
1С сначала прочла ложную пустую конфигурацию, проверка identity её отбросила,
ограниченный повтор в новой ИБ восстановил правильный тип. Повтор допустим
только после несовпадения проверенных identity; остальные ошибки и отмена
завершают операцию. Native суффиксы меняются только у собственной временной копии.
Подробности — в [контракте распаковки](artifact-export.md).

Workspace MCP BSL недоступен; изменённый модуль проверен установленным
`bsl-analyzer-app`: полный результат для одного файла, `failed_files = 0`,
диагностик Error нет. Сохранились 28 рекомендаций других уровней и предупреждение
о недостающем контексте основной конфигурации. Это проверка модуля, а не полная
семантическая или runtime-приёмка расширения.

[Машинный результат](extension-results.json) фиксирует измерения.
EPF/ERF и адаптер версии T84 остаются следующей частью EF-14; полнота анализа,
новый общий CLI, установка Explorer и весь MVP здесь не объявляются готовыми.
