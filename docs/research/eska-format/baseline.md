# Принятая база и разрешения, EF-05

Внутренний `accept_source` принимает проверенный полный ESKA-снимок в новый
отдельный каталог. Рабочая модель сначала проходит те же проверки файлового
состава, native identity и ссылок, что экспорт EF-04. Неизвестные UUID в списке
дополнительной заморозки отклоняются.

База содержит `accepted.json` и блоки `blobs/<первые два символа SHA-256>/<SHA-256>`.
Manifest закрепляет версии схемы/правил, профиль, revision исходного XML и
принятого ESKA, UUID конфигурации, все файлы/директории и заморозку.
Одинаковые байты сохраняются одним блоком. Восстановление создаёт полный исходный
ESKA-каталог без оригинального checkout, платформы, Git и восстанавливаемого кеша.
Готовый manifest записывается после блоков; ошибка не оставляет заявленную готовой
базу. Существующие каталоги не заменяются.

`AcceptedRef.sha256` — контрольная сумма байтов `accepted.json`. `AcceptedBase::open`
требует ожидаемую ссылку от вызывающего инструмента и проверяет все обязательные
блоки до вычисления прав. Для CI эта ссылка должна поступать из отдельно
управляемого источника доверия, например защищённой настройки job. Взять её
из произвольно редактируемого YAML и назвать это проверкой политики нельзя.
Способ доставки/закрепления в публичном CLI будет добавлен в EF-10.

Native правила читаются существующим `project::support::Support` из закреплённого
`Ext/ParentConfigurations.bin`. В наблюдаемом профиле каждому поставщику необходим
`Ext/ParentConfigurations/<native name>.cf`; отсутствие, неоднозначность и лишний
CF дают отказ. Байты правил и этих CF должны совпадать с файловым свидетельством
импорта. Их пути, размеры, SHA-256, ID поставщика и UUID его конфигурации входят
в принятую базу. Отсутствие правил явно закрепляет конфигурацию без поддержки;
оно не допускается при присутствующих CF поставщиков.

Эта проверка связывает комплект с принятым входом. Она не читает внутренности CF
и не доказывает подлинность поставщика. Загрузка реальных CF и сохранение native
поддержки проверяются платформой в EF-08. Синтетические тесты используют явно
обозначенные непрозрачные CF-заглушки, а не утверждают их нативную валидность.

Разрешение вычисляется по принятому UUID для конкретной операции. Поддержаны
изменения покрытых [typed properties](readable-layout.md), модулей и ресурсов
согласно native состоянию. [Перестановка существующих детей](child-order.md)
использует `Reorder`; protected selector дополнительно проверяет прежний состав,
native class каждой позиции и права всех перемещённых элементов.
Создание/удаление, перенос, переименование и изменение `Name`
пока возвращают `unsupported_operation`. Проверка разрешения не заменяет
проверку существования свойства или файлового владельца при применении правки.

Несколько поставщиков пересекают ограничения. Заблокированный родитель
не отменяет явно редактируемую inline-часть. Дополнительная ESKA-заморозка
распространяется на принятых inline и внешних потомков, включая формы;
native состояние при этом сохраняется отдельно. Неизвестный UUID не получает
разрешение. Решение содержит UUID, состояние, native причину, ESKA причину и
контрольную сумму базы. Рабочий YAML, его статус и переключатель редактора
не участвуют в чтении принятой политики.

Публичная сборка пока не подключена. Восстановление запрещённых правок и публикация
проверенных поколений выполняются следующим этапом EF-06.

Реальная C1: принят и побайтово восстановлен полный комплект из 7 829 файлов ESKA,
включая правила и 134 388 317 байт CF двух поставщиков. Полный цикл теста в debug
занял 151,48 с. Это файловая проверка новой базы; доказательство работы CF в 1С
к ней не приписывается. Обычные тесты отдельно удаляют оригинальные каталоги,
переносят только принятую базу и восстанавливают исходники на чистом месте.
