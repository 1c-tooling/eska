# Структура ESKA и граница MVP

Решение о приоритетах от 2026-10-11: закончить структуру исходников и файловый
цикл четырёх типов проектов, затем анализатор, затем принять работу в Explorer.
После MVP — `fmt`, затем VCS. Это целевой план, а не описание уже доступного API.
Реализация и статусы находятся в [очереди EF](../../roadmap/15-eska-format-experiments.md).

## Что подтверждено сейчас

| Представление | Проверенное устройство | Вывод для ESKA |
|---|---|---|
| Designer XML | Коллекции типов; descriptor объекта и каталог его ресурсов; `Ext`, формы, модули, макеты. Запросы находятся внутри XML формы/СКД | Сохранить узнаваемые коллекции, родные identity и обратную карту; отделить редактируемые тексты от XML-оболочки |
| EDT, опубликованный пример 1С | `.mdo` содержит свойства, реквизиты и описания форм/макетов; содержимое лежит в `Forms/.../Form.form`, `Module.bsl`, `Templates/.../Template.dcs`; модули объекта лежат рядом с `.mdo`. Проверенные запросы остаются внутри XML `.form`/`.dcs` | Полезна близость файлов одного владельца. Специальное расширение само по себе не делает XML удобнее для ручной правки |
| Текущая экспериментальная ESKA | Семейная версия 1 сохраняет `ObjectSource.nested`. [Версия 2](descriptor-layout.md) даёт самостоятельным descriptors собственные YAML; [версия 3](resource-layout.md) явно переносит модули и ресурсные наборы; [descriptor schema 2](readable-layout.md) использует именованные значения и отдельные native details. Writer типизирует [32 скаляра](typed-scalars.md) и [Type с qualifiers](type-description.md), [ссылки и списки метаданных](metadata-reference.md), [цели Type/TypeSet](type-targets.md) и [запрет вложенных именованных наборов](named-type-sets.md); [аннотации YAML](annotation-migration.md) мигрируют вместе с исходными полями | Импорт, reader/SDK, protected export и оба плана миграции сохраняют native evidence, байты и политику. Остальные составные домены/коллекции, совместимость типов, orchestration проекта и структурные операции ещё нужны |
| Текущий Explorer | Дерево и поддержка получаются из `eska ide`; есть защищённые вкладки и мост к языковым провайдерам. В `package.json` нет собственных `languages`/`grammars` | Наличие дерева сейчас не подтверждает подсветку и анализ нового формата. Их поставка и работа в защищённых вкладках требуют отдельной приёмки EF-11 |

Проверены исходники `project_core/source_format/{package,import,model}.rs`,
`project_cli/args.rs`, а в соседнем Explorer — `package.json`, `src/extension.ts`,
`src/protected-language.ts` и `docs/support-policy.md`. `eska-project import`
создаёт только новый каталог из Designer XML; это не `new/init` нового формата
и не обновление существующего проекта из нативного артефакта.
[Параметр `--layout readable`](readable-project-import.md) выбирает именованные
YAML и физические resources. Без параметра сохраняется family layout.
[Явная миграция standalone-проекта](project-migration.md) создаёт новую читаемую
копию с раздельным переносом рабочих правок и независимо закреплённой базы.
[Перестановки существующих детей](child-order.md) принимают прежний состав с
проверкой native class каждой позиции и поддержки/freeze. Workspace и операции
create/delete/rename ещё не приняты.

Внешние источники проверены 2026-10-11:

- [Руководство платформы 8.3.27, раздел 2.17](https://1c-dn.com/library/tutorials/1c_enterprise_developer_guide_8_3_27/?sphrase_id=1678862) — иерархическая выгрузка и отдельные ресурсы; версия соответствует исследуемому платформенному профилю.
- [Руководство EDT: работа с конфигурацией как с файлами](https://its.1c.ru/db/content/edtdoc/src/topics/i034.html).
- [Опубликованный пример EDT от 1С](https://github.com/1C-Company/dt-demo-configuration/tree/master/DemoConfDT/src) — проверены `.mdo` справочника, форма с динамическим списком, `.dcs` отчёта и `.rights` роли. Это свидетельство устройства конкретного примера, не обещание совместимости со всеми версиями EDT.

EDT служит референсом организации. Импорт/экспорт EDT, Java и `1cedtcli`
в этот план не входят.

## Граница файла

Файл соответствует самостоятельно редактируемому объекту или тексту со своим
языком и контекстом. Маленькие связанные свойства остаются вместе. Размер файла
сам по себе не создаёт новые границы: одинаковая структура проекта не должна
зависеть от случайного порога строк.

Основной `object.yaml` содержит свойства, реквизиты, табличные части с колонками,
измерения, ресурсы и упорядоченные ссылки на отдельные формы/макеты/команды.
Каждый реквизит не становится отдельным файлом. Описание самостоятельной формы,
макета, команды и подсистемы переносится из `nested` к собственному содержимому.
Команда формы остаётся частью формы; отдельная команда метаданных получает свой
каталог. Вложенная подсистема получает свой `object.yaml`, а не растущий блок
в YAML верхней подсистемы.

Целевой пример для обсуждаемого профиля; имена полей и версия схемы принимаются
в EF-24. Имена объектов условные, расположение не является текущим контрактом:

```text
project/
  eska.toml
  src/
    configuration.yaml
    source.json
    Catalogs/
      Products/
        object.yaml
        ObjectModule.bsl
        ManagerModule.bsl
        Forms/
          List/
            form.yaml
            Module.bsl
            Queries/
              List.sdbl
        Commands/
          Print/
            command.yaml
            Module.bsl
        Templates/
          Label/
            template.yaml
            Template.xml
    Reports/
      Sales/
        object.yaml
        ObjectModule.bsl
        Templates/
          Main/
            template.yaml
            schema.xml
            Queries/
              Main.sdbl
              Details.sdbl
    Roles/
      User/
        object.yaml
        Rights.xml
    Subsystems/
      Sales/
        object.yaml
        Subsystems/
          Reports/
            object.yaml
  .eska/
    accepted/
    generations/
```

`form.yaml` объединяет descriptor формы и её редактируемую модель EF-12;
параллельного descriptor этой же формы в `object.yaml` нет. Определения элементов
и порядок `layout` разделены внутри файла, модули и запросы вынесены. Обычная
двоичная форма хранится отдельным ресурсом с descriptor; её содержимое не
объявляется редактируемым YAML.

`schema.xml` в примере — сохраняемая структура СКД с явными ссылками ESKA вместо
текста извлечённых запросов. Это исходный ресурс ESKA, не готовый Designer XML.
EF-23 задаёт namespace/slots ссылок и убирает их при материализации. Inline-текст
и ссылка одновременно недопустимы. Остальные части схемы сохраняются; полный
typed writer СКД не требуется для изменения запроса. Такой же переходный envelope
применим к XML-форме до её миграции в EF-12; после миграции остаётся один источник.

У модулей сохраняются знакомые названия (`ObjectModule.bsl`, `Module.bsl`), но
рабочему дереву не нужна универсальная прослойка `Ext`. Физические имена и пути
ресурсов, на которые есть внутренние ссылки, меняются только вместе с обратной
картой. HTML с картинками, XDTO/XSD, макеты и бинарные payloads остаются цельными
ресурсными наборами. Служебные базы и поколения не показываются как исходники.
`accepted` — закреплённые обязательные данные, `generations` — удаляемый кеш;
попадание обоих под общее правило игнорирования `.eska` недопустимо.
Существующий контракт переноса байтов из [EF-10](git-transport.md) сохраняется:
исходники, обратная карта и база переживают чистый checkout без изменения байтов.
Эта проверка нужна MVP независимо от сроков выделения VCS.

## Читаемость и целостность

EF-24 должен убрать XML-механику из повседневных свойств: именованные свойства,
прямые типизированные значения, компактные ссылки и отдельная служебная секция
для точного восстановления. Нужно расширить редактируемое покрытие за пределы
четырёх строковых свойств: bool/enum, точные числа, составные типы, ссылки,
коллекции и свойства дочерних элементов по явной матрице. Отсутствие, пустое
значение, `nil` и явное значение по умолчанию остаются различимыми.

Для человека и ИИ действуют одинаковые правила:

- одна редактируемая копия каждого значения; нет одновременно актуальных XML
  и YAML одного объекта или inline-запроса и `.sdbl`;
- родной UUID плюс контекст владельца — identity; имя/путь служат навигации.
  Для наборов без native UUID нужна явная устойчивая привязка, без позиционного
  номера как единственного ключа;
- состав и смысловой порядок объявлены один раз. Сканирование файлов даёт
  индекс, но не может самовольно добавить объект в конфигурацию;
- краткие комментарии к нетривиальным свойствам и literal-строки допустимы;
  no-op и точечная правка не переформатируют соседние части;
- неизвестные XML-секции сохраняются с namespace, порядком и запретами опасных
  изменений. Они явно помечены как preserved, а не объявлены typed-поддержкой;
- ручные/ИИ-правки проверяются теми же валидаторами состава, ссылок и поддержки.
  GUI для создания объектов и автоматический глобальный rename не являются
  условием редактирования файлов;
- смена схемы и путей имеет отдельный план миграции, проверку исходных байтов
  и восстановление. Старые экспериментальные проекты не меняются при открытии.

У `source.json` уже есть обратная карта всех native файлов и provenance.
Нельзя объявить его целиком пересоздаваемым индексом и потерять opaque-файлы.
EF-24 отдельно определяет авторитетный состав, обязательную обратную карту и
производные hashes/индексы. Обычная правка запроса не должна требовать ручного
обновления checksum; проверка принятой базы остаётся независимой.

## Дополнительные кандидаты

Повторно прочитан локальный корпус C1 без изменений и без запуска платформы.
В 825 XML-формах найдены 123 непустых `QueryText`; в 51 СКД — 27 непустых
`query` и 397 `expression`, из них 30 многострочных. В 212 `Rights.xml` —
66 `restrictionByCondition` и 45 `restrictionTemplate`, всего 111 непустых
`condition`. Это инвентаризация XML-текстов одного корпуса, не результат
анализа языка, дедупликации запросов или платформенной приёмки.

| Кандидат | Решение | Причина и граница |
|---|---|---|
| Запросы наборов СКД и динамических списков | MVP: EF-23, анализ — EF-27 | Самостоятельный язык, частые длинные правки; один файл на запрос, пакет не дробится |
| Формы, макеты, отдельные команды, вложенные подсистемы внутри `nested` | MVP: EF-24/EF-12 | Собственная identity и область изменения; правка формы не раздувает основной YAML |
| Условия RLS и шаблоны ограничений | Следующее расширение: EF-26, после MVP/fmt/VCS | Реально встречаются длинные тексты и препроцессор; это контекст ограничений доступа, а не обычный standalone SELECT. Сначала утвердить диалект, расширение и bindings роли/объекта/права |
| Выражения вычисляемых полей, ресурсов, отбора и представления СКД | Кандидат EF-26; короткие оставить у владельца | Язык выражений СКД не равен BSL или SDBL. Выносить только явно выбранные самостоятельные длинные выражения после проверки пользы, без автоматического порога длины |
| `Rights.xml`, `Predefined.xml`, расписания, командный интерфейс, состав обмена | Сохранять отдельными ресурсами в MVP | Уже отделены Designer XML. Typed YAML для них — самостоятельное развитие, дробить каждое право/предопределённый элемент сейчас не нужно |
| HTML/текстовые макеты, картинки, XDTO/XSD, табличные и графические документы | Сохранить естественные файлы и связи | В исследованной выгрузке уже отдельные ресурсы; не превращать payload в YAML/base64 и не разделять табличный макет на ячейки |
| Строки запросов, собранные BSL во время выполнения | Не извлекать автоматически | Подстановка, порядок исполнения и динамический состав требуют отдельной задачи; статический текст нельзя произвольно заменить чтением файла |

## Приёмка MVP

«Структура завершена» означает принятую схему, миграцию текущего эксперимента,
полный обратимый состав и рабочий файловый цикл для `configuration`, `extension`,
`processing`, `report`. Сохранение непрозрачного ресурса подтверждается отдельно
от его редактируемой typed-модели. Неизвестные классы нельзя пропускать молча;
непринятое покрытие боевого проекта блокирует объявление этого проекта готовым.

Для каждого `.cf`, `.cfe`, `.epf`, `.erf` нужна отдельная строка отчёта:
`new/init` → открытие Explorer → правка YAML/BSL/доступного `.sdbl` → импорт
изменений в тот же проект → проверка → сборка → повторная выгрузка. Реальный
внешний отчёт обязателен; пустой ERF не заменяет приёмку. Для расширения проверяется
контекст базы и заимствованные объекты. Контракт версии T83/T84 сохраняется;
автоматические релизы для MVP не требуются.

Повторный импорт сравнивает общий синхронизированный предок, текущие исходники
и новую распаковку. Этот предок не равен автоматически принятой базе поддержки.
Изменение поставщика/прав проходит EF-15 с отдельным принятием. EF-25 показывает
добавления, удаления, переименования и конфликты, не теряет локальные правки и
не требует реализации Git merge. При неизвестном предке/identity требуется
явный выбор базы или сопоставления; эвристика по имени не разрешает конфликт.

В Explorer нужны прежние дерево, порядок, поиск, значки и объяснения поддержки,
защищённое открытие, файлы YAML/BSL/SDBL и изменения извне. Подсветка BSL/SDBL
и YAML должна работать сразу, включая защищённые URI, независимо от готовности
семантического индекса. Один analyzer владеет диагностикой, completion и
навигацией; одинаковые saved inputs дают согласованные IDE/batch результаты,
unsaved inputs и неполное покрытие видны явно.

EF-16 принимает установленный комплект и реальные пользовательские сценарии,
первый/повторный запуск и память большого проекта. Успешная компиляция Rust,
платформенная сборка, контрольная выгрузка и работа отчёта/списка в клиенте —
отдельные результаты. Здесь выполнено только исследование и изменение плана.
Форматтер, новый VCS, merge-драйвер форм, отладчик, автоматические релизы и
визуальный редактор форм находятся за границей MVP.
