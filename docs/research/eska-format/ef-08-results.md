# Платформенная приёмка: EF-08

Первый профиль принят для полного файлового цикла и CF-сборки обычной
конфигурации C1. Это не приёмка применения к рабочей ИБ и не проверка клиента.
Платформа — 8.3.27.2325 в установленном Distrobox; режим совместимости C1 —
`Version8_3_21`. Все действия выполнены на собственных копиях в соседнем
playground, исходный demo не менялся. Большие конфигурации не собирались.

## Маршруты

Контроль: исходный Designer XML → `eska build --manifest` → CF →
`eska new --from` с новой изолированной ИБ → Designer XML.
Эксперимент: импорт ESKA → закреплённая база → защищённое XML-поколение →
тот же маршрут `build`/`new --from`. Сборки используют
`--recreate-infobase --platform-version 8.3.27.2325`.
Подключение копий выполняется через `eska init --source src --workflow trunk
--no-vcs` с явной платформой. Публичный build самого формата ESKA пока не добавлен.

Выполнены независимые контрольный и преобразованный циклы без правок,
повторный контрольный цикл того же XML и два цикла после изменений.
Во всех повторных выгрузках по 8 769 файлов и 8 064 каталога.

| Сравнение | Результат |
|---|---|
| Исходный XML против ESKA, без правок | Все файлы и каталоги совпадают с оговоркой ниже |
| Повторная сборка того же исходного XML | Та же оговорка, остальных отличий нет |
| Изменённый контрольный XML против изменённого ESKA | Остальных отличий нет |
| До правок против результата ESKA | Ровно два изменённых native файла: descriptor и BSL |

Оговорка ограничена `configVersion` в `ConfigDumpInfo.xml`: при независимом
создании ИБ меняются все 7 011 таких значений. Повтор того же исходного XML
воспроизводит это без участия конвертера. Имена, ID, состав 11 746 именованных
записей и **все остальные байты** файла совпадают. Сравнение не исключает файл
целиком и не игнорирует UUID или порядок.

Платформа не переносит в CF десять файлов объектов вне объявленного состава
исходной конфигурации и добавляет `ConfigDumpInfo.xml`. Это одинаково для обоих
контрольных маршрутов. Файловый XML → ESKA → XML сохраняет все исходные 8 778
файлов, включая эти данные; перенос произвольных файлов через CF не обещается.

Правила нативной поддержки и оба полных CF поставщиков во всех сравниваемых
выгрузках сохранены байт в байт. Одинаковые остальные native файлы подтверждают
сохранение описаний, ID, ссылок, форм, модулей и ресурсов в принятом маршруте.

## Разрешённые и запрещённые правки

Opt-in `real_playground_edit_acceptance` самостоятельно выбирает локальный
общий модуль и объект с настоящим запретом поставщика. Принятая база задаётся
независимым pin, исходники восстанавливаются из неё в новый собственный каталог.

Существующий `Comment` меняется точечным редактором EF-07, в отдельный BSL
добавляется комментарий с сохранением BOM и EOL. Редактор отклоняет правку
запрещённого объекта. Затем его рабочий YAML изменяется напрямую для проверки
обхода редактора: `strict` возвращает отказ до публикации, обычный экспорт
восстанавливает свойство из принятой базы с одной адресной диагностикой.
Рабочие исходники экспорт не исправляет. Прямая контрольная правка native XML
и BSL даёт тот же результат после CF-цикла.

Прогон подготовки реального C1 прошёл за 230,47 с в debug-сборке. Время включает
полное открытие/восстановление базы, две проверки экспорта, копии и проверки
исходников; это не измерение одной production-операции. Замеры вынесены в EF-09.

## Проверки и ограничения

`ibcmd config check` успешно проверил метаданные исходного, преобразованного
и изменённого CF в отдельных новых ИБ. Эти проверки не объявляются полной
проверкой компиляции BSL во всех контекстах Designer `/CheckConfig`.

Workspace MCP bsl-analyzer недоступен. Установленный `bsl-analyzer-app 0.2.86`
использован с явным корнем проекта, `configuration-root = src` и одним изменённым
модулем. `bsl-analyzer.toml` в этих исходниках нет; использованы defaults.
Контекст конфигурации загрузился, подавление по baseline отключено,
анализ не имел failed files.
До и после изменения получены одинаковые 20 диагностик, включая существующие
замечания к типу модуля и неразрешённым вызовам. Новых диагностик нет;
конфигурация в целом не объявляется свободной от ошибок.

Применение к файловой БД не принято: исходный CF и преобразованный CF одинаково
отклоняются платформой при создании слишком длинного составного индекса
(`Index key length exceeds maximum allowed`, exit 102).
Повторная загрузка CF в уже загруженную конфигурацию на поддержке также требует
разблокировать объекты (exit 1); тот же отказ воспроизведён неизменённым исходным
CF. Поддержка не снималась, структура исходной конфигурации не исправлялась.
Обновление существующей ИБ на поддержке, запуск клиента и полная проверка BSL
остаются непроверенными сценариями. Для них нужен отдельный подходящий стенд
и принятый маршрут обновления, а не обход ограничений в конвертере.

Полные fmt/check/strict Clippy/test/Rustdoc и diff-проверки прошли:
283 unit- и 525 integration-тестов, 11 opt-in проверок пропущены обычным запуском.
Реальный opt-in выше запущен отдельно и прошёл.

## Повторяемость

[`scripts/compare_native.py`](scripts/compare_native.py) сравнивает все файлы
и каталоги, проверяет SHA-256 ресурсов и отказывается от symlink/special entries.
`--allow-dump-versions` допускает только наблюдаемые 40-значные hex-атрибуты
профиля `Hierarchical 2.20`, сохраняя сравнение всех остальных байтов.
Изменение ID, потеря ресурса и symlink проверены отдельными отрицательными
сценариями: каждый вызывает отказ. Для пары до/после два ожидаемых пути явно
передаются через `--expect-changed`.

Полные команды, manifests, private source paths, контрольные суммы, журналы
платформы, JSON диагностики и результаты сравнений сохранены в собственном
каталоге playground. Производственные имена, локальные UUID и пути в публичный
отчёт не включены. Результат EF-08 разрешает замеры EF-09 в ограниченном CF-профиле;
он не расширяет покрытие формата на расширения, внешние объекты и обновления.
