# Защищённый экспорт, EF-06

Внутренний `export_protected` принимает рабочий каталог, открытую принятую базу,
отдельный каталог поколений и флаг strict. База повторно проверяется перед
подготовкой и публикацией. Рабочий `source.json` не заменяет принятую композицию.

Восстанавливаются исходные native пути, UUID, kind, Name, состав ссылок
`ChildObjects`, служебные данные, namespaces и непрозрачные части descriptors.
Рабочие owner-файлы могут отсутствовать целиком; каталог может быть пустым.
Принятые members восстанавливаются из базы; разрешённые
[новые EnumValue](enum-value-creation.md) добавляются через права владельца и
закрытый native профиль. Физическое переименование/перенос
owner-файла пока не поддержаны: новый путь исключается, прежний восстанавливается.
Разрешённые правки других владельцев сохраняются.

Для существующих типизированных свойств берётся
рабочее значение при разрешении принятого UUID. Inline-права вычисляются отдельно
от родителя. Подмена рабочего UUID, логического имени, schema/rules/profile или
отображаемого статуса не меняет разрешение. Текущее покрытие включает
[скаляры](typed-scalars.md), [Type](type-description.md) и
[ссылки метаданных](metadata-reference.md). [Порядок существующих детей](child-order.md)
выбирается отдельно при прежнем составе и native class каждой позиции, с проверкой
владельца и всех перемещённых элементов. Запрещённая перестановка восстанавливается,
независимые разрешённые правки сохраняются по UUID.
Неоднозначные повторные части/свойства и некорректные разрешённые значения дают
ошибку, без выбора случайного варианта. Создание/удаление свойств, создание
объектов других профилей, удаление, переименование и перенос пока не разрешены.

BSL и существующие ресурсы выбираются по принятому native владельцу и пути;
заморозка учитывает inline и внешних потомков. Бинарные модули, правила поддержки,
CF поставщиков и файлы без проверенного владельца восстанавливаются из базы.
Исчезнувшие файлы также восстанавливаются. Новые файлы/директории исключаются
явно. Непрозрачный ресурс проверяется целиком; он не превращается в typed form.
Для изменённых XML ресурсов проверяются ограниченный XML envelope и синтаксис.
Смысл выражений, BSL и внутренних ссылок непрозрачных native ресурсов проверяется
своими инструментами/платформой, а не обещается общим XML-парсером.

После объединения проходят полная source-модель и разрешение объявленных связей
descriptor → descriptor. Для неизвестных метаданных внутри YAML сохраняется
принятый непрозрачный фрагмент. Экспорт не разрешает произвольное создание ссылок
в обход этого правила. Проверка текущего покрытия не заявляется статической
проверкой всех возможных ссылок платформы.

Каждая исключённая правка получает стабильные `id`, `code`, native `uuid`,
`path`, schema coordinates, операцию, действие `restored`/`excluded`, native
состояние/причину, ESKA причину и контрольную сумму базы. Схема не зависит от locale.
Strict возвращает `source_changes_excluded` со всем списком до публикации.
Обычный режим возвращает диагностику вместе с восстановленным результатом.
Оба режима оставляют рабочие байты без изменения.

Все распознаваемые виды BSL-модулей имеют тот же статус модуля для расширения
`.bin`, включая модули приложения, сеанса, внешнего соединения и команд.
Изменённые двоичные модули восстанавливаются из принятой базы; strict отказывает
до создания поколения, даже если владелец разрешает правки ресурсов.

Каталог результата содержит `store.json`, а каждое завершённое поколение —
`<SHA-256>/generation.json` и `<SHA-256>/xml`. Снимок связывается с revision всех
рабочих файлов/директорий, принятой базой, версиями schema/rules/profile и hash
полного native результата. Неполный `.preparing-<SHA-256>` не возвращается читателю.
Перед rename проверяются скопированные bytes, весь native состав, рабочий revision
и база. Неудачная подготовка удаляет только собственное незавершённое поколение.

Получатель использует возвращённый путь завершённого поколения. Общий изменяемый
XML-каталог и автоматическое удаление предыдущих результатов отсутствуют.
Повторный экспорт проверяет готовые bytes и ничего не перезаписывает. Внешняя
порча кеша даёт `source_generation_corrupt`; она не становится источником проекта.
Неподходящий существующий каталог и параллельная подготовка того же поколения
дают отдельный отказ. Удаление собственного производного store допускает повторную
генерацию из тех же исходников и базы.

Проверены восстановление пустого/перенесённого дерева, смешанные inline-права,
подмена/повреждение UUID, заморозка, изменение политики, missing CF, strict,
некорректное разрешённое значение и XML ресурс, бинарный модуль, сохранность
чужого каталога, обнаружение изменения между подготовкой и публикацией и чтение
старого поколения во время новой сборки.

Реальная C1: strict-экспорт дал 8 778 файлов и ноль исключений. Все bytes совпали
с полным контрольным экспортом EF-04. Debug-тест открытия базы, подготовки,
публикации и файлового сравнения занял 120,31 с; это не benchmark. Проверка
платформой, адресное редактирование и публичный build остаются последующими этапами.
