# Размер и производительность: EF-09

Решение — продолжить ограниченную интеграцию EF-10. Эксперимент подтвердил
приемлемую стоимость полного преобразования C1 и защиту адресных правок,
но **не подтвердил экономию места или ускорение обычного Git**. Текущая схема
остаётся экспериментальной; автоматическая миграция проектов не вводится.

Замеры выполнены в release на Linux, Rust 1.98.1, system Git 2.56.0,
Git LFS 3.7.1. Сборка binary исключена из времени core API. Page cache не
сбрасывался. Открытие базы измерено отдельно от повторного использования
проверенной модели. [Методика](performance-protocol.md) описывает ограничения;
полные private JSON и входные manifests сохранены в собственном playground.

## Постоянные и производные данные C1

MB в таблицах — 1 000 000 байт. Фактический объём — `st_blocks`, включая
подкаталоги. Каждое дерево посчитано целиком, без исключения поддержки и ресурсов.

| Данные | Файлы | Каталоги | Логический объём, MB | Фактический объём, MB |
|---|---:|---:|---:|---:|
| Исходный XML | 8 778 | 8 077 | 368,713 | 390,222 |
| Детерминированный XML | 8 778 | 8 077 | 368,722 | 390,222 |
| Рабочий ESKA | 7 829 | 8 740 | 403,477 | 421,601 |
| Полная принятая база | 6 682 | 257 | 405,169 | 419,066 |
| Одно завершённое XML-поколение с markers | 8 780 | 8 079 | 368,723 | 390,230 |

Рабочий ESKA больше XML на **9,43%**. Он содержит на 949 файлов меньше,
но на 663 каталога больше. Рабочий источник вместе с необходимой базой занимает
808,646 MB логически. С одним XML-поколением — 1 177,368 MB, **3,19×** исходного
XML. Восстановленный из базы источник добавляет ещё полное рабочее дерево;
он нужен для восстановления, а не является обязательным постоянным кешем.

Отдельный дисковый прогон сохранил первое поколение и подготовил второе
после двух разрешённых правок. Наличие `.preparing-*` наблюдалось при опросе;
рабочие источники не менялись. Пик занятого store — 737,445 MB логически
и 780,456 MB фактически, столько же содержит итоговый store двух поколений
(17 559 файлов, 16 158 каталогов). Вместе с источником и базой — около
1 546,091 MB логически и 1 621,123 MB фактически. Сканирование диска влияет
на время процесса, поэтому его времена не подменяют таблицу core ниже.
Опрос может пропустить короткий промежуточный пик; итоговый полный размер
также включён в максимум. Автоматического удаления старых поколений пока нет.

База хранит исходные байты, поэтому рабочая копия не получает дедупликацию Git.
Производный XML можно пересоздать. Источник и принятая база необходимы после
чистого checkout; ссылку на hash без содержимого эксперимент не считает базой.

после операций через `/proc/self/status`, не задана как гарантированный предел.
Разные режимы выполнялись отдельными процессами; внутри одного режима VmHWM
накапливается. Debug-прогоны EF-04–EF-08 не используются как benchmark.

## Большие стенды: ограниченное чтение и импорт

Оба входа — обычные конфигурации XML 2.20. Импорт выполнен последовательными
release-процессами с `RLIMIT_AS = 4 GiB`: это лимит адресного пространства,
не лимит RSS. Файлы пользователя только читались. Сборка платформой, создание
базы и полный обратный экспорт этих стендов не запускались.

| Стенд | Исходный XML: файлы / MB | ESKA: файлы / MB | Импорт, с | VmHWM, MB |
|---|---:|---:|---:|---:|
| C2 | 95 365 / 6 817,613 | 72 080 / 7 264,786 | 54,079 | 1 344,0 |
| C3 | 111 792 / 8 038,085 | 84 837 / 8 623,269 | 70,696 | 1 704,9 |

Оба импорта прошли с полным файловым manifest и повторной проверкой входных
байтов. Фактический объём ESKA — 7 431,442 MB и 8 821,264 MB соответственно.
Для полного преобразования допустим пакетный процесс, но наблюдаемая память
не подходит как обязательная цена открытия проекта в IDE. EF-10/EF-18 должны
загружать нужные владельцы и факты отдельно от полной принятой базы и ресурсов.
Успешный импорт не объявляется платформенной приёмкой C2/C3.

## Git: одна правка Comment и одна правка BSL

Каждый вариант содержит одинаковые две смысловые правки и два коммита.
ESKA включает полную базу в истории. Во всех вариантах перенос байтов отключает
Git text normalization; отдельно проверен LFS с одинаковой классификацией
двоичных payload. Время status/diff — медиана трёх вызовов, add/commit/pack —
одиночные операции. Существующий gix backend ESKA здесь не измерялся.

| Вариант | Index, MB | Pack, MB | LFS objects, MB | Clean status, мс | Dirty status, мс | Diff, мс | Add / commit, мс |
|---|---:|---:|---:|---:|---:|---:|---:|
| XML | 1,796 | 152,178 | — | 43,19 | 41,94 | 7,77 | 53,77 / 17,90 |
| Детерминированный XML | 1,796 | 152,177 | — | 45,13 | 43,34 | 7,56 | 51,53 / 18,27 |
| ESKA + база | 2,673 | 191,865 | — | 50,73 | 50,73 | 7,97 | 56,87 / 19,90 |
| XML + LFS | 1,796 | 14,613 | 186,609 | 43,65 | 44,49 | 8,13 | 50,96 / 87,34 |
| Детерминированный XML + LFS | 1,796 | 14,613 | 186,609 | 43,94 | 44,70 | 6,84 | 50,62 / 86,61 |
| ESKA + база + LFS | 2,673 | 17,644 | 186,609 | 52,37 | 52,58 | 9,84 | 57,13 / 101,25 |

Pack ESKA с базой больше исходного XML на **26,08%**, index — на **48,88%**.
При LFS общий payload истории, включая локальные LFS objects, составляет
204,253 MB против 201,222 MB XML: рост **1,51%**. Оба варианта LFS хранят
одинаковые 594 уникальных двоичных объекта. Это дедупликация истории,
а не снижение объёма исходного рабочего дерева и базы.

Размер diff — 1 550 байт ESKA против 1 525 XML; маленькая правка остаётся
маленькой в обоих форматах. `gc --aggressive` с одним потоком занял 39,31 с
для ESKA против 54,03 с XML; с LFS — 30,37 против 45,67 с. Это одиночные
синтетические истории: сокращение времени pack не обосновывает общее обещание
ускорения повседневных операций. Status, diff и save такого ускорения не показали.

## Граница VCS до публичного использования

Стандартное `* text=auto` меняет CRLF в extensionless блоках принятой базы.
На реальном BSL-блоке 2 802 байта превратились в 2 731 байт при добавлении
в index. Это нарушает SHA-256 и делает базу непригодной после checkout.
`-text -filter` сохраняет байты; LFS требует классификации блоков по исходным
путям, поскольку расширения у их имён отсутствуют.

В benchmark эта политика задана явно. В продукте её ещё нет: **до публичного
Git/CI-маршрута EF-10/EF-19 обязаны обеспечить byte-preserving transport**
и проверить новый checkout с LFS и без него. Core сохраняет независимость от
Git и отклоняет повреждённую базу. Доступность базы не подменяется наличием
старого XML-кеша.

## Решение и следующие проверки

Продолжаем для проверенного профиля обычной конфигурации: адресное редактирование
и защита поддержки уже проверены платформой, release-преобразование C1 занимает
секунды. Цена полной базы и XML-поколений измерена и должна быть видна в продукте.
Переупаковка базы, кеши и типизированные формы не добавляются ради обещанной
экономии, которой пока нет.

EF-10 подключает формат к discovery и сборке без eager-загрузки всей базы
в IDE. Сборка потребляет только завершённый защищённый результат и проверяет
закреплённые входы. EF-19 повторяет те же операции для фактического gix backend;
результаты system Git не переносятся на него автоматически. Ограничения
CF-профиля EF-08, включая непроверенный клиент и применение к БД, сохраняются.

Полные fmt/check/strict Clippy/test/Rustdoc и diff-проверки прошли:
283 unit- и 525 integration-тестов, 12 opt-in проверок пропущены обычным запуском.
Release-прогоны импорта C1/C2/C3, базы C1, обоих экспортов и двух поколений
выполнены отдельно. Python script проверен синтаксически и завершил все шесть
Git/LFS-сценариев; локальные ссылки документации проверены.
