# Проверенные входы сборки ESKA

`prepare_protected` выполняет тот же защищённый экспорт EF-06 и возвращает
`PreparedSource`. Конструктор находится в materialization core; внешний
потребитель не может создать этот тип из пути, JSON или изменённого отчёта.
Принятая база открывается по отдельно переданному `AcceptedRef`. Подготовка
не приравнивает checksum к аутентификации поставщика.

Тип хранит private binding и полный ожидаемый native inventory. Публичный
`ProtectedExport` остаётся данными представления: его изменение не меняет
проверенный вход. Поколение связывает schema/rules/profile, рабочую ревизию,
принятую базу и native bytes. Изменение рабочих файлов после подготовки не
переписывает этот снимок; следующий запуск заново выбирает входы.

`PreparedSource::validate` проверяет marker и полный XML-состав. Проверяются
байты, дополнительные/пропавшие файлы, пустые каталоги и aliases, включая
symlink в родительском пути. Это проверка всех payloads, а не одного
`Configuration.xml` или только объявленных метаданных.

`build_core::execute_prepared_with_manifest` использует native path только
из `PreparedSource`. Перед подготовкой результата проверяется поколение;
затем создаётся частный снимок и проверяются именно скопированные байты.
Повторная проверка поколения закрывает изменение cache во время копирования.
Только после этого открывается managed infobase и запускается платформа.
При ошибке рабочий или старый XML не используется как fallback.

Проверенный снимок сохраняет каждый native payload, даже с именем `.git`:
такой путь в materialization не означает repository. Обычный Designer build
сохраняет прежнее исключение Git-служебных данных. Нативный профиль этой точки
входа ограничен обычной конфигурацией; расширения и внешние объекты требуют EF-14.

## Manifest

Прежний Designer build пишет artifact manifest schema 1 без нового поля.
Новая подготовленная сборка пишет schema 2 с дополнительным
`source.protected`:

| Поле | Фактически собранный контекст |
|---|---|
| `source_schema_version` | Версия исходной модели ESKA |
| `rules_version` | Версия правил преобразования и защиты |
| `profile` | Native профиль |
| `generation` | Поколение защищённого экспорта |
| `input_revision` | Полный рабочий вход до выбора разрешённых частей |
| `baseline` | Закреплённая принятая база |
| `native_revision` | Полный native inventory проверенного снимка |
| `source_map_checksum` | SHA-256 карты фактически собранных входов |

SHA-256 артефакта, версия из snapshot descriptor, snapshot id, платформа
и переданный Git provenance также записываются. Полная [карта файлов](source-map.md)
находится в `source.source_map`; она различает выбранные bytes рабочих и принятых
payloads и составное происхождение metadata XML.

## Проверки и текущие границы

Прошли полный набор fmt/check/strict Clippy/test/Rustdoc/diff check и отдельно
минимальные source/build сборки. Приложение: 332 unit и 529 integration;
source core: 138 unit; build core: 154 unit. Пропущены 14 opt-in тестов
в приложении и три в каждом изолированном ядре.

Проверены изменение отчёта, marker и XML, подмена payload ссылкой, ancestor
alias, изменение/потеря/добавление ресурса, потеря пустого каталога, сохранение
старой prepared revision, полная копия `.git` payload, schema 1/2 и обе
локали ошибки `source-verification`. Синтетический CF sentinel используется
только для проверки сохранности, не для подтверждения валидности CF платформой.

Независимый consumer с минимальным build feature выполнил полный маршрут
C1: исходники ESKA → закреплённая база → protected generation → проверенный
build snapshot → CF на 1С 8.3.27.2325. CF содержит 200 418 047 байт;
SHA-256 совпадает с manifest. Все поля `source.protected` совпали с marker,
generation id независимо пересчитан из binding, base pin проверен отдельно.
Через установленный `eska new --from` CF повторно выгружен в новый собственный
каталог. С контрольным исходным циклом совпали 8 769 файлов и 8 064 каталога;
изменились только 7 011 `configVersion` в ConfigDumpInfo, все остальные байты
совпали. Сравнение выполнил строгий comparator EF-08. Пять предупреждений
платформы относятся к ссылкам справки. Применение к рабочей БД, клиент и
полный Designer CheckConfig в этой проверке не запускались.

Это экспериментальный Rust API; [конфигурация ESKA](project-selection.md) уже
выбирает source и путь базы; [самостоятельный project CLI](project-cli.md)
подготавливает такое поколение. [Сборочный бинарник](build-cli.md) повторяет
protected prepare и проверяет собственный snapshot до платформы.
[Координаты](source-locations.md) уже вычисляются
по конкретным native/YAML bytes; [адреса платформы](platform-locations.md)
поступают с origins проверенного snapshot при успехе и отказе. Наблюдённые
сообщения XDTO не содержат строки/колонки.
[Byte-preserving transport](git-transport.md) также готов.
Проверки не дают файловой системе CAS-гарантию против внешней записи в частный
снимок после последней проверки; рабочее редактирование не получает его путь.
