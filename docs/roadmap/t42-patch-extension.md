# T42 — спецификация и feasibility patch-extension

Дата проверки: 2026-09-06. Платформа: **8.3.27.2325**, Designer XML 2.20,
Linux, существующий Distrobox runner. Других установленных версий в этом
окружении нет. Выводы не распространяются автоматически на 8.5 или другие ОС.

## Результат и границы

На синтетической конфигурации доказан путь от изменения одного метода в Git
до работающего `.cfe`: заимствованный серверный общий модуль, неизменная
сигнатура, тело `Return 1` заменяется на `Return 2`. Расширение имеет purpose
`Patch`; новый UUID объекта расширения ссылается на UUID объекта основной
конфигурации через `ExtendedConfigurationObject`.

**T42 завершает исследование и спецификацию, а не добавляет production-команду.**
Полная сборка `eska build` сохраняет прежний контракт. Генерация patch-extension
для произвольной конфигурации пока не поддерживается. Имя новой команды и её
публичная схема не утверждены; описанные ниже требования относятся к будущей
реализации. `.cfu` в этот scope не входит.

Ключевой вывод: одного `ibcmd` достаточно для импорта/сохранения этого примера,
но недостаточно для доказательства правильности BSL и выполнения патча.
В прототипе потребовались пакетный Конфигуратор и запуск клиента 1С.

## Воспроизводимый эксперимент

Скрипт [examples/t42_patch_extension.py](../../examples/t42_patch_extension.py)
использует только стандартную библиотеку Python и явно выбранные `ibcmd`,
`1cv8`, Git. Python — инструмент эксперимента, не новая зависимость продукта.
Для пакетного клиента в проверенном Linux-окружении требуется доступный display
и работоспособная установленная платформа. Скрипт создаёт только собственный
уникальный каталог в `<repo>/../eska-playground`; существующие demo не читает
и не изменяет. Каталог сохраняется для изучения evidence, включая базы.

Из корня репозитория, с путями к установленной платформе:

```sh
python3 examples/t42_patch_extension.py \
  --ibcmd "$T42_IBCMD" \
  --client "$T42_CLIENT" \
  --distrobox "$T42_CONTAINER"
```

Для прямого запуска параметр `--distrobox` опускается. Скрипт проверяет версию
`ibcmd`; переданные `ibcmd` и `1cv8` должны относиться к одной установке
8.3.27.2325. Другие версии скрипт намеренно не принимает.

Синтетическая база содержит общий модуль `PatchProbe` и неизменный модуль
приложения, записывающий результат вызова в файл и завершающий клиент.
В отдельном Git repository создаются два commit: базовая версия и изменение
только `CommonModules/PatchProbe/Ext/Module.bsl`. Тело патча читается из blob
второго commit. Git здесь служит fixture эксперимента, а не новым VCS backend
`eska`. Скрипт принимает только эту точную delta и не является BSL-конвертером.

Последовательность проверки:

1. `infobase create`, выгрузка пустой базы, добавление синтетических исходников,
   `config import`, `config apply`. Клиент возвращает `1`.
2. `extension create --purpose=patch`, выгрузка заготовки расширения.
   Добавляются `ObjectBelonging=Adopted`, отдельный UUID и ссылка на UUID
   базового модуля. Исходники записываются с UTF-8 BOM и CRLF.
3. Отрицательный контроль: заведомо неверная аннотация `&Instead` проходит
   `config import` и `config check` (оба exit 0), но пакетный
   `/CheckConfig -Server -ExternalConnection -Extension EskaPatch`
   возвращает 101 с `Unknown annotation (Instead)`.
4. Правильная английская аннотация — `&Around("Value")`. Метод расширения
   `EskaPatch_Value` содержит тело из HEAD и не вызывает `ContinueCall`.
   Импорт, проверка, применение и пакетная проверка BSL проходят.
5. `config save --extension=EskaPatch` создаёт промежуточный `candidate.cfe`.
   Он загружается и применяется в другой новой базе с базовыми исходниками.
6. `/CheckCanApplyConfigurationExtensions` проходит. При default safe mode
   клиент завершается с exit 0, но возвращает **1**. В исследовательском
   запуске журнал зафиксировал `Session. Cannot apply configuration extension`:
   расширение модуля нельзя применить в safe mode.
7. Только в синтетической базе отключается safe mode расширения: результат
   становится **2**. Отключение активности патча возвращает **1**; повторное
   включение — **2**. Защита от опасных действий не отключается скриптом.
8. Обратная выгрузка проверяет `Adopted`, UUID-связь и текст метода. Загрузка
   того же `.cfe` в пустую базу проходит, `config check` также возвращает 0,
   но `config apply` возвращает 1: `Object not found: CommonModule.PatchProbe`.
9. Только после всех проверок `candidate.cfe` становится `patch.cfe` и
   записывается `result.json`.

В каталоге результата находятся `commands.json` с точными argv и exit codes,
stdout/stderr каждого шага, результаты пакетных проверок, отдельные `.value`
для запусков клиента, два Git commit и выгрузка `roundtrip`. Последовательность
runtime-значений должна быть **1, 1, 2, 1, 2**. Размер и хеш бинарного `.cfe`
не являются golden-контрактом: заготовку с UUID создаёт платформа.

Контрольный запуск 2026-09-06 завершил все 45 шагов в собственном каталоге
`t42-feasibility-6aajphbw` соседнего playground; `.cfe` имеет размер 5335 байт.
Базовый commit fixture — `08b66b7626dd32f1d281603c07d8a36cb738cd12`,
HEAD — `6632a4623547d6468210456477a67150629e1409`. Это commits тестового
repository, не история `eska`. `cargo fmt --check`, `cargo check`, строгий
Clippy и полный `cargo test` с `ESKA_TEST_ROOT` прошли: 116 unit-тестов и
158 integration-тестов, без ошибок.

## Матрица поддержки будущей первой версии

«Кандидат» означает только доказанную возможность для fixture; это не обещание
поддержки произвольного пользовательского исходника. Пока production-генератора
нет, ни одна строка не является доступной возможностью CLI.

| Изменение | Решение для первой реализации | Причина / необходимая проверка |
|---|---|---|
| Тело существующего метода общего модуля, сигнатура и свойства неизменны | Кандидат с узким allowlist | Пример с константой доказан; нужны точный разбор BSL, проверки и runtime acceptance |
| Новый метод, удаление или переименование метода | Отклонять | Нужно определить новые имена, ссылки, семантику старых вызовов |
| Изменение параметров, `Export`, директив компиляции, аннотаций | Отклонять | Не доказана совместимость вызовов и контекстов |
| Код вне методов, переменные модуля, условная компиляция, неполный разбор | Отклонять | Нельзя молча потерять часть изменения |
| Ссылки на новые методы/объекты, неоднозначные зависимости, рекурсия | Отклонять до отдельной проверки | Замена декларации не доказывает сохранение разрешения имён |
| Добавление, удаление, переименование объекта или смена UUID | Отклонять | Нужна отдельная семантика заимствования/владения и ссылок |
| Изменение свойств общего модуля | Отклонять | Меняет контексты, права или кэширование вызовов |
| Формы, модули объектов/менеджеров, макеты, команды | Отклонять | Прототип эти виды не покрывает |
| Реквизиты, табличные части, измерения, ресурсы и другие изменения структуры | Отклонять | Нет доказанной семантики миграции данных и расширения структуры |
| Корневые свойства конфигурации, включая совместимость и версию | Отклонять | Они не эквивалентны свойствам расширения |
| Неизвестные исходники, opaque binary, неполная ownership-модель | Отклонять | Нельзя публиковать частично применённую delta |
| Только несемантические различия | Без артефакта после доказанной классификации | Нельзя объявлять произвольные отличия форматированием |
| Пустая delta | Без артефакта | Нет исправления для поставки |

Неподдерживаемое изменение отклоняет **всю** сборку до публикации, даже если
остальные методы поддерживаются. `--force` не должен обходить эту матрицу.
Исходники уже готового extension project остаются задачей обычного `eska build`.

## Контракт Git и входных данных

- Только configuration project с Designer XML. Базовое направление берётся
  из разрешённого `workflow.integration_target`; явный `--base <revision>`
  заменяет это направление. В обоих случаях сравнение —
  `merge-base(base, HEAD)..HEAD`, а не diff до текущей вершины base.
- Все refs однократно разрешаются в commit IDs. Нет fetch, угадывания remote,
  переключения ветки, изменения index или создания worktree в проекте.
  Нет общей базы, недоступные объекты истории или несколько лучших merge-base
  означают отказ. Произвольно выбирать одну из нескольких баз нельзя.
- Preview фиксирует requested base, resolved base, merge-base и HEAD.
  Базовые исходники для заимствования читаются именно из merge-base, изменённые
  — из HEAD. Вершина integration branch может уже отличаться: применимость
  к ней и к любой установленной версии отдельно не доказана.
- Первая реализация требует чистую рабочую копию целиком, включая index и
  untracked, и предлагает `eska save` при изменениях. Даже после preflight
  исходники для сборки берутся из зафиксированных Git blobs, а не из worktree.
- Версия платформы и относительный source root фиксируются в плане. Смена
  project type/source root между концами сравнения отклоняется. Исходники из
  submodules, symlinks, LFS pointers и недостающие blobs не подменяются файлами
  с машины и не скачиваются автоматически.
- План содержит все changed paths и причину решения для каждого. Нельзя
  фильтровать неподдерживаемые изменения и объявлять оставшийся патч полным.
  Различия вне исходников должны классифицироваться явно: build/config settings
  влияют на план, неизвестные влияющие на сборку данные блокируют результат.

## Архитектурные границы

Переиспользуются `src/vcs/diff.rs` (refs, commit trees, blobs),
`src/project/diff.rs` и `src/project/semantic.rs` (сравнение committed snapshots),
build settings/tool discovery из `src/project/build/`. Текущий
`merge_base_commit` возвращает одну базу: для нового строгого контракта нужна
отдельная проверка неоднозначности. Чтение полного базового дерева нужно для
временной базы, но не должно превращаться в полный parse каждого вызова diff.

Semantic events T21 — материал для preview, **не программа преобразования**.
Текущий `parse_routines` выделяет тела по строкам и пропускает текст вне методов;
его достаточно для сводки, но нельзя использовать как доказательство полноты
при генерации BSL. Нужен отдельно ограниченный и проверяемый разбор либо зрелый
парсер после оценки зависимости. Новый parser/crate в рамках T42 не добавлен.

План patch-extension должен быть отдельным от `BuildPlan` полной сборки:
заимствование, преобразование методов и проверка применимости имеют другой
контракт. Можно переиспользовать запуск процессов и безопасную публикацию,
не добавляя режим «переименовать `.cf` в `.cfe`». Python-прототип в core не
включается. Существующий JSON build schema v1 не меняется.

## Проверки и публикация будущего артефакта

До создания итогового файла: структурированный preview и полный support gate;
временная база из merge-base; импорт расширения; проверка метаданных; проверка
BSL во всех допущенных контекстах; проверка применимости; сохранение во временный
файл; установка в отдельную базу; acceptance поддерживаемого сценария.
Все базы принадлежат текущей сборке; пользовательская development/production
база не используется как временная среда.

`ibcmd config check`, `config apply` и `/CheckCanApplyConfigurationExtensions`
решают разные задачи. Ни один из них сам по себе не подтверждает выполнение
нового кода. Ошибки загрузки расширения могут сопровождаться exit 0 клиента.
Поэтому контракт проверки должен фиксировать наблюдаемый результат, а не только
успех процессов. Для реальной задачи ожидаемое поведение нельзя автоматически
вывести из Git diff — требуется явная стратегия acceptance.

Safe mode — настройка подключения в конкретной базе. Успешно сохранённый `.cfe`
не означает, что получатель сможет применить его с настройками по умолчанию.
Продукт не должен молча менять эти настройки. Прототип отключает safe mode
только у собственного синтетического расширения; этот шаг нельзя переносить
в пользовательскую базу как скрытый побочный эффект сборки.

Существующий итоговый артефакт сохраняется при любой ошибке; неподдерживаемые
изменения не создают результата. Публикация — после всех обязательных проверок,
по принципу существующего build subsystem. Временные данные production-сборки
очищаются при успехе, ошибке и прерывании; режим сохранения evidence, если нужен,
требует явного контракта. Сосуществование с другими расширениями, иные версии
базовой конфигурации, производственные данные и подпись патча не проверены.

## Решение перед production-реализацией

Рекомендуемый следующий scope — согласовать узкий allowlist методов общего
модуля и обязательную проверку BSL/acceptance. Нужно решить, допустим ли
пакетный `1cv8` как проверяющий инструмент рядом с `ibcmd`; чисто `ibcmd`-путь
на проверенной версии не обеспечивает продемонстрированных проверок.
Только после этого выбирать CLI и реализовывать отдельную команду. Без этих
решений нельзя честно заявить безопасную автоматическую генерацию патча из
произвольной разницы веток.

## Источники evidence

Основной источник — встроенные `ibcmd help config` / `help extension` и
результаты запуска **конкретной** установленной версии, сохраняемые прототипом.
Веб-поиск официальных материалов 1С выполнен 2026-09-06: выдача 1Ci содержит
описания `Around` и пакетных проверок; открытие страниц перенаправляет на
support portal, ИТС возвращает 403. Непрочитанные веб-страницы не используются
как доказательство поддержки. Синтаксис и ограничения выше подтверждены
локальными положительными и отрицательными проверками.
