# Эксперименты с форматом исходников ESKA

План отдельного экспериментального направления от 2026-10-08. Проверяем маршрут
Designer XML → типизированный YAML, BSL и ресурсы → Designer XML → существующая
сборка платформой. Цель — удобные исходники, локальные изменения и соблюдение
поддержки при экспорте. Экономию места и ускорение Git нужно доказать измерениями.

Рабочая ветка: `codex/eska-format-experiments`, создана от `main` на
`b5218a4627f7056460136e19aef357d0dcf841b1`. Текущий продукт поддерживает только
Designer XML. Этот план описывает будущую работу и не вводит новый публичный
формат, команды или обязательную миграцию существующих проектов.

[Границы инструментов](../tool-boundaries.md) определены до реализации:
общая модель проекта; отдельные project/build/VCS-инструменты; общее ядро
анализа с IDE- и пакетной точками входа; будущий самостоятельный DAP-отладчик.
Имена пакетов пока рабочие. Выбор основы анализа — EF-17, выделение его точек
входа — EF-18, самостоятельный VCS — EF-19.

Принятая модель поставки: обычная установка `eska` даёт комплект согласованных
инструментов и небольшую оболочку; выборочная установка позволяет запускать
нужные `eska-*` напрямую. Сквозные команды и создание из CF выделены в EF-20,
полная/выборочная установка — в EF-21. Это будущая поставка, текущий установщик
и release pipeline не менялись.

Настраиваемый форматтер ведётся в существующей [T26](08-quality.md), без второй
реализации в этой очереди. BSL можно форматировать и в Designer XML-проекте;
новый source format не является условием появления CLI. Интеграция в новый
IDE-host зависит от EF-18, оформление YAML — от EF-02/EF-07. Форматтер не входит
в обязательные условия первого пилота EF-16.

Релизы проекта ведутся в [T83/T84/T56/T32](10-delivery-and-integrations.md):
схемы `x.y.z`/`x.y.z.build`, обязательная неэкспортная `Версия()` для внешних
объектов, план версии и отдельный `eska-release`. Designer XML остаётся первым
потребителем. Интеграция с ESKA требует EF-10, внешние объекты — также EF-14;
готовый релизный инструмент не является условием пилота EF-16. EF-22 отвечает
за подключение готовых форматтера и релизного процесса к ESKA, включая адаптер
версии, без повторной реализации задач T26/T83/T84/T56/T32.

Задачи `EF` образуют отдельную очередь. Сейчас **EF-10** — `IN-PROGRESS`. Очередь остальных
направлений в [общем трекере](README.md) сохраняется. Каждый следующий этап
начинается после проверки результата предыдущего; список не означает запуск
всех задач одновременно. Общие правила — в [working-agreement.md](working-agreement.md).

## Основание и границы

Исследование реальных выгрузок в соседнем playground дало инвентаризацию,
ограниченные прототипы и один платформенный цикл преобразованной формы.
Проверены 90 слияний трёх форм и девять сценариев защиты одного описателя.
Полный типизированный конвертер, общая композиция поддержки и ускорение Git
новым форматом ещё не подтверждены.

В двух больших конфигурациях описатели метаданных и управляемые
формы занимают 7,54% и 7,71% исходников. Механическое представление XML-дерева
в YAML увеличило размеры выбранных форм. Поэтому размеры YAML-файлов отдельно
от ресурсов, принятой базы, XML-материализации и Git не являются критерием успеха.

Первый результат — полный файловый цикл небольшой конфигурации с явно
ограниченным набором редактируемых типизированных свойств. Остальные данные,
включая формы, сохраняются без интерпретации либо вызывают конкретный отказ.
Сохранение всего проекта не означает поддержку редактирования всех его частей.

Принимаемые для эксперимента правила:

- один YAML на основной объект; вложенные реквизиты, табличные части и описания
  команд находятся у владельца; BSL и крупные ресурсы остаются отдельными файлами;
- состав проекта и смысловой порядок задаются явно, а индекс файлов производный;
- родные UUID и служебные ID сохраняются; identity хранения отделяется от
  изменяемого при переименовании `ObjectId` существующего API;
- неизвестное содержимое имеет правило восстановления и ограничения правок;
- принятая база, правила поставщика, дополнительная заморозка ESKA и защита
  редактора — отдельные сущности; рабочий YAML не выдаёт сам себе разрешения;
- экспорт не исправляет рабочие исходники; XML создаётся как производный результат;
- чтение и преобразование не требуют EDT; приёмка сборки требует платформы 1С.

## EF-01 Покрытие и набор приёмки

Зафиксировать XML-профиль, классы объектов и свойства, которые первая версия
читает и изменяет типизированно. Для каждой остальной конструкции выбрать
сохранение без интерпретации или отказ. Использовать готовую инвентаризацию
исследования; переносить в репозиторий только небольшие обезличенные примеры.
Различать чтение, обратное сохранение, изменение свойства и структурные операции:
поддержка импорта типа не означает готовность его создания, удаления или rename.

**Готово, когда:** есть карта XML → ESKA → XML с порядком, identity и уровнем
покрытия; сохранены исходные hashes и параметры запуска. Набор включает небольшую
конфигурацию, вложенные объекты, смешанную поддержку, локальные namespaces,
двоичные ресурсы и файлы вне объявленного состава. Большие конфигурации остаются
стендом чтения и измерений. Результаты, схемы и сценарии собираются в
`docs/research/eska-format/`. Требования REQ/FMT/SUP/ID/FORM/TEXT/PERF связываются
с проверками и непокрытыми случаями.

**Результат:** [покрытие и воспроизводимые сценарии](../research/eska-format/README.md)
зафиксированы; 48 требований связаны с конкретными этапами/проверками.
Обезличенный корпус содержит девять файлов и manifest SHA-256. Повторная
инвентаризация пяти реальных корней прочитала 216 050 файлов без XML-ошибок;
полные входные hashes и команды остаются в собственном каталоге playground.
Платформа 8.3.27.2325 обнаружена через ESKA. BSL fixture проверен установленным
bsl-analyzer 0.2.86: один файл, ноль диагностик. Сборка конвертера ещё не выполнялась.

## EF-02 Схема и обратимая модель

Определить профиль YAML, версии формата и правил преобразования, структуру
`configuration.yaml` и `object.yaml`. Отделить полный исходный документ от
семантической проекции существующего `metadata_model`.

Модель и правила формата не зависят от LSP, DAP, Git, runner платформы или
конкретного query engine. Для анализа определить типизированные факты,
владельца BSL-модуля, source locations и входную ревизию. Чтение из XML/YAML
даёт общую проекцию без второй независимой схемы метаданных.

**Готово, когда:** схема различает отсутствие, пустое значение, `null` и
наследование; сохраняет точные числа, строки, порядок, UUID, generated IDs и
контекст QName. Есть правила сохранения неизвестных узлов и служебных данных.
Дубликаты ключей и неподдержанные конструкции YAML отклоняются. Повторный импорт
не меняет identity; неоднозначные соответствия дают ошибку. Дополнительные ID
ESKA вводятся только для подтверждённой потребности. Синтаксис проверен на
реальных примерах, версия остаётся экспериментальной.

Версия формата, версия правил преобразования, версия инструментов и версия
проекта 1С — разные значения. Последняя сохраняется как точная строка даже при
отсутствии подходящей стратегии bump; автоматические изменения номера следуют
T83/T84. Для каждой версии схемы фиксируются значения по умолчанию и профиль
платформы. Неподдержанная версия схемы отвергается до записи, открытие проекта не
мигрирует исходники молча. До стабильной схемы допускается явный отказ с
описанным маршрутом через совместимую версию инструмента и Designer XML.

**Результат 2026-10-08:** реализован внутренний `project::source_format`: полный
descriptor, typed свойства, ordered sections/children, native UUID и opaque XML
с наследованием namespace. [Схема и ограничения](../research/eska-format/schema.md)
разделяют отсутствие, empty, nil и неизвестные/default значения без вывода
новых defaults. YAML проверяется через CST, дубликаты и неподдержанная версия
отклоняются. 13 новых тестов проверяют точные значения, контекст, identity и
публичный пример. Полный набор: 279 unit и 479 integration прошли, 6 прежних
тестов ignored; fmt/check/strict Clippy/Rustdoc прошли. Один существующий тест
обновления CLI сначала получил `Text file busy`, затем прошёл отдельно и в полном
наборе. Импорт/проекция целого проекта и native round trip ещё не реализованы.

## EF-03 Импорт Designer XML

Реализовать импорт выбранного покрытия в отдельный новый каталог. Состав брать
из корневых и вложенных деклараций. Файлы вне состава учитывать отдельно.
BSL и ресурсы копировать с сохранением байтов и относительных связей.

**Готово, когда:** результат имеет полный manifest входных файлов и правила
восстановления; нет молчаливых пропусков или включения лишних объектов. Неизвестный
профиль, опасный путь, коллизия имён и неоднозначный UUID диагностируются.
Исходная выгрузка неизменна. Повторный импорт того же входа даёт те же данные.
Импорт всегда отличает исходники от производного XML: только один выбранный
формат является редактируемым источником проекта. Обновление существующего
ESKA-каталога и принятие новой защищённой базы не входят в этот первичный импорт.

**Результат 2026-10-08:** [импорт](../research/eska-format/import.md) реализован
как внутреннее core API. Declared composition определяет основные и nested
descriptors; manifest учитывает все файлы и empty directories. Ресурсы/BSL
сохраняются побайтово, опасные пути и неоднозначность отклоняются до записи.
На C1 преобразованы 3 595 descriptors в 2 645 YAML, учтены все 8 778 файлов;
hashes совпали с EF-01. Два импорта дали одинаковые пути/байты всех 7 829 файлов
результата; все 2 645 YAML прочитаны строгим Rust reader. 11 новых обычных
integration-тестов прошли; real-corpus тест opt-in и выполнен отдельно.
Полный набор: 279 unit и 490 integration прошли, 7 тестов ignored;
fmt/check/strict Clippy/Rustdoc и проверки локальных ссылок/schema прошли.
Native round trip остаётся EF-08. Предварительный размер вырос на 9,43%;
это вход EF-09, не доказательство пользы формата.

## EF-04 Обратный экспорт и повторяемость

Восстановить Designer XML из модели EF-03. Внутренний writer этого этапа
используется для приёмочных копий; пользовательский build подключается после EF-06.
Отдельно определить допустимые лексические отличия XML и точное сохранение
непрозрачных ресурсов.

**Готово, когда:** состав, identity, ссылки, порядок и namespace-контекст
проверяются автоматически; бинарные данные и BSL совпадают побайтово.
Экспорт без правок не теряет файлы. Повторный экспорт не меняет байты и mtime
готового результата; удаление производного кеша не меняет итог.
Необъяснённая разница останавливает эксперимент.

**Результат 2026-10-08:** реализован [native writer и полный экспорт](../research/eska-format/export.md)
из ESKA-модели. До записи проверяются current composition, файловый map,
identity и generated XML. Существующее несовпадающее назначение сохраняется.
На C1 восстановлены все 8 778 файлов; полные модели 3 595 активных descriptors
совпали с оригиналом, остальные файлы совпали побайтово. Повторный экспорт
сохранил mtime всех 8 778 файлов. Полный набор: 279 unit и 496 integration
прошли, 8 тестов ignored; два запуска real export выполнены отдельно.
fmt/check/strict Clippy/Rustdoc, schema/example/local links и diff check прошли.
Схема уточнена: `text` непустой, пустое значение задаётся через `empty`.
Writer пока экспериментальный и не выдаёт права поддержки; публичный build
подключается после EF-06. CF/платформенный цикл остаётся EF-08.

## EF-05 Принятая база и разрешения

Переиспользовать действующий читатель нативной поддержки. Определить состав
принятой базы, хранение и восстановление закреплённых байтов, проверку целостности
и отдельную операцию принятия. Сохранить согласованный комплект правил и поставок.
Формат физического хранения выбрать по корректности и полной стоимости.

**Готово, когда:** разрешения вычисляются для объекта, вложенной части и операции;
учтены несколько поставщиков, неизвестное состояние и дополнительная заморозка
редактируемого объекта. Правка отображаемого статуса, переключателя Explorer
или рабочего UUID не меняет принятую политику. Отсутствующая, повреждённая или
несогласованная база даёт конкретный отказ. Для CI определён источник принятой
политики, независимый от произвольных изменений рабочего YAML.
Проверены получение самих закреплённых данных на чистом рабочем месте и работа
после удаления восстанавливаемых кешей. Ссылка или hash без доступного содержимого
не считаются базой. Первичное принятие фиксирует источник и проверенное состояние;
оно не обещает доказательство подлинности поставщика по одной контрольной сумме.

**Факт:** [принятая база](../research/eska-format/baseline.md) сохраняет полный
ESKA-снимок в блоках SHA-256, требует отдельную доверенную ссылку и проверяет
состав/identity при открытии. Повторно используется native reader; обязательные
CF каждого поставщика и правила сверяются с исходным импортом. Пересечение прав,
inline/external ancestry, заморозка и отказы при повреждении проверены тестами.
Реальная C1: восстановлены побайтово все 7 829 ESKA-файлов, включая правила и
134 388 317 байт CF двух поставщиков. Debug-проверка принятия/открытия/восстановления
заняла 151,48 с; это не benchmark. Полные fmt/check/strict Clippy/tests/Rustdoc
успешны: 279 unit и 504 integration, 9 ignored суммарно; реальный baseline-test
выполнен отдельно. Платформенная проверка внутренних данных CF остаётся EF-08.

## EF-06 Защищённый экспорт

Объединять рабочую модель с полным составом принятой базы. Восстанавливать
запрещённые части, применять разрешённые изменения и проверять получившиеся
ссылки. Только после проверки публиковать завершённое поколение XML.

**Готово, когда:** в пустой каталог восстанавливаются удалённые защищённые объекты
и части; проверены ручная правка, физическое и логическое переименование,
перемещение, подмена UUID, удаление родителя и смешанные ограничения. Разрешённые
правки сохраняются. Невалидная ссылка после восстановления даёт ошибку.
Есть устойчивые коды, identity, причина, база и действие; строгий режим считает
исключённую правку ошибкой. Исходники не меняются, предыдущий корректный экспорт
сохраняется при сбое или конкурентном чтении.
Поколение связывается с неизменяемым снимком входов, принятой базой и версиями
правил. Изменение входов во время подготовки обнаруживается до публикации;
нельзя собрать каталог из файлов разных ревизий и объявить его одним снимком.

**Факт:** [защищённый экспорт](../research/eska-format/protected-export.md)
восстанавливает принятый состав и identities, сохраняет разрешённые typed/BSL/
resource правки, возвращает объяснения исключений и strict-отказ.
Завершённые поколения добавляются отдельно; ошибочная подготовка и конкурентное
чтение сохраняют прежний результат. Изменение после подготовки обнаружено тестом;
порча XML-кеша, неоднозначная identity и неподходящий store дают отказ.
Восстановление/проверка ссылок покрывает объявленную композицию descriptors;
смысл внутренних native ресурсов проверяется платформой, не XML-парсером.
Реальная C1: 8 778 файлов совпали побайтово с EF-04, strict дал ноль исключений.
Debug-тест занял 120,31 с. Полные проверки успешны: 280 unit, 515 integration,
10 ignored суммарно; real-test выполнен отдельно. Public build остаётся EF-10.

## EF-07 Адресное редактирование YAML

Проверить CST-парсер на выбранной схеме и реализовать изменение существующего
свойства без полной пересериализации документа. Отдельные BSL остаются обычными
исходными файлами. Форматтер всего проекта в этот этап не входит.

**Готово, когда:** сохраняются комментарии, кавычки, LF/CRLF и незатронутые байты;
определена и проверена политика BOM. Внешнее изменение файла между чтением и
записью обнаруживается. Сохранение без правок не создаёт diff. Изменение одного
свойства и одного модуля затрагивает только ожидаемые участки; экспорт применяет
правила EF-06. Новая библиотека выбирается после проверки текущей версии и границ.
Для непокрытых структурных операций возвращается явный отказ или диагностика;
готовность точечной правки свойства не объявляется поддержкой всех операций.

**Результат EF-07:** добавлены план и публикация правки существующего свойства
через CST, привязанные к принятому владельцу и UUID. Сохранены комментарии,
кавычки, LF/CRLF и незатронутые байты; no-op не перезаписывает файл. Проверены
переходы text/empty/nil, существующие переводы, вложенный descriptor, запрет
поставщика, заморозка, внешняя запись, смена/повреждение базы, BOM, read-only
и symlink. Правка descriptor и BSL меняет ровно два native файла в защищённом
экспорте. Три unit- и десять integration-проверок прошли. Границы и отказы
описаны в [edit.md](../research/eska-format/edit.md); полного форматтера,
структурного редактора и публичной команды пока нет.
Полные fmt/check/strict Clippy/test/Rustdoc и diff-проверка прошли:
283 unit- и 525 integration-тестов, 10 opt-in тестов пропущены.

## EF-08 Проверка платформой

На собственной копии небольшой реальной конфигурации выполнить контрольный
маршрут исходного XML и маршрут через ESKA: build → новая ИБ → повторная выгрузка.
Повторить после разрешённой правки свойства и BSL, а также попытки запрещённой
правки. Сборку и выгрузку выполнять через ESKA.

**Готово, когда:** сравнение включает состав, ID, связи, ресурсы и нативную
поддержку; каждое допустимое отличие подтверждено отдельным контролем.
Версия платформы и compatibility mode зафиксированы. Нужные режимы проверки
конфигурации и интерактивные проверки отмечены отдельно от успешной сборки CF.
Применение к существующей ИБ на поддержке принимается на отдельной одноразовой
копии; недоступный сценарий явно ограничивает покрытие.

**Результат EF-08:** приняты независимые CF-циклы C1 на 8.3.27.2325,
compatibility `Version8_3_21`, без правок и после разрешённой правки Comment/BSL
с восстановлением запрещённой правки. Обе повторные выгрузки имеют 8 769 файлов
и 8 064 каталога; после правок отличаются ровно два ожидаемых native файла.
Различаются только configVersion в ConfigDumpInfo — это воспроизведено повтором
того же исходного XML; все остальные байты, ID и поддержка с CF поставщиков
совпадают. Нативная проверка метаданных проходит, scoped BSL-анализ сохраняет
прежние 20 диагностик без новых. Применение к файловой БД не принято из-за
лимита индекса в самом исходном C1; повторная загрузка CF на поддержку нативно
блокируется даже без изменений. Клиент и полный Designer CheckConfig не проверены.
Подробности и границы — [ef-08-results.md](../research/eska-format/ef-08-results.md).
Полные проверки прошли: 283 unit/525 integration, 11 opt-in пропущены;
подготовка реального C1 запущена отдельно и прошла за 230,47 с в debug.

## EF-09 Размер и производительность

Сравнить исходный XML, XML с устойчивой сериализацией и типизированный ESKA на
одинаковых проектах и одинаковой последовательности смысловых изменений.
Использовать готовые исходные замеры как контроль, не как результат нового writer.

**Готово, когда:** измерены файлы и каталоги, логический и фактический объём,
Git index/pack/LFS и история, база, кеш, материализованный XML и временный пик.
Есть время и память импорта, экспорта, повторного экспорта; clean/dirty status,
diff, save и повторения с одинаковыми настройками. Чтение больших стендов
ограничено памятью; их сборка не запускается. Отдельно указано влияние состояния
кеша. Зафиксировано решение: продолжить интеграцию, изменить схему или остановить
эксперимент, с измеренными преимуществами и ценой.
Измерения системного Git и путей ESKA/gix разделены. До интеграции результаты
обычного Git не выдаются за ускорение команд ESKA; после EF-19 их замеры
повторяются для фактического backend на той же последовательности изменений.

**Результат EF-09:** принято продолжение ограниченной интеграции EF-10.
[Полные замеры](../research/eska-format/ef-09-results.md) не подтвердили экономию
места и ускорение обычного Git: источник C1 +9,43%, источник/база/одно XML-поколение
1,177 GB, обычный pack с базой +26,08%. LFS дедуплицирует двоичные payload,
но index/status/save не стали дешевле. Release: импорт C1 3,38 с,
защищённый экспорт 5,49 с плюс открытие базы 3,34 с, VmHWM около 150 MB.
Большие C2/C3 импортированы за 54,08/70,70 с с лимитом адресного пространства
4 GiB, VmHWM 1,34/1,70 GB; их сборка не выполнялась. Временная подготовка
второго поколения измерена при сохранённом первом. Обнаружена необходимость
byte-preserving Git transport для extensionless блоков базы: стандартный
`text=auto` меняет CRLF. Это обязательная граница публичной интеграции EF-10/EF-19,
а не исправление core через Git. Полные fmt/check/strict Clippy/test/Rustdoc
и diff-проверки прошли; реальные release opt-in выполнены отдельно.

## EF-10 Общая модель и проектные инструменты

Добавить выбранный формат в проверенную конфигурацию проекта и узкую границу
источников рядом с `DesignerSource`. Подключить чтение, source locations,
инвалидацию и диагностику к существующей модели. Проектные операции и запуск
платформы разместить в своих библиотеках и точках входа согласно
[границам инструментов](../tool-boundaries.md). Экспериментальный CLI-контракт
определить по готовым операциям импорта, экспорта и сборки.

**Готово, когда:** Designer XML сохраняет действующее поведение; новый источник
работает с discovery и выбранными workspace members. `build` получает только
проверенное поколение EF-06, stale XML не обходит защиту. Ошибка платформы
сопоставляется с исходным YAML или ресурсом. Проектные операции работают без
платформы, сборка — без BSL-анализатора и Git. Human/JSON-контракты, локали,
идентичность кеша и адресные обновления проверены. Результат сборки включает
контекст и карту фактически собранных исходников для будущего отладчика.
Сохраняемые кеши различают форматы, версии схемы/правил и принятую базу. После
чистого checkout или удаления кеша используется тот же набор закреплённых входов;
старый производный XML не становится запасным источником при ошибке чтения ESKA.
Специализированные инструменты не требуют установленной оболочки `eska`.

Логические части реализации: проверенная конфигурация и ленивый адаптер источника;
защищённая материализация и карта фактически собранных входов; отдельные
проектная и сборочная точки входа. Перенос в Git обязан сохранять байты базы
после чистого checkout; исходный XML не служит fallback при ошибке ESKA.

**Промежуточный результат:** [общий core](../research/eska-format/core-boundary.md)
выделен из зависимостей приложения: реестр типов, native support/XML и один
writer используются обоими форматами. Общие model/config/discovery/selection
тоже доступны без приложения; правила schema и workspace не дублируются.
Добавлен [reader владельцев](../research/eska-format/source-reader.md): открытие
читает только manifest/configuration, остальные YAML — по запросу; typed facts,
родительские UUID и byte locations относятся к точным дисковым/несохранённым
байтам. Ошибка YAML не включает native XML как fallback. Права и полная
проверка состава остаются на границе защищённого экспорта.
Model и pure XML parser вынесены в core; [YAML-проекция](../research/eska-format/semantic-projection.md)
возвращает те же логические объекты, свойства и ссылки без генерации проекта XML.
Координаты различаются по исходному формату и привязаны к SHA-256 source text.
В `build_core` вынесены план сборки, runner платформы и managed infobase;
прежний сборщик использует их же. Feature `build` проверяется отдельно от
приложения, без Git engine, HTTP, CLI, TTY и IDE runtime.
[Конвейер](../research/eska-format/build-boundary.md), снимок и artifact manifest
также вынесены; приложение только поставляет Git provenance. Независимый
consumer собрал native C1 через установленную 1С, SHA-256 CF проверен.
[Подготовленная сборка](../research/eska-format/prepared-inputs.md) принимает
private proof поколения, проверяет фактический snapshot до ИБ/платформы
и записывает source context в manifest schema 2. Прежний XML build сохраняет
schema 1. [Карта файлов](../research/eska-format/source-map.md) различает
рабочие и принятые bytes BSL/ресурсов, составные metadata origins и сохраняется
в manifest с SHA-256. Следующие части — координаты YAML, диагностика платформы
и публичная конфигурация.
Маршрут ESKA → prepared snapshot → CF → новая выгрузка C1 принят:
8 769 файлов/8 064 каталога совпали с контролем, исключение — только
проверенные служебные configVersion. Все остальные байты равны.
Minimal library compile graph не содержит
gix, HTTP, CLI, TTY или IDE runtime. Это подготовка текущих потребителей;
публичная конфигурация ESKA, discovery, build и самостоятельные инструменты
ещё не подключены. Этап остаётся `IN-PROGRESS`.

## EF-16 Решение о пилотном использовании

формат проекта не является основанием автоматически переписывать BSL parser.

**Готово, когда:** выбран вариант по реальным API, лицензиям компонентов,
транзитивным зависимостям, памяти и стоимости сопровождения. Минимальный пример
связывает BSL с метаданными ESKA и учитывает несохранённое изменение свойства.
Языковое ядро принимает версионированные входы без обязательного экспорта XML,
запуска платформы, Git и сетевых сервисов. Решение и ограничения воспроизводимы.
Указано, какие компоненты синтаксиса можно переиспользовать в T26 и T84 без
полной базы анализа; общего выбора parser достаточно, готовность этих команд
не является условием EF-17.

## EF-18 Сервер анализа и пакетная проверка

Подключить выбранное ядро к общей модели проекта. Выделить `eska-analyzer` для
IDE и `eska-check` для одноразового анализа. Имена предварительные; вычисления
и правила диагностики едины. LSP и metadata-расширения не смешиваются молча
с существующим handshake IDE protocol 1.x.

**Готово, когда:** один сервер согласует дерево, свойства и анализ открытых
YAML/BSL; запросы учитывают revision, отмену и ограничения памяти. Пакетная
проверка того же сохранённого снимка и профиля даёт согласованные результаты,
работает без сервера, LSP runtime, платформы и Git. Проверены неполные результаты
и ошибки окружения. Изменения возвращаются планами с проверкой входной версии.

## EF-19 Самостоятельный инструмент VCS

Выделить текущие Git/workflow-операции в отдельную библиотеку и CLI-потребителя
общей модели проекта. Смысловой diff использует снимки и необходимые парсеры;
постоянный сервер анализа для него не требуется. Публичные команды прежнего
`eska` сохраняются через согласованный переход без второй реализации операций.

**Готово, когда:** status/diff/save и сценарии задач работают без платформы,
IDE и ядра полного BSL-анализа. Сохранность незакоммиченного состояния и JSON
контракты подтверждены существующими сценариями. Проверены транзитивные
зависимости. Git-коммит не изменяет правила допустимости защищённого экспорта.
Снимки обеих сторон diff читаются по собственным версиям исходного формата;
проверены YAML-свойство, BSL, непрозрачный ресурс, rename и обновление состава.
Обычное слияние метаданных проверяется валидатором EF-06 даже при отсутствии
текстовых конфликтов. Merge форм и специальный драйвер остаются в EF-13.
Замеры status/diff/save через gix сопоставлены с контрольными вариантами EF-09
без скрытого изменения правил учёта файлов и rename.

## EF-20 Сквозной CLI и создание из CF

Согласовать и реализовать пользовательский вход `eska`, делегирующий операции
самостоятельным инструментам. В оболочке остаются маршрутизация и координация
этапов; правила формата, проверки и Git-операции имеют одну реализацию у владельца.
Сохранить документированные текущие команды/JSON для Designer XML либо заранее
описать явную миграцию контракта.

Эскиз создания: `eska new <name> --from <file.cf> --source-format eska`.
Распаковка принадлежит `eska-build`, создание и XML → ESKA — `eska-project`,
Git init при выбранном workflow — `eska-vcs`. Использовать наработки T82 по
определению фактического типа, выбору платформы и сохранности назначения.
Исходный CF, существующий каталог и рабочая ИБ не изменяются. Источник принятой
базы и операция её принятия должны быть явно отражены в контракте создания.

После сохранения правок `eska check` делегирует пакетную проверку,
`eska build --output <file.cf>` — защищённую материализацию и нативную сборку.
Прямой `eska-project export` создаёт Designer XML без платформы. `eska fmt`
подключается по готовности T26; его отсутствие не подменяется другой реализацией.
Имена новых флагов утверждаются в этой задаче, примеры пока не являются API.

**Готово, когда:** на отдельном реальном CF пройден маршрут создания, сохранённой
правки свойства/BSL, проверки, сборки CF и контрольной повторной выгрузки.
Проверены standalone/workspace, RU/EN, JSON и запуск без TTY с явными настройками.
Оболочка и прямые команды дают одинаковые результаты; сохраняются аргументы,
stdout/stderr, exit codes и отмена. Отсутствующая/несовместимая утилита, ошибка
платформы или преобразования не оставляют проект, объявленный успешно созданным.
Для частично выполненной операции определены восстановление и явный отчёт.
У нового ESKA-проекта один редактируемый source, служебный XML исключён из Git.
Повторный импорт в существующий ESKA не наследует слепо полную замену из T82:
без отдельного принятого плана он отклоняется, принятие новой базы относится к EF-15.

## EF-21 Комплект инструментов и выборочная установка

Обычная установка `eska` устанавливает небольшую оболочку и все готовые основные
`eska-*` согласованной версии. Комплект содержит отдельные исполняемые файлы;
самостоятельные пакеты устанавливаются и работают без оболочки. Для первого
пилота состав задают готовые EF-10/EF-18/EF-19/EF-20; formatter/release добавляются
после T26/T32, отладчик остаётся отдельным дополнением. Отсутствующая возможность
явно обозначается, полный комплект не означает готовность незавершённых задач.

Определить состав пакетов, поиск бинарников, совместимость протоколов/форматов,
обновление и удаление с сохранением выборочного состава. В начале достаточно
согласованного набора версий из одного Rust workspace. Изменение способа поставки
и обновления текущего `eska` согласовать с T57, без второй независимой automation.
Действующие workflows и установщики меняются только в отдельной реализации
этой задачи, не в ходе текущего уточнения плана.
Приёмка EF-21 фиксирует состав первого комплекта. Проверки formatter/release
применяются при включении готовых T26/T32 и не задерживают первый пилот;
регрессия поставки входит в подключение этих компонентов.

**Готово, когда:** проверены полный комплект, `eska-check` без IDE/Git/платформы,
сборщик с проектными библиотеками без анализатора и работа расширения только с
`eska-analyzer`. После T26 форматтер работает самостоятельно, а IDE использует
его библиотеку без установки второго процесса. После T32 локальный release plan
не требует сборщика; публикация проверяет доступность нужных check/build либо
подтверждённых результатов CI до действий с релизом. Несовместимые версии
обнаруживаются до изменяющей операции.
На заявленных ОС проверены установка/обновление/удаление, прерванное обновление,
пути с пробелами и восстановление рабочего комплекта; непроверенные ОС отмечены.
Замерены размеры поставок и транзитивные зависимости. Выборочная установка
не превращается при обновлении в неявную установку всего набора.

## EF-22 Форматирование и релиз проекта ESKA

Подключить готовые T26/T83/T56/T32 к источникам ESKA и сценарию EF-20. Эта задача
владеет адаптерами нового источника и сквозной приёмкой, а не второй реализацией
formatter, bump, changelog или provider adapters. Версия конфигурации/расширения
меняется через точечный редактор YAML; у внешних объектов источником остаётся
литерал `Версия()`. Внешние профили принимаются отдельно после EF-14/T84.

**Готово, когда:** форматирование/проверка BSL в ESKA даёт те же результаты, что
в IDE, а изменение стиля не влияет на правила XML-экспорта. Ручной и автоматический
bump сохраняют обе схемы номера и затрагивают только ожидаемые исходники.
Проверен CI-маршрут `eska-fmt --check` / `eska-check` → `eska-release prepare` →
слияние Release PR/MR → `eska-release publish` для точного release commit.
Принятая база восстанавливается из закреплённого источника, итоговая версия
проверяется после защищённого экспорта и в нативном артефакте. Строгий режим CI
не публикует релиз с исключёнными правками. Повтор после сбоя не меняет номер,
commit и готовые артефакты. Непринятые внешние профили не объявляются поддержанными.

## Проверки и результаты каждой задачи

Все ручные сценарии создают собственные каталоги только в
`<repo>/../eska-playground`. Исходные demo и рабочие ИБ не изменяются.
Необезличенные конфигурации, CF, принятые базы и большие кеши не включаются
в репозиторий. После эксперимента остаются небольшой воспроизводимый пример,
результаты сравнения и измерения с параметрами входа.

Каждая законченная логическая часть получает отдельный содержательный commit
вместе со статусом и решением. При изменении приложения выполняется полный набор
проверок из [AGENTS.md](../../AGENTS.md); для документации — проверка ссылок,
структуры и diff. Успешные unit-тесты, платформенная сборка и проверка поведения
в клиенте фиксируются как разные уровни подтверждения.
