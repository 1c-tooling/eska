# T106: скорость дерева и языкового клиента на buhmfo

Изначально 2026-10-22 измеренные превышения T89 были отложены в отдельную
задачу оптимизации. В ходе ревью пользователь разрешил выполнить T106,
если установлена причина. T106 — `IN-PROGRESS`; порядок T98–T99,
T100–T105 и отметки `NEXT` не меняются.

T89 завершена на Linux/VSCodium с этим явно отложенным остатком.
Текущая серия проходит 9 из 12 performance gates; T106 ещё не завершена.
Допуски не повышаются.

[исправленные измерения](../measurements/t89-corrected.json),
[исходный допуск T90](../measurements/t90-baseline.json).

## Задача и границы

Уменьшить время готовности дерева, запуска собственного языкового клиента
и definition в сценарии с чередованием правок и запросов. Владельцы — ESKA
и Explorer; сначала установить, в каком процессе и на каком участке возникает
задержка, затем менять только подтверждённую причину.

|---|---|---|---|---|
| Дерево, мс | 420,45 / 411,86 | 532,58 / 528,62 | 26,67% / 28,35% | 10,622% / 17,113% |
| Язык, мс | 5243,74 / 5120,60 | 6241,48 / 6207,36 | 19,03% / 21,22% | 10% / 10% |
| Definition, мс | 143,14 / 111,27 | 239,81 / 239,89 | 67,54% / 115,58% | 10% / 10% |

Это исторические медианы исправленной серии T89 до оптимизации.
Hover и completion в ней проходят исходный допуск.
Правка/восстановление с новой семантической диагностикой медленнее на 32–33%,
но укладывается в исходный разброс T90 40,759% / 41,069%.
На момент T89 причина задержки definition не была установлена.
Результаты нового разбора и сохраняющийся остаток приведены ниже.

Сохраняются Designer XML/BSL, первичный `eska.toml` и внешний опубликованный
bsl-analyzer без форка и встроенного Rust-ядра. Не входят новые возможности
редактора запросов, отладчик, release automation и публикация.
Обновление версии анализатора требует отдельного решения; при сравнении
используется один и тот же бинарник сервера у обеих пар.

## Порядок работы

1. Подтвердить ветки, чистоту исходников, версии, входы и сохранённые raw-данные.
   Сначала прочитать probe и реальные пути запуска production-клиента.
2. Разделить время discovery/context, подготовки конфига/lease, старта процесса,
   LSP initialize, запросов и публикации диагностики. Для definition сопоставить
   отправку запроса, обработку upstream и доставку ответа редактору. Измерять
   тем же probe; дополнительные диагностические прогоны учитывать отдельно.
3. Исправить установленную причину минимальным изменением. Сохранить ленивый
   запуск: открытие только дерева не запускает LSP и не генерирует его конфиг.
   Не переносить работу за границу таймера и не добавлять искусственное ожидание
   для изменения результата benchmark.
4. Повторить минимум пять cold и пять repeat каждой пары, 30 операций каждого
   вида за запуск, пять секунд покоя и 30 отдельных steady hover. Восстановление
   буфера завершается только свежей уникальной семантической диагностикой;
   пустая коллекция редактора не подтверждает окончание анализа.
5. Проверить правильность hover/completion/definition, свежесть diagnostics,
   XML/BSL refresh, смену ветки/приложения и shutdown. Сохранить protected bridge,
   атомарную проверку языковых правок, lease и остановку своего клиента
   при конфликте. Проверки policy не подменять серией с отключённой policy.
6. Опубликовать median/p95, суммарные RSS/PSS/CPU/I/O, размеры кэшей, версии,
   команды и hashes. Выполнить релевантные Node/Bun/native проверки Explorer;
   при изменении Rust — полный набор из `working-agreement.md`.

## Приёмка T106

Готовность дерева, языка и definition проходит исходные фиксированные gates
T90: максимум 10% или первоначальный измеренный разброс, если он больше.
Hover, completion и цикл диагностики также сохраняют исходные gates и
корректность. Новая серия и профиль не используются для повышения допуска.
В отчёте отдельно видны результат каждого gate и изменение методики, если оно
понадобилось; смена таймера требует объяснения и не заменяет исходную метрику.

Не остаются процессы собственного запуска, старые diagnostics, изменения
пользовательского проекта или незадокументированное расширение scope.
Остальные ОС, VS Code и Remote остаются непроверенными до отдельных запусков.

## Ревью и исправления 2026-10-22

Новый стенд — `../eska-playground/t106-review-8un6rmfa` относительно корня ESKA.
Обе конфигурации скопированы отдельно; предыдущие серии T89 и пользовательский
проект не меняются. `diagnostic/` содержит отдельные трассировочные прогоны,
`pilot/` — пробную пару, `series/` — прерванную промежуточную серию.
Она сохранена вместе с причиной остановки и не используется для итоговых gates.

Подтверждены три причины в Explorer:

- Команда подключения повторно открывала уже подключаемый или готовый проект.
  Теперь для одного workspace folder она ожидает текущую попытку или использует
  готовую сессию. Явная команда перезапуска и обновление manifest по-прежнему
  заменяют backend. Нативный тест удерживает настоящий `workspace/open`,
  проверяет один процесс и последующий явный restart.
- При каждом изменении BSL клиент удалял текущие diagnostics, после чего
  сервер публиковал замену. Дополнительное пустое состояние провоцировало
  фоновые запросы редактора и задерживало definition. В отдельном контрольном
  прогоне удаление только этой очистки уменьшило медиану definition
  с 229,78 до 57,02 мс; завершение правки по-прежнему подтверждалось уникальной
  семантической диагностикой. Диагностики буфера теперь заменяет upstream.
  Изменение конфигурации и остановка клиента всё ещё очищают коллекцию;
  проверки поколения, версии документа, разрешений и lease сохранены.
- Каждый запуск повторно вызывал `configPrepare` для уже проверенного
  управляемого конфига со статусом `current` (около 366 мс в трассе).
  Теперь такой конфиг используется повторно; новый, устаревший или выбранный
  другой контекст по-прежнему проходит подготовку и upstream `check-config`.
  Проверка бинарника не пропускается. `acquire` заново проверяет входы под
  lease; несовпадение token/fingerprint/body/path/context отменяет запуск
  и освобождает полученный lease. Это проверено отдельной гонкой status/acquire.

Профиль не используется для итоговых gates: его proxy/trace отдельно отмечены.
Исходный probe не изменён, ленивый запуск LSP сохранён. Открытие одного дерева
не создаёт конфиг анализа и не запускает LSP.

## Воспроизведение новой серии

Из корня ESKA; команды используют сохранённые private copies и frozen runtime.
Новый каталог не перезаписывает raw-данные принятой серии:

```bash
review_stand="$(realpath ../eska-playground/t106-review-8un6rmfa)"
replay_dir="$(mktemp -d "$review_stand/replay-XXXXXXXX")"
cp "$review_stand/series-final/"{run.py,probe.cjs,execute.py,summarize.py,replay-summary.py,provenance.json} "$replay_dir/"
python3 -B "$replay_dir/execute.py"
python3 -B "$replay_dir/replay-summary.py"
```

Каждый launch создаёт отдельные `--user-data-dir` и `--extensions-dir`; точная
команда и завершение собственных PID сохраняются в `launch.json`. Для новой
сборки сначала обновить frozen runtime и provenance в отдельном стенде.
Не запускать сборки и другие тяжёлые проверки параллельно измерениям.

## Продолжение: один снимок корневого XML

По запросу пользователя от 2026-10-22 T106 продолжается перед T100–T105.
В resolver устранены повторное чтение корневого XML и построение полной
модели свойств/дочерних деклараций ради `CompatibilityMode`.
Идентичность и совместимость берутся из одного проверенного снимка корня.
Кэш для анализа не вводится; статус конфига и acquire по-прежнему заново
проверяют входы, включая проверку под OS lease.

Обычное открытие метаданных сохраняет прежние правила кэша. Анализ продолжает
проверять полный XML envelope, namespace и тип корня, UUID/Name, уникальность
корневых Properties/Name и скалярность compatibility. CDATA и текст,
разделённый комментариями, декодируются общим reader; чужой namespace
не задаёт режим совместимости. Полный Rust workspace: fmt/check/Clippy,
debug/release build, Rustdoc — passed; 908 tests passed, 12 ignored.
Два новых теста проверяют эти ограничения и бюджет одного чтения корня
при 2000 дочерних декларациях. Численные gates T106 этим не объявляются
пройденными: новая серия с release-бинарником выполняется отдельно.
[Отчёт этой части](../measurements/t106-root-snapshot.json) содержит hashes,
логи полного Rust workspace и побайтовую сверку прежнего/нового CLI JSON
на шести sources `buhmfo` в обеих локалях.
