# Метаданные Designer XML и IDE protocol

План развития собственного metadata layer `eska`. Все задачи ниже описывают
будущее поведение; обновление roadmap не реализует API, команды или fixtures.
Общий статус и очередь остаются в [трекере](README.md), продуктовый контекст —
в [Milestone 8 и Milestone 21](../eska-roadmap.md).

## Границы и последовательность

Поддерживаются только стандартные выгрузки Конфигуратора: основная
конфигурация, расширение, внешний отчёт и внешняя обработка. Первый
функциональный результат — полностью read-only дерево и библиотечный API;
первый IDE milestone тоже ничего не записывает в проект.

| Milestone | Задачи | Результат |
|---|---|---|
| Metadata V0.1 — Core model | T60–T62 | Логическая модель, identity, resolver и набор fixtures |
| Metadata V0.2 — Designer XML parser | T63–T64 | Выбор стратегии чтения и разбор четырёх типов проектов |
| Metadata V0.3 — Configurator tree | T65–T66 | Схемы дерева, golden tests и read-only API |
| Metadata V0.4 — Incremental workspace | T67–T68 | Lazy index, cache, invalidation и измеренная производительность |
| IDE V0.1 — Read-only protocol | T69–T70 | Контракт и постоянный процесс `eska ide --stdio` |
| Metadata V0.5 — Existing object editing | T71–T73 | Safe XML patching и изменение существующих элементов |
| Metadata V0.6 — Structural editing | T74 | Отдельный будущий этап создания, удаления и переименования |

Версии обозначают этапы metadata/IDE, а не версии crate. Порядок действует
внутри этого направления; он не заменяет текущий `NEXT` T58 и ближайшую очередь
CLI. Реализация каждого этапа требует отдельной задачи пользователя. V0.5
начинается после приёмки стабильного read-only дерева и IDE V0.1; V0.6 отложен.

Не входят: VS Code extension (остаётся T41), EDT и другие source formats, MCP,
AI-функции, собственный BSL language server, редактор или визуальный дизайнер
форм. По решению проекта `bsl-analyzer` / `bsl-metadata` исключены из
зависимостей metadata layer из-за неопределённости лицензирования.
Пользователь может независимо использовать `bsl-analyzer` как LSP/анализатор BSL.

| T59: [порядок semantic diff](04-core-vcs-ux.md) | План единой таблицы порядка типов Конфигуратора | Дочерних коллекций и полного дерева; T59 остаётся отдельной задачей |
| T25: [version.rs](../../src/project/version.rs) | Замена диапазона `Properties/Version`, сохранение остальных байтов | Общего mapping свойств и переносимой атомарной записи произвольных изменений |
| T41: [VS Code extension](10-delivery-and-integrations.md) | Место будущего тонкого клиента | Серверного metadata protocol; он выделен в T69–T70 |

`ObjectModel::discover` сейчас явно обходит source и строит полный индекс;
`discover_affected` ограничивает работу затронутыми descriptors. Ни один из них
нельзя просто вызывать при каждом запросе IDE-дерева. Существующие
`status`/`diff`/`save`, их JSON identities и схемы сохраняются; перенос общих
частей не должен навязать им полный parse или долгоживущий процесс.

В [Cargo.toml](../../Cargo.toml) уже есть `roxmltree` с `std`/`positions`,
`serde`, `serde_json` и `sha2`. Их можно оценить для разбора отдельных файлов,
protocol DTO и проверки снимков. `roxmltree` строит read-only дерево одного XML,
а streaming API предлагает, например, `quick-xml`; выбор новой зависимости
остаётся результатом T63, а не решением этого плана. Основание:
[документация roxmltree](https://docs.rs/roxmltree/latest/roxmltree/),
[документация quick-xml](https://docs.rs/quick-xml/latest/quick_xml/).

## Архитектурные границы

```text
Designer XML files -> parser -> metadata model
                          \-> source mapping / Designer resolver
metadata model + ConfiguratorSchema -> ConfiguratorTree
lazy metadata workspace -> read-only API -> IDE protocol -> будущий клиент
логическая операция изменения -> validation -> XML patch -> invalidation
```

Модель описывает типы, identity, свойства и отношения; она не хранит XML DOM
как публичное представление и не выводит identity из физического пути.
Resolver знает файлы и XML locations. Schema знает допустимые коллекции,
модули и порядок дерева. Workspace управляет загрузкой и временем жизни cache.
Protocol переносит запросы и DTO, не дублирует эти правила.

Metadata workspace — сессия чтения выбранных `Project`, а не новый формат
`[workspace]`. Discovery и выбор members переиспользуются из T44/T48.
Идентификатор проекта и logical metadata identity различаются: одинаковые
`Catalog.Контрагенты` в двух members не должны сталкиваться. При открытии
монорепозитория не разбираются XML всех невыбранных members.

## T60 — Модель метаданных и логическая identity

**Статус:** `PLANNED`
**Зависит от:** T01, T03, T06, T19, T44

Развить существующую модель вместо второго независимого каталога объектов.
Отделить данные метаданных от XML и source paths; определить отношение
`MetadataId` к существующему `ObjectId` до введения нового публичного API.
Переиспользование текущей identity предпочтительно; новый тип допустим только
при конкретном отличии контракта. Не менять документированные CLI/JSON IDs
молча и не строить compatibility layer для недокументированных внутренних API.

**Готово, когда:**

- модель различает конфигурацию, расширение, внешний отчёт и внешнюю обработку,
  переиспользуя распознавание `ProjectType`, включая именованные внешние descriptors;
- матрица типов покрывает справочники, документы, перечисления, константы,
  общие модули, роли, подсистемы, планы видов характеристик, планы счетов,
  планы видов расчёта, регистры сведений/накопления/бухгалтерии/расчёта,
  бизнес-процессы, задачи, отчёты и обработки;
- остальные стандартные типы поддерживаемых версий Designer XML занесены в
  ту же матрицу: существующий `kind_from_tag` служит отправной точкой, полнота
  сверяется с реальными выгрузками, а неизвестный тип получает явный diagnostic;
- вложенные сущности включают реквизиты, табличные части и их реквизиты,
  измерения, ресурсы, значения перечислений, формы, команды, макеты и модули;
- identity детерминирована логической иерархией, независима от source root,
  разделителей ОС, locale и порядка чтения; UUID остаётся вспомогательным
  значением, поскольку существующие fixtures допускают его повторение;
- определены escaping, project scope, identity модулей и виртуальных коллекций;
  у коллекции дерева свой node ID, она не выдаётся за реальный metadata object;
- перенос проекта на диске сохраняет IDs; логическое переименование относится
  к T74 и не обязано сохранять основанный на имени ID.

Примеры логических адресов, не новая сериализация текущего `ObjectId`:

```text
Catalog.Контрагенты
Catalog.Контрагенты.Attribute.ИНН
Catalog.Контрагенты.TabularSection.Контакты.Attribute.Телефон
Catalog.Контрагенты.Form.ФормаЭлемента
Catalog.Контрагенты.Module.Object
InformationRegister.КурсыВалют.Dimension.Валюта
```

Текущий формат `catalog:Контрагенты/attribute:ИНН` и его escaping учитываются
в решении. Отображаемая подпись не используется для поиска или identity.

## T61 — Designer path resolver

**Статус:** `PLANNED`
**Зависит от:** T19, T60

Выделить из существующего ownership/mapping слой logical object → physical
sources и обратное разрешение changed paths → owners. Пути относительны source
выбранного проекта; core metadata model от них не зависит.

```text
Catalog.Контрагенты
  -> Catalogs/Контрагенты.xml
Catalog.Контрагенты.Module.Object
  -> Catalogs/Контрагенты/Ext/ObjectModule.bsl
Catalog.Контрагенты.Module.Manager
  -> Catalogs/Контрагенты/Ext/ManagerModule.bsl
```

**Готово, когда:** fixtures подтверждают mapping для каждого поддержанного
типа, inline реквизитов и табличных частей, descriptors и payload форм/команд/
макетов, всех применимых видов модулей, подсистем и расширений. Внешние отчёты
и обработки учитывают прямые `Ext`/`Forms` и фактически встречающиеся варианты
выгрузки, без обязательного каталога с именем корневого объекта.

Для inline элемента возвращаются владеющий XML и логическая location внутри
него, для объекта с несколькими sources — их роли. Вычисленный кандидат пути
не выдаётся за существующий файл. Нет полного recursive scan; разрешение
ограничено владельцем и нужными locations, не выходит из source через symlink
или `..` и не читает BSL для определения его пути. Регрессии mapping T19/T50
проверяются прежними тестами.

## T62 — Набор Designer XML fixtures

**Статус:** `PLANNED`
**Зависит от:** T19, T60

Расширить существующие fixtures из [object model tests](../../tests/project/object_model.rs)
отдельным переиспользуемым набором небольших XML/BSL-фрагментов и ожидаемых
результатов. Зафиксировать происхождение и версии платформы/формата; не
подменять реальные особенности выгрузки предположениями по именам каталогов.

**Готово, когда:** есть конфигурация, расширение, внешний отчёт и обработка;
справочник, документ, перечисление, все четыре вида регистров, объект с формами,
несколькими модулями, табличными частями и их реквизитами. Покрыты inline и
standalone представления, namespaces/префиксы, BOM, LF/CRLF, Unicode, повтор
UUID, неизвестный тип, повреждённый XML и отсутствующий source.

Для матрицы остальных стандартных типов добавляются минимальные фрагменты по
мере T64/T65; отсутствие покрытия явно отмечается до приёмки этих задач.
Fixtures и ожидаемые snapshots можно хранить в репозитории как тестовые данные;
рабочие тестовые проекты создаются только в собственных уникальных каталогах
`ESKA_TEST_ROOT`, равного абсолютному `<repo>/../eska-playground`, и удаляются
самими тестами. Существующие demo пользователя не меняются.

## T63 — Выбор стратегии XML parsing

**Статус:** `PLANNED`
**Зависит от:** T61, T62

Исследовательская задача до реализации parser. Сравнить текущий ограниченный
разбор отдельного descriptor через `roxmltree` с namespace-aware streaming
reader. В текущих прямых зависимостях streaming XML API нет; `quick-xml` —
кандидат для проверки, не автоматически принятая зависимость.

**Готово, когда:** записаны измерения времени, памяти, прочитанных байтов и
копирований на маленьком descriptor, большом `Configuration.xml` и крупном
объекте с вложенными сущностями; проверены namespaces, entities, limits и
позиции исходного текста. Решение описывает, где достаточно текущего parser,
а где нужен streaming. При выборе crate проверены актуальная стабильная
версия, поддержка, лицензия и минимальные features; при сохранении текущего
parser показано выполнение lazy/performance требований без общей DOM проекта.
Ни T63, ни T64 не создают собственный низкоуровневый XML tokenizer.

## T64 — Разбор Designer XML в модель метаданных

**Статус:** `PLANNED`
**Зависит от:** T60–T63

Собственный parser формата Designer поверх выбранной XML-библиотеки должен
возвращать доменную модель и source mapping. Разделить чтение корневого
descriptor/списков ссылок и чтение содержимого отдельного объекта по запросу.

**Готово, когда:**

- распознаются `Configuration.xml`, расширение с его свойствами, внешние
  отчёты/обработки и XML верхнеуровневых объектов по матрице T60;
- доступны существующие свойства, вложенные/составные значения, реквизиты,
  табличные части и их реквизиты, измерения, ресурсы, значения перечислений,
  формы, команды, макеты и связанные модули;
- списки ссылок `ChildObjects` читаются без загрузки XML каждого указанного
  объекта; его свойства и дочерние элементы разбираются только по требованию;
- XML descriptors и payload форм/макетов различаются: показ узла или source
  не требует разбора внутреннего устройства формы, макета или текста BSL;
- namespace проверяется по URI, не по выбранному префиксу; неизвестные свойства
  не теряются молча, неподдержанная форма значения помечена явно;
- нет общей DOM всего проекта; per-file buffers и лимиты размера/глубины/узлов
  обоснованы T63, не создаются лишние полные копии XML;
- ошибка одного descriptor локализована на объекте/ветке, остальные доступны;
  нет ложного полного успеха при повреждённом или неподдержанном фрагменте;
- тесты T62 и матрица типов подтверждают parent/children, свойства и source
  mapping для четырёх видов проектов; регрессии T19/T50 не меняют CLI contracts.

## T65 — ConfiguratorSchema и ConfiguratorTree

**Статус:** `PLANNED`
**Зависит от:** T61, T64; согласуется с таблицей порядка T59

Описать отдельную схему каждого типа: корневые разделы, допустимые дочерние
коллекции, виды модулей и их порядок. Дерево строится из metadata model и schema,
не из списка каталогов. Порядок корня начинается «Общие», «Константы»;
остальное, включая порядок внутри объекта, сверяется с Конфигуратором на
зафиксированной версии платформы. Схема разделяет machine keys и RU/EN подписи.

Иллюстрация требуемых различий, окончательный порядок подтверждают fixtures:

```text
Справочники                       Регистры сведений
└── Контрагенты                    └── КурсыВалют
    ├── Реквизиты                      ├── Измерения
    │   ├── ИНН                       ├── Ресурсы
    │   └── КПП                       ├── Реквизиты
    ├── Табличные части                ├── Формы
    ├── Формы                         ├── Команды
    ├── Команды                       ├── Макеты
    ├── Макеты                        ├── Модуль менеджера
    ├── Модуль менеджера               └── Модуль набора записей
    └── Модуль объекта
```

**Готово, когда:** все типы матрицы T60 имеют проверенные schema и порядок;
справочник и регистр не получают одинаковый универсальный набор children.
Определены пустые коллекции, отсутствующие optional modules, fallback для
неизвестных типов, порядок объектов внутри коллекции и возможность раскрытия
без предварительного parse всех потомков. Таблица порядка общая с T59,
без зависимости core от CLI и без расширения scope semantic diff.

Golden tests проверяют `Designer XML -> parser -> ConfiguratorTree ->
expected-tree.json`: корень, группы, вложенные реквизиты, табличные части,
формы, команды, макеты, модули и все регистры. Snapshots малы, детерминированы,
не содержат абсолютных путей/времени и проверяют IDs отдельно от RU/EN labels.

## T66 — Read-only metadata workspace API

**Статус:** `PLANNED`
**Зависит от:** T60–T65

Предоставить библиотечную границу открытия/закрытия metadata workspace и
операции `root`, `children(node)`, `object(id)`, `properties(id)`, `source(id)`.
Первый функциональный milestone read-only: ни источники, ни manifest, ни Git,
ни служебные cache-файлы не изменяются. Cache T67 существует в памяти сессии.

**Готово, когда:** API возвращает identity, parent, тип узла, отображаемое имя,
признак возможности раскрытия, дочерние элементы, существующие свойства и
sources XML/BSL с ролями. Для виртуальной коллекции отсутствие физического
source нормально; объект с несколькими sources не теряет их при выборе одного.
Machine kinds/keys/IDs и structured errors независимы от locale, подписи
локализуются на границе представления в RU/EN без зависимости core от Fluent/TTY.

Открытие ограничено discovery, определением типа и основной структурой выбранного
проекта; запрос детей/свойств читает только необходимые descriptors. Тестовый
библиотечный клиент проходит дерево всех четырёх типов проектов без запуска
CLI на каждый запрос и подтверждает побайтовую неизменность файлов. Неизвестный
ID, отсутствующий source и повреждённый объект имеют различимые ошибки.

## T67 — Lazy index, cache и инкрементальное обновление

**Статус:** `PLANNED`
**Зависит от:** T50, T66

Добавить индекс и cache разобранных объектов на время metadata workspace.
Повторные запросы используют его; изменённые source paths инвалидируют объекты,
зависимые children/properties и нужных предков, а не всю конфигурацию.

**Готово, когда:**

- первоначально загружаются только тип, корневая структура и коллекции;
  XML конкретного объекта читается при первом запросе его данных;
- для неизменившегося объекта повторные запросы не делают повторный parse;
  lifetime, ограничение памяти и eviction cache задокументированы;
- изменения XML/BSL, добавление, удаление и перемещение файлов внешним редактором
  корректно отражаются в индексе; это чтение внешних изменений, не write API;
- можно обновить отдельную ветку; повторно разбираются только затронутые
  descriptors и необходимые владельцы, остальной cache сохраняется;
- выбран и проверен способ получения file changes (события клиента или watcher),
  есть явный refresh для восстановления после пропущенных событий; гонка чтения
  и обновления не публикует смешанный снимок, устаревание различимо клиентом;
- изменение корневых списков инвалидирует соответствующие коллекции;
  исправленный после ошибки XML возвращает ветку в доступное состояние;
- полезность `ConfigDumpInfo.xml` измерена отдельно: он может ускорять обнаружение
  изменений, но не является полной моделью или единственным критерием свежести;
  его отсутствие, устаревание и ручная правка XML/BSL не скрывают изменения;
- тесты проверяют точный набор перечитанных файлов и неизменность независимой
  ветки. Persistent cache и фоновый prefetch не обязательны и сюда не входят.

## T68 — Производительность metadata workspace

**Статус:** `PLANNED`
**Зависит от:** T67

Расширить [протокол замеров](../performance.md) отдельными сценариями дерева:
cold open/root, первое раскрытие, повторный запрос properties/source,
refresh одной ветки. Сравнить маленькую fixture, крупную синтетическую выгрузку
и доступную реальную конфигурацию с фиксированной версией/размером данных.

**Критерии приёмки:**

- при старте нет полного recursive scan/parse всех XML; затраты root зависят от
  размера корневого descriptor/списков, а не суммы содержимого всех объектов;
- каждый запрос открывает только необходимые descriptors/locations; число
  `read_dir`, `stat`, открытий, прочитанных байтов и parse фиксируется счётчиками;
- повторный запрос при валидном cache не перечитывает/не разбирает descriptor,
  кроме обоснованной проверки свежести; число таких проверок тоже измерено;
- refresh одного объекта не перечитывает независимые объекты; добавление
  посторонних XML не увеличивает число parse для того же запроса;
- увеличение количества/объёма неиспользуемых BSL-модулей не добавляет их чтений
  или обходов при запросе дерева, свойств либо пути source;
- измерены cold/warm latency, median/p95, peak RSS и объём cache; нет лишних
  копий крупных XML. В отчёте указаны build profile, ОС, оборудование и повторы;
- численные бюджеты времени/памяти устанавливаются по воспроизводимому baseline
  до приёмки и закрепляются рядом с замерами; без них T68 не считается `DONE`.
  CI проверяет устойчивые счётчики, замеры времени не выдаются за SLA любой базы.

Если после этих проверок нужен prefetch, он оформляется отдельной последующей
оптимизацией в [backlog](99-deferred.md); базовый lazy API должен работать без него.

## T69 — Спецификация постоянного IDE protocol

**Статус:** `PLANNED`
**Зависит от:** T66–T68, T49

Спроектировать `eska ide --stdio`: один процесс на IDE workspace до его закрытия,
с повторным использованием metadata sessions. Рассмотреть JSON-RPC 2.0 поверх
stdio и зафиксировать решение перед T70. [JSON-RPC 2.0](https://www.jsonrpc.org/specification)
задаёт сообщения, но не framing потока; framing выбирается отдельно.

| Метод | Назначение |
|---|---|
| `project/info` | Типы и identity выбранных проектов, версия API/capabilities |
| `metadata/root` | Корневые узлы выбранного проекта |
| `metadata/children` | Дочерние узлы одного node |
| `metadata/get` | Объект по логическому ID |
| `metadata/properties` | Свойства существующего объекта |
| `metadata/source` | XML/BSL sources и их роли |
| `metadata/refresh` | Обновление выбранной ветки/проекта из файлов без записи |

**Готово, когда:** задокументированы handshake/open/close/shutdown, project
selection, node IDs, versioned DTO, ошибки, request IDs и notifications,
framing, лимиты сообщений, обработка batch, отмены и конкурентных запросов.
Зафиксированы поколение снимка, invalidation events и восстановление после
пропуска file changes. Выбор простого последовательного исполнения допустим,
если описано его поведение и выполнены бюджеты T68.

Stdout содержит только protocol messages, stderr — diagnostics, без ANSI и
интерактивных prompts. Machine payload/errors не зависят от locale; отдельные
display labels имеют RU/EN представление. Схема IDE API версионируется отдельно
от существующих одноразовых CLI JSON. Приведены request/response fixtures и
правила завершения на EOF, разрыве канала и ошибке сообщения. Нет write methods,
MCP, BSL LSP или зависимости от VS Code.

## T70 — Постоянный read-only IDE процесс

**Статус:** `PLANNED`
**Зависит от:** T69

Реализовать принятый T69 контракт поверх T66/T67. Один запуск обслуживает много
запросов и хранит cache до закрытия workspace; клиент не запускает отдельный
`eska` на каждый узел. Команда и help добавляются в README и обе локали только
при реализации.

**Готово, когда:** отдельный тестовый protocol client проверяет все методы в
одном процессе, последовательное раскрытие, refresh после внешней правки,
несколько project scopes, повреждённые сообщения, неизвестные методы/IDs,
EOF/shutdown и отсутствие утечки ресурсов. Stdout разбирается без фильтрации
human text; прогон RU/EN сохраняет machine schema. Содержимое проекта до/после
сеанса совпадает побайтно, cache переиспользуется, budgets T68 проверены через
protocol. `metadata/updateProperty` недоступен до T73. VS Code extension здесь
не разрабатывается.

## T71 — Архитектура safe XML patching

**Статус:** `PLANNED`
**Зависит от:** T25, T70

Отдельно исследовать изменение существующего свойства без полной
пересериализации XML. Переиспользовать подход T25 с диапазонами исходных байтов,
проверив применимость к namespace-qualified значениям, synonym, comment и
составному типу реквизита. Это проектирование общего patch engine, а не
расширение команды `version` произвольными XML edits.

**Готово, когда:** решение определяет mapping логического свойства к единственной
XML location, escaping/serialization поддерживаемых значений, minimal ranges,
preview, повторный parse результата и domain validation. Проверены BOM,
CRLF/LF, namespaces/префиксы, comments, порядок атрибутов и одноимённые вложенные
теги; нет regex-редактирования структурного XML и скрытого full-serialize fallback.

Запись проектируется через sibling temporary file и atomic replace с проверкой
ожидаемого исходного снимка, сохранением прав и очисткой только своих временных
файлов. Отдельно фиксируются гарантии Windows/Linux/macOS и конфликт внешней
правки. Текущий T25 использует на Windows последовательное переименование через
backup; это не доказательство атомарности и не переносится как готовая гарантия.
Неподдержанная безопасная запись отклоняется явно; разрушительный fallback не
считается реализацией. При неоднозначном mapping запись запрещена.

## T72 — Точечный XML patch и безопасная запись

**Статус:** `PLANNED`
**Зависит от:** T71

Реализовать принятый patch plan отдельно от публикации: исходный снимок →
проверенные replacements → preview → parse/validation → безопасная запись.
Контракт — изменение одного свойства меняет только необходимые байты/строки.

**Готово, когда:** golden byte-diff тесты доказывают сохранность всего вне
replacements, no-op не пишет файл, неверный XML или конфликт снимка не меняет
исходник. Failure injection проверяет ошибки temporary write/replace, права,
очистку и восстановление на поддерживаемых ОС. После patch XML повторно
разбирается; документация отличает XML well-formedness и domain checks от полной
проверки платформой 1С. Поддерживаются только однозначные mapping; запись
нескольких связанных файлов относится к T74.

## T73 — Редактирование существующих элементов

**Статус:** `PLANNED`
**Зависит от:** T67, T70, T72

Добавить логическую операцию `metadata/updateProperty`. Клиент передаёт project,
metadata ID, property key, значение и ожидаемый снимок; `eska` выбирает XML,
namespace, элемент, serializer значения и validation. Клиент не конструирует
XML, offsets или файловые операции. Поддержанные editable properties/capabilities
объявляются явно, неизвестная операция завершается без записи.

**Готово, когда:** можно менять простые свойства, синоним, комментарий,
поддержанные свойства существующего реквизита и его тип. Свойства существующих
форм/команд разрешены лишь после проверенного mapping, без редактирования
визуального устройства формы. После успешной записи инвалидируются нужные
объекты/ветки T67, ответ содержит новый снимок; неудача не публикует ложный успех
или новое cache-состояние. Preview, validation, конкурирующая внешняя правка и
byte-minimal diff покрыты интеграционными тестами для четырёх типов проектов.

Изменение `Name`, добавление/удаление объектов, реквизитов, форм, команд и
макетов запрещены в V0.5. Даже если имя хранится в простом XML property,
переименование остаётся структурной операцией T74. Изменение свойства,
требующее синхронной правки нескольких файлов, также откладывается до T74.

## T74 — Структурные изменения метаданных

**Статус:** `DEFERRED`
**Зависит от:** T73 и отдельной спецификации транзакции связанных файлов

Будущий Metadata V0.6: создание, удаление и переименование объекта;
создание/удаление реквизита; создание/удаление формы; создание команды и макета.
Операции меняют согласованно descriptors, списки детей/ссылки и физическую
структуру Designer XML. Rename рассматривается наравне с add/remove.

**Условие возврата:** приняты стабильные read-only и existing-object editing
milestones. До реализации описать preview затронутых файлов/ссылок, правила
UUID/identity, multi-file transaction и восстановление после частичного сбоя,
валидацию через реальные Designer exports/платформу, cache invalidation и
golden tests согласованности. Ни T71–T73, ни будущий IDE-клиент не могут вводить
эти операции обходным редактированием XML.
