# T109–T114 — Продолжение конструктора запросов

Очередь явно разрешена пользователем 2026-10-24:
**T109 → T110 → T111 → T112 → T113 → T114**.
Она продолжает [T108](19-query-advanced.md). Выполнение начинается со связанных
метаданных базы и расширений; соседние CLI, debugger и форматы в неё не входят.

Для всех задач ESKA владеет разбором, областями, связями, типизированной моделью,
проверками и минимальными планами правок. Explorer проверяет DTO и отображает
контролы, навигацию и штатный Undo/Redo. Новый адаптер IDE использует те же RPC;
собственного парсера, генератора запросов и правил метаданных в нём нет.
Designer XML остаётся единственным форматом; внешний анализатор не форкается.

## T109 — Связанные метаданные базы и расширений

**Статус:** `DONE`. Выполнено 2026-10-24; [проверки](../measurements/t109-related-metadata.json).

Единый каталог выбранного приложения разрешает наследуемые свойства и поля
заимствованных объектов, планы счетов, графики и базовые регистры расчёта во всех
его sources. Порядок расширений соответствует конфигу приложения. Объекты других
приложений не подмешиваются. Объявленный, но отсутствующий/нечитаемый descriptor
не превращается в успешный пустой ответ. Без базы сохраняется ограниченный контекст.

Приёмка: base+extension fixtures и RPC ru/en, новые и заимствованные объекты,
переопределения свойств, связанные схемы в соседнем member, отсутствие записи,
чужие sources и неизвестная связь. Корректность каталога принадлежит ESKA;
интерфейс использует существующий контракт, если его достаточно.

## T110 — Временные таблицы и пакеты

**Статус:** `DONE`. Выполнено 2026-10-24; [проверки](../measurements/t110-query-packages.json). Зависит от T109.

Добавить `ПОМЕСТИТЬ/INTO`, создание, использование и удаление временных таблиц.
Колонки выводятся из проекции создающего запроса; видимость зависит от порядка
операторов пакета. Переименование и проверки зависимостей выполняет ESKA.
Пакет остаётся одним исходным текстом; комментарии, окончания строк и независимые
операторы сохраняются без перегенерации. Интерфейс выбирает оператор и его свойства.

Приёмка: цепочки временных таблиц, `UNION`, `*`, повторное создание после удаления,
неизвестные/неоднозначные ссылки, атомарный отказ и native apply/cancel/Undo ru/en.

## T111 — Отбор по агрегатам

**Статус:** `IN-PROGRESS`. Зависит от T110.

Добавить `ИМЕЮЩИЕ/HAVING` отдельной секцией после группировки и до общего хвоста.
Типизированные условия, добавление, изменение, удаление и перенос комментариев
реализуются в ESKA. UI отличает отбор до группировки от отбора по агрегатам.

Приёмка: оба языка запросов независимо от языка IDE, вложенные области,
объединения, агрегатные выражения, безопасные отказы и точный no-op.

## T112 — Последовательные секции итогов

**Статус:** `PLANNED`. Зависит от T111.

Представить несколько секций `ИТОГИ … ПО` как отдельные узлы общего хвоста.
ESKA определяет владельца каждой группировки, порядок секций и допустимость
операций. UI выбирает секцию без сборки SQL. Сохраняются общие итоги, иерархия,
заполнение периодов, комментарии и разделение с ветками объединения.

Приёмка: несколько секций, пустые автоматические итоги, добавление/удаление
секции и группы, перемещения, комментарии, `UNION`, неактивные вложенные итоги.

## T113 — Конструкции языка СКД

**Статус:** `PLANNED`. Зависит от T112.

По первичной справке платформы определить и реализовать типизированное
редактирование конструкций языка СКД: необязательных полей, источников/условий
и параметров виртуальных таблиц в поддерживаемых позициях. Точные границы
фиксируются перед реализацией по грамматике платформы. Неизвестные конструкции
остаются точным непрозрачным текстом; поддержка не объявляется по наличию скобок.

Приёмка: настоящие запросы СКД Designer XML и автономные fixtures ru/en,
точное извлечение/возврат в XML, комментарии, атомарные отказы и интерфейс адаптера.

## T114 — Приёмка запросов реальной платформой

**Статус:** `PLANNED`. Зависит от T113.

Проверить сформированные запросы платформой 1С на отдельной тестовой ИБ buhmfo
и минимальных fixtures. Использовать только собственные копии/управляемые ИБ
в соседнем `eska-playground`; пользовательскую ИБ, исходники и данные не менять.
Отдельно фиксировать подготовку, выполнение, проверку результата и случаи,
которые не выполнены из-за недоступного runtime/лицензии/данных.

Приёмка: виртуальные таблицы и параметры, связанные схемы, вложенные запросы,
временные таблицы, объединения, HAVING, несколько итогов и СКД; установленный
VSIX ru/en, сохранность XML/BSL и Undo/Redo. Сборка/выгрузка выполняются через
ESKA. Изменённый BSL проверяется доступным BSL Analyzer. Матрица Linux/VSCodium
не означает приёмку Windows/macOS/VS Code/Remote.

## Общие проверки и поставка

Каждая законченная причина изменения фиксируется отдельным commit. Для
implementation tasks применяются [общие правила](working-agreement.md),
полные Rust gates, строгий Rustdoc и релевантные core/RPC/native проверки.
Для адаптера обязательны TypeScript, Node/Bun и проверка установленного VSIX.
Публичные изменения API согласуются capability/version и документируются.
`DONE` отмечается только после фактической приёмки соответствующего scope.
