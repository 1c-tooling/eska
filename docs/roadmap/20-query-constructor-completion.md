# T109–T114 — Продолжение конструктора запросов

Очередь явно разрешена пользователем 2026-10-24:
**T109 → T110 → T111 → T112 → T113 → T114**.
Она продолжает [T108](19-query-advanced.md). Выполнение начинается со связанных
метаданных базы и расширений; соседние CLI, debugger и форматы в неё не входят.

Для всех задач ESKA владеет разбором, областями, связями, типизированной моделью,
проверками и минимальными планами правок. Explorer проверяет DTO и отображает
контролы, навигацию и штатный Undo/Redo. Новый адаптер IDE использует те же RPC;
собственного парсера, генератора запросов и правил метаданных в нём нет.
Designer XML остаётся единственным форматом; внешний анализатор не форкается.

## T109 — Связанные метаданные базы и расширений

**Статус:** `DONE`. Выполнено 2026-10-24; [проверки](../measurements/t109-related-metadata.json).

Единый каталог выбранного приложения разрешает наследуемые свойства и поля
заимствованных объектов, планы счетов, графики и базовые регистры расчёта во всех
его sources. Порядок расширений соответствует конфигу приложения. Объекты других
приложений не подмешиваются. Объявленный, но отсутствующий/нечитаемый descriptor
не превращается в успешный пустой ответ. Без базы сохраняется ограниченный контекст.

Приёмка: base+extension fixtures и RPC ru/en, новые и заимствованные объекты,
переопределения свойств, связанные схемы в соседнем member, отсутствие записи,
чужие sources и неизвестная связь. Корректность каталога принадлежит ESKA;
интерфейс использует существующий контракт, если его достаточно.

## T110 — Временные таблицы и пакеты

**Статус:** `DONE`. Выполнено 2026-10-24; [проверки](../measurements/t110-query-packages.json). Зависит от T109.

Добавить `ПОМЕСТИТЬ/INTO`, создание, использование и удаление временных таблиц.
Колонки выводятся из проекции создающего запроса; видимость зависит от порядка
операторов пакета. Переименование и проверки зависимостей выполняет ESKA.
Пакет остаётся одним исходным текстом; комментарии, окончания строк и независимые
операторы сохраняются без перегенерации. Интерфейс выбирает оператор и его свойства.

Приёмка: цепочки временных таблиц, `UNION`, `*`, повторное создание после удаления,
неизвестные/неоднозначные ссылки, атомарный отказ и native apply/cancel/Undo ru/en.

Уточнение T114: реальная платформа 8.3.27.2325 принимает английское `DROP`,
а не использовавшееся ранее `DESTROY`. Исправлены разбор, генерация и проверки
в ESKA; RPC-значение операции `destroy` сохранено. Неизвестный `DESTROY`
остаётся непрозрачным исходным текстом без ложной семантики временной таблицы.

## T111 — Отбор по агрегатам

**Статус:** `DONE`. Выполнено 2026-10-25; [проверки](../measurements/t111-having.json). Зависит от T110.

Добавить `ИМЕЮЩИЕ/HAVING` отдельной секцией после группировки и до общего хвоста.
Типизированные условия, добавление, изменение, удаление и перенос комментариев
реализуются в ESKA. UI отличает отбор до группировки от отбора по агрегатам.

Приёмка: оба языка запросов независимо от языка IDE, вложенные области,
объединения, агрегатные выражения, безопасные отказы и точный no-op.

## T112 — Секция итогов и уровни группировки

**Статус:** `DONE`. Граница уточнена и проверена в T114: [core, RPC, редактор
и реальная платформа](../measurements/t114-native-query-runtime.json). Прежний
[отчёт](../measurements/t112-total-sections.json) подтверждает только редактор.
Зависит от T111.

Платформа 8.3.27.2325 отклоняет повторное `ИТОГИ/TOTALS` на обоих языках.
Повторение из встроенной грамматики не подтверждено исполнением. ESKA разрешает
одну секцию с несколькими выражениями и уровнями группировки; API 1.30 явно
объявляет лимит 1. Повторное добавление отклоняется атомарно; исходные несколько
секций остаются непрозрачными и сохраняются без изменений. Основная логика
и разрешения принадлежат ESKA; UI использует полученные DTO.

Приёмка: одна секция, несколько уровней, общие/автоматические итоги, иерархия,
периоды, комментарии, `UNION`, неактивные вложенные итоги, атомарный отказ второй
секции и точное сохранение неподдержанного исходного текста. Независимые
последовательные секции не заявляются как исполнимая возможность платформы.

## T113 — Конструкции языка СКД

**Статус:** `DONE`. Выполнено 2026-10-25; [проверки](../measurements/t113-dcs.json). Зависит от T112.

По первичной справке платформы определить и реализовать типизированное
редактирование конструкций языка СКД: необязательных полей, источников/условий
и параметров виртуальных таблиц в поддерживаемых позициях. Точные границы
фиксируются перед реализацией по грамматике платформы. Неизвестные конструкции
остаются точным непрозрачным текстом; поддержка не объявляется по наличию скобок.

Граница T113 по встроенной справке 8.3.27.2325
`dcsui_ru.hbk: SKD_ExtQueryLangv`: списки доступных полей `{ВЫБРАТЬ …}`
(псевдонимы основной проекции, только первая ветка), `{ГДЕ …}` (поля таблиц,
дочерние поля, псевдонимы и бинарные условия), переключение необязательности
существующего JOIN с сохранением его тела, `{&Параметр}` в позициях периода
виртуальной таблицы и списки полей/условий в её параметре отбора. ESKA определяет
позиции и типы по сигнатурам, строит фрагменты и проверяет минимальные правки.
Редактирование выполняется отдельной моделью СКД над тем же исходным текстом;
обычные секции запроса с расширениями остаются консервативно непрозрачными.
Характеристики, произвольные макросы, сложные неподдержанные элементы и неизвестные
позиции доступны только для точного сохранения. Полная проверка платформой — T114.

Приёмка: настоящие запросы СКД Designer XML и автономные fixtures ru/en,
точное извлечение/возврат в XML, комментарии, атомарные отказы и интерфейс адаптера.

## T114 — Приёмка запросов реальной платформой

**Статус:** `IN-PROGRESS`. Зависит от T113.
[Результаты и оставшаяся работа](../measurements/t114-platform-acceptance.json), 2026-10-25.

Проверить сформированные запросы платформой 1С на отдельной тестовой ИБ buhmfo
и минимальных fixtures. Использовать только собственные копии/управляемые ИБ
в соседнем `eska-playground`; пользовательскую ИБ, исходники и данные не менять.
Отдельно фиксировать подготовку, выполнение, проверку результата и случаи,
которые не выполнены из-за недоступного runtime/лицензии/данных.

Приёмка: виртуальные таблицы и параметры, связанные схемы, вложенные запросы,
временные таблицы, объединения, HAVING, несколько итогов и СКД; установленный
VSIX ru/en, сохранность XML/BSL и Undo/Redo. Сборка/выгрузка выполняются через
ESKA. Изменённый BSL проверяется доступным BSL Analyzer. Матрица Linux/VSCodium
не означает приёмку Windows/macOS/VS Code/Remote.

Редактор принят на Linux/VSCodium: 16 сценариев установленного VSIX ru/en и
четыре проверки копии buhmfo с внешним анализатором. Приёмка выявила и устранила
неверную границу неименованного `CASE` в модели СКД и бесконечный возврат фокуса
при несохранённом XML-родителе. Дополнительно устранено взаимное ожидание
проекции и отложенного открытия скрытого BSL-модуля в LSP-синхронизации.
Регрессионные проверки фокуса и синхронизации воспроизводили ошибки до
исправлений; XML-сценарий после исправления фокуса повторно прошёл в каждой
локали. Полные Rust gates, строгий Rustdoc, TypeScript и Node/Bun пройдены.

Платформенная часть не принята: подготовлены 13 запросов, выполнено **0**.
Минимальная конфигурация собрана и применена, но два запуска клиента
8.3.27.2325 завершились `License not found`. Полная buhmfo собрана в `.cf`,
однако обновление отдельной файловой ИБ отменено с
`Index key length exceeds maximum allowed` для `_InfoRg60459_5@`.
Три расширения собраны; `external-systems` и `dzp-typical-code` не прошли импорт
XML из-за ссылок на предопределённые значения и значения цвета соответственно.
Установленный ESKA не поддерживает `--base-configuration` при сборке расширений;
контекстную причину ошибок ещё требуется подтвердить.

Для завершения нужны лицензированная тестовая среда и успешно обновляемая ИБ
buhmfo с расширениями. Затем требуется закончить платформенные fixtures и
исполнитель матрицы, выполнить запросы, сравнить колонки, значения, временные
таблицы и итоги, проверить связанные метаданные по применённой конфигурации.
Подготовленный `retry-probe.py` проверяет только `SELECT 1` и доступность runtime;
он не выполняет всю матрицу. Сборка `.cf` и проверки редактора не заменяют эти шаги.

Ручной стенд `../eska-playground/buhmfo-query-manual-d5inc0y_` обновлён до
API 1.29 и девяти вкладок с резервной копией компонентов. Его исходники,
профиль и открытое окно не изменялись; новый комплект устанавливается следующим
запуском `run.sh`. Стенд предназначен для проверки редактора, без выполнения
запросов в информационной базе.

## Общие проверки и поставка

Каждая законченная причина изменения фиксируется отдельным commit. Для
implementation tasks применяются [общие правила](working-agreement.md),
полные Rust gates, строгий Rustdoc и релевантные core/RPC/native проверки.
Для адаптера обязательны TypeScript, Node/Bun и проверка установленного VSIX.
Публичные изменения API согласуются capability/version и документируются.
`DONE` отмечается только после фактической приёмки соответствующего scope.
