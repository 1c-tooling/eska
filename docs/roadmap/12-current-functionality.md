# Улучшение текущего функционала

Задачи сформированы по анализу текущего кода и CLI от 2026-09-08. Они расширяют
завершённые этапы, не меняя их исторические статусы `DONE`. Порядок выполнения
задан в [трекере](README.md); следующей после завершённой T29 остаётся T49.

## T49 — Стабильные JSON-ошибки и обратимые пути

**Статус:** `NEXT`
**Зависит от:** T12, T28, T47

Подтверждённые ограничения:

- `build --format json` при незаданной платформе возвращает пустой stdout,
  exit code 1 и локализованный текст в stderr; одиночная ошибка исполнения также
  не формирует JSON-документ;
- `status --format json` преобразует корни проекта/workspace через
  `to_string_lossy()`, а branch — в `String` без обратимого представления байтов.

Сначала описать общий контракт ошибок для уже существующих JSON-режимов:
стабильные `code`, необязательные `stage` и project context, документированные
stdout/stderr и exit codes. Определить границу между ошибками разбора аргументов
и ошибками выполнения команды. Реализовать его для всех ошибок `build` после
успешного parsing, включая discovery, selection, preflight, поиск платформы,
одиночное исполнение и aggregate failures. Сверить контракт с текущим `patch`.

Отдельной логической частью исправить представление путей и Git byte strings
в single/aggregate `status`; использовать проверенные подходы существующих
`diff`/`history`/`build`. Согласовать versioning: существующие успешные JSON-схемы
и значения для UTF-8 не менять несовместимо без явной новой версии протокола.
Массовая переработка human output и добавление JSON к остальным командам сюда
не входят.

**Готово, когда:** RU/EN дают одинаковые machine-facing ошибки; ранняя и поздняя
ошибки сборки доступны без разбора текста; пути и ветки восстанавливаются без
потерь; регрессионные проверки сохраняют существующие успешные схемы, aggregate
results и отсутствие ANSI в перенаправленном выводе.

## T50 — Анализ только затронутых объектов и явный fallback

**Статус:** `PLANNED`
**Зависит от:** T19, T21, T22, T47

`save` без `-m` и workspace semantic diff вызывают полное обнаружение объектной
модели. Генератор workspace draft делает это для каждого выбранного member,
включая проекты без изменений. Ошибки модели/анализа в draft молча превращаются
в точное файловое описание.

Пропускать members без изменений и строить необходимый набор descriptors от
changed paths: затронутые объекты, их владельцы и нужные snapshot-версии для
удалений/переименований. Сохранить UUID identity, staged/worktree edges,
revision comparison и точный file-level fallback. Нераспознанный изменённый
объект не должен отменять анализ остальных независимых объектов.

При упрощении draft показывать причину и область неполного анализа в RU/EN,
сохраняя возможность `save`; диагностические предупреждения не включать в
сообщение коммита. Для semantic JSON ошибки и неполнота должны быть различимы
по документированному контракту, без скрытого изменения схемы.

**Готово, когда:** результаты корректных сценариев совпадают с baseline;
неизменённые members и посторонние descriptors не читаются без необходимости;
проверены удаления, перемещения, inline/standalone identities и повреждённый XML.
Записать сравнимые замеры времени, памяти и числа прочитанных descriptors на
большой выгрузке с малой delta. Persistent cache и полный BSL parser не входят
в задачу; оценка ускорения до замеров не считается результатом.

## T51 — Предварительный просмотр `eska save`

**Статус:** `PLANNED`
**Зависит от:** T15, T22, T47, T50

Добавить `save --dry-run`: точные включаемые пути и состояния файлов, выбранный
project/workspace scope и draft сообщения либо переданное `-m`. Использовать
общую с исполнением подготовку, чтобы preview и commit имели одинаковый scope.
Сохранить текущую семантику одного `-p` и полного `--workspace`.

Preview не запускает editor/hooks, не меняет index, refs или worktree и не
создаёт commit. Он описывает снимок на момент проверки, не обещая неизменность
файлов при отдельном последующем запуске; реальное сохранение повторяет preflight.

**Готово, когда:** RU/EN preview соответствует составу последующего commit на
неизменённом снимке; проверены unborn HEAD, staged + unstaged, удаления,
untracked/ignored, sibling staging, конфликты и пустой scope. До/после preview
состояние repository совпадает побайтно. Выбор отдельных hunks не добавляется.

## T52 — Предварительный просмотр `eska build`

**Статус:** `PLANNED`
**Зависит от:** T28, T46, T49

Добавить `build --dry-run` поверх существующих `BuildPlan` и group preflight.
Показывать members в порядке исполнения, source, artifact type/path,
существование заменяемого результата, требуемую и найденную платформу и runner.
Поддержать human и отдельный документированный JSON-документ плана.

Разрешены проверки файлов, поиск инструментов и чтение их версии. Не создавать
каталоги artifacts/временные базы и не запускать import/build. План не заменяет
повторный preflight обычной сборки и не гарантирует, что 1С примет XML/BSL.
Все пути проходят те же проверки, что при исполнении.

**Готово, когда:** preview single/aggregate совпадает с планом обычной сборки;
проверены selectors, overrides, коллизии outputs, отсутствующая платформа и
ошибки members; файловая система не изменяется, JSON не зависит от locale.

## T53 — Завершение задачи после squash/rebase

**Статус:** `NEEDS-SPEC`
**Зависит от:** T40

Текущий `finish` с `require-integrated` проверяет достижимость исходного task tip.
После squash/rebase это может отклонять задачу, изменения которой уже перенесены.
Текущий консервативный контракт T40 остаётся действующим до отдельного расширения.

Перед реализацией описать способ подтверждения интеграции и пользовательский
сценарий, если Git ancestry её не доказывает. Разделить доказанное завершение,
просмотр оставшихся различий и явный возврат на base с сохранением task branch.
Не считать один совпавший patch-id или отсутствие различий по отдельным файлам
достаточным доказательством для автоматического удаления ветки. Не ослаблять
`require-integrated` глобально и не делать MR/PR provider обязательной зависимостью.

**Готово, когда:** зафиксированы CLI/policy, критерии удаления или сохранения
локальной ветки, поведение без сети и матрица обычного merge, squash, rebase,
частичной интеграции, последующих правок target и неоднозначных случаев. После
спецификации перевести задачу в `PLANNED`; `DONE` означает реализацию и проверку
принятого сценария, а не только написание документа.

## T54 — Паспорт собранного артефакта

**Статус:** `PLANNED`
**Зависит от:** T25, T28, T45, T46, T49

Добавить явный режим обычного `build`, сохраняющий рядом с результатом
машиночитаемый паспорт с собственной версией схемы: проект, версия 1С-проекта,
artifact type, версия платформы, commit и dirty state при наличии Git,
контрольная сумма артефакта и идентификатор фактического снимка исходников.
Отсутствующий Git или недоступная версия описываются явно, не выдумываются и
не меняют доступность обычного `build` без паспорта.

Метаданные должны описывать входы, действительно прочитанные сборкой. Для режима
с паспортом зафиксировать снимок исходников и читать версию из него; commit и
dirty flag сами по себе не обеспечивают воспроизводимость. Сохранить байты,
containment и правила исключения результатов из снимка. Наличие паспорта не
обещает побайтно детерминированный результат платформы 1С.

Определить согласованную публикацию пары artifact/manifest: ошибка не оставляет
новый artifact со старым паспортом или наоборот; старые результаты сохраняются
при неуспехе. В workspace каждый member получает паспорт своего результата.
Не записывать credentials и machine-local secrets. `patch`, signing, upload и
release automation остаются отдельными расширениями.

**Готово, когда:** паспорт относится к реально собранному снимку и checksum
результата; проверены clean/dirty/no-Git, изменение исходников во время сборки,
ошибка публикации пары и частичный успех workspace. Обычный build и его текущий
JSON-контракт сохраняются.

## T55 — Переносимые проверки сборки

**Статус:** `PLANNED`
**Зависит от:** T28, T46, T52, T54

Основной набор `tests/cli/build.rs` ограничен `cfg(unix)` и использует shell fake
`ibcmd`. Вынести portable process-fixture без зависимости от Unix shell;
системные сценарии Distrobox оставить отдельными Linux-проверками.

Покрыть Windows и Unix: пути с пробелами/кириллицей, все четыре artifact types,
version mismatch, JSON, workspace, dry-run, паспорт, замену результата,
прерывание и cleanup управляемой временной базы. Проверки должны исполнять
реальный процессный путь; fake tool не подтверждает совместимость платформы 1С.

**Готово, когда:** переносимые сценарии успешно выполнены на Windows и Linux,
для macOS записан отдельный результат проверки host runner. Протокол реальной
1С указывает ОС, версию, команды и полученные artifacts; недоступные сочетания
помечены непроверенными. Изменения GitHub Actions и publication pipeline в scope
не входят; одна компиляция под Windows не заменяет запуск тестов на Windows.
