# Схемы и дерево Конфигуратора

T65 реализована в `project::configurator`. Это библиотечное построение дерева,
ещё не расширение VS Code и не команда IDE. `ConfiguratorSchema::for_source`
выбирает схему по проверенному `eska.toml`; `ConfiguratorTree::build` принимает
разобранный descriptor и сведения о наличии модулей. Дерево не читает файлы.

Конфигурация и расширение имеют корневые разделы. Внешние отчёт и обработка
имеют собственный объект-корень с реквизитами, табличными частями, формами,
командами и макетами. Менеджер конфигурационного отчёта/обработки не добавляется
внешнему объекту даже при наличии одноимённого файла.

Первая группа владельца — «Модули», раскрытая по умолчанию. После проверки
показываются только применимые роли с существующими BSL-файлами; `.bin` не
становится модулем дерева. Если BSL нет, группа отсутствует, объект остаётся.
Состояние последующего раскрытия хранит будущий клиент, а не эта проекция.
`ModuleAvailability::resolve` проверяет только BSL-пути владельца, не читая код.
Отсутствие результата проверки означает `Unloaded`, ошибка — `Failed`;
непроверенная группа не содержит вымышленных модулей.

Порядок корня: модули при наличии, «Общие», «Константы», «Справочники»,
«Документы» и последующие классы из общей таблицы `METADATA_ORDER`.
«Нумераторы» и «Последовательности» вложены в «Документы» перед объектами.
Таблица вынесена из CLI в core; ранги существующего semantic diff сохранены.
Имена объектов внутри коллекции идут в порядке объявления XML, без сортировки
по имени или синониму. Порядок самих коллекций задаёт схема, не порядок XML.

Справочник имеет реквизиты, табличные части, формы, команды и макеты;
регистр — измерения, ресурсы, реквизиты, формы, команды и макеты. У регистра
расчёта дополнительно есть перерасчёты; у плана счетов — признаки учёта и
признаки учёта субконто; у задачи — реквизиты адресации. Последний вид
`AddressingAttribute` добавлен после чтения реального XML задачи большого стенда.

Реквизиты табличных частей, вложенные подсистемы, измерения последовательностей/
перерасчётов и подчинённые элементы сервисов показываются непосредственно
под владельцем. Дополнительная одноимённая виртуальная папка не создаётся.

`NodeId` различает объект, коллекцию и модуль. Родитель в дереве может быть
виртуальной группой и не подменяет логического родителя метаданных. Core
возвращает имя объекта либо ключ подписи; RU/EN строки находятся в Fluent.
Никакой зависимости core от CLI/locale нет. Wire-формат относится к T69.

`TreeOptions::default()` скрывает только доказанно пустые разделы корня
конфигурации/расширения. Вложенные пустые группы сохраняются; у внешних объектов
это правило не скрывает реквизиты/формы. «Общие» и «Документы» не пусты, если
содержат данные в подгруппах. `Empty`, `NonEmpty`, `Unloaded`, `Error` различаются;
переключение фильтра не меняет IDs и не читает XML.

Неизвестные теги и неподдержанные сочетания owner/children остаются в группе
«Неподдержанные элементы». Diagnostics сохраняют диапазон исходного XML;
незнакомый descriptor не выдаётся за успешно прочитанную пустую ветвь.
Для внешних источников данных это пока fallback для таблиц, кубов, функций
и их потомков: эти виды отсутствуют в исходной матрице T60 и ещё не имеют
проверенного Designer resolver. Полная поддержка их внутреннего дерева
не заявляется. Сам раздел внешних источников и известный объект сохраняются.

## Основания и пределы проверки

Пользователь зафиксировал эталон **8.3.27.2325**. XML большого стенда — Designer
2.20. Установленного Конфигуратора для живого UI-сравнения в этой среде нет;
точное визуальное совпадение этой сборки платформы не проверялось.

Использованы текущий справочник платформы через bsl-analyzer-reference,
[описание дерева 1С](https://1c-dn.com/1c_enterprise/configuration_object_tree/),
[пример документа, рис. 4.27](https://1c-dn.com/library/tutorials/practical_developer_guide_lesson4_designer4/)
и руководство разработчика 8.3.27. На иллюстрации отдельно проверены прямая
вложенность реквизитов табличной части и положение нумераторов/последовательностей.
Список свойств справочника подтверждает допустимые коллекции, а не их UI-порядок.
[Сохранённая сверка](measurements/t65-schema-reference.json) отмечает и случаи,
где справочник не дал точного типа внешнего объекта. Настройки хранилища
взяты из фактических XML: в них есть отдельные формы.

Тесты проводят XML через parser и дерево, отдельно проверяют IDs и RU/EN
подписи. Эталонные снимки покрывают четыре вида проектов, справочник с
табличной частью, четыре вида регистров и модули. Матрица схем проверяет
66 зарегистрированных типов, включая явно описанный fallback. Синтетические
фрагменты не объявляются конфигурациями, проверенными загрузкой в платформу.

Read-only smoke большого стенда: 18 751 ссылка, 18 804 узла, 104 мс на построение
дерева из уже прочитанного корня в debug/Linux. Проверены отдельные descriptors
42 представленных в корне видов. Это один запуск, не p95 и не время открытия
проекта/отрисовки VS Code; производительность всего backend проверяет T68.
Исходники стенда не изменялись, сборка и платформа 1С не запускались.
